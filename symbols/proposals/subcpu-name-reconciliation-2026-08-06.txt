# Sub-CPU name reconciliation, 2026-08-06
#
# The three sub-CPU artifacts -- the authoritative LLVM source (v142/subcpu/*.s),
# the parallel ASL archive (archive/asl/subcpu/kn5000_subprogram_v142.asm) and the
# hand-curated symbol reference (symbols/subcpu_symbols_reference.txt) -- had
# drifted apart. Matching was done by ADDRESS (llvm-nm -n on the LLVM ELF against
# ASL's own `-g map` symbol table), never by name text.
#
# Before: 2409 addresses agreed across all three, 899 disagreed.
# After:  3317 agree, 0 disagree.
#
# ORIGIN OF THE DRIFT
# Three dedicated naming/documentation passes on 2026-07-26 -- 350aa28 (pitch /
# velocity / TVF), 1ebc634 (amplitude / envelope / voice lifecycle) and 808ad6f
# (wave / sample selection) -- landed their researched names in the ASL archive and
# the symbol reference ONLY. They never touched the LLVM source, which kept the
# older, pre-analysis structural names from 3d87c95. So for these routines the
# "authoritative" file held the WORSE name, and the two mirrors held the better one.
# Direction of each fix below was therefore decided per address by reading the
# machine code, not by preferring a file.
#
# Verdict column:  CURATED = adopted the ASL/reference name into the LLVM source
#                  SOURCE  = adopted the LLVM name into the ASL + reference
#                  THIRD   = both were wrong; a new name was derived
# 114 parents were renamed; 235 sub-labels were re-parented to follow them.

## ---------------------------------------------------------------------------
## A. Keybed vs tone-generator (the block all three artifacts fought over)
## ---------------------------------------------------------------------------
# 0x03D0DA reads the hardware latch at 0x110000. The ASL source's own comment
# already records that "0x110000 / 0x110002 are the keybed data and status ports,
# NOT tone-gen", and the reference's own curated data symbol at 0x004A48 is
# Keybed_Touch_Mode. The code at 0x03D11F takes the raw key byte, clears bit 7,
# adds 0x24 (= MIDI note 36, the bottom key) and stores it at (XWA+0); it then
# computes a velocity into (XWA+1) via touch-mode tables at 0x01F420/0x01F421,
# and at 0x03D1AA it subtracts a trim when the note mod 12 is in {1,3,6,8,10} --
# exactly the black keys. It is keybed note+velocity decoding, not pitch.
0x03D11F  CURATED  ToneGen_Calc_Pitch          -> Keybed_Decode_Event
0x03D1AA  THIRD*   ToneGen_Pitch_Adjust        -> Keybed_Vel_BlackKey_Trim   (* reference also fixed)
0x03D1C4  THIRD*   ToneGen_Pitch_Clamp         -> Keybed_Vel_Clamp
