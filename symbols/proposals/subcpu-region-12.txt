# region 12: 0x0354CA..0x0370BE
# The DSP command pipeline: the 2 KB ring buffer at 0x3B60 that every inter-CPU command in
# the 0x60..0x7F class is copied into, the consumer (Audio_Process_DSP) that reframes it into
# 0x2B/0x2C/0x2D messages and dispatches them, the effect-configuration buffer at 0x448E and
# its change-detection ("diff") machinery, the two DSP transports (IC311 parallel with
# handshake, IC310 two-wire bit-bang with hand-counted nop delays), and the 8-slot auxiliary
# tone-generator voice pool driven by internal 0xF0-status pseudo-MIDI packets.
#
# INTEGRATION NOTE -- READ FIRST, IT SAVES A WASTED PASS
#   The AUTHORITATIVE LLVM build already carries a real name for EVERY address in this range:
#   585 symbols, ZERO LABEL_ placeholders (verified with
#     /home/fsanches/compartilhado/llvm-project/build/bin/llvm-nm -n \
#       rebuilt_ROMs/kn5000_subprogram_v142.llvm.elf
#   filtered to 0x0354CA..0x0370BE; the 585 are exactly the non-__jrt_nop symbols).
#   symbols/subcpu_symbols_reference.txt is the file that lags: 551 of its 585 entries in this
#   range are still LABEL_xxxxxx, and the ELF and the reference file agree 1:1 on addresses.
#   So 551 of the 585 need no thought at all -- copy the ELF name verbatim against the
#   matching LABEL_. This proposal therefore does NOT re-propose those 551 one at a time.
#   What it contributes is:
#     (a) doc headers for the substantive routines (the region has 220 non-nop symbols;
#         the other 365 are pure delay-chain labels, see [DATA] "nop chains" below),
#     (b) 23 genuinely NEW names for subroutines and dispatch stubs that live INSIDE two
#         blocks the converter emitted as `.byte` data and that therefore have no symbol at
#         all in either file,
#     (c) three existing names I believe are wrong, in [UNCERTAIN], left alone as required.
#
# BUILD VERIFIED BEFORE WRITING THIS: `python3 scripts/build/compare_roms.py` reports
#   100.00% on all 8 LLVM ROMs and all 6 ASL ROMs. Address base confirmed: ROM file offset
#   = address - 0x0EF00 for offsets >= 256; every disassembly quoted below was produced with
#   `unidasm <dd'd bytes> -arch tlcs900 -basepc 0x<addr>` and matches the .s source.
#
# ★ THE BLOCK NAMED DSP_StateTable_DefaultData (0x036205-0x036304, 256 bytes) IS NOT DATA.
#   It is TEN complete subroutines. Proof: CmdHandler2C's jump table at ROM 0x0121BD holds
#   offsets that, added to the table base 0x035DD2, land on thirteen 13-byte stubs, and each
#   of those stubs does `ld A,(0x4370) / extz WA / call 0x0362xx / jrl 0x036033`. Ten distinct
#   0x0362xx targets are called, all inside the "DefaultData" block, and all disassemble
#   cleanly from their first byte and end in `ret` or a tail `jp`. Named below.
#   The block named CmdHandler2C_TableData (0x035DD2-0x035E7A) is likewise CODE -- it is the
#   thirteen dispatch stubs themselves.
#
# ================= STRUCTURES USED THROUGHOUT (all derived from code in this region) =======
#
# DSP COMMAND RING -- control block at 0x3B60, cleared by DSP2_Init:
#     0x3B60 write index (w)   0x3B62 read index (w)   0x3B64 byte count (w)
#     0x3B66..0x3E65 2048-byte data area, both indices masked with 0x7FF.
#   Producer: DSP_RingBuf_Enqueue (0x035910), reached from Audio_CmdHandler_60_7F, which is
#   entry 3 of CMD_DISPATCH_TABLE (subcpu_data_tables.s:191), i.e. inter-CPU commands
#   0x60..0x7F. Consumer: Audio_Process_DSP (0x035AC8), called once per pass of
#   Audio_Main_Loop (0x01FAE6) between MIDI_Dispatch and Audio_Process_Final.
#
# MESSAGE FRAMING inside the ring: [type][7 header bytes][payload].
#   DSP_Process_ReadNext reads the type byte; DSP_Cmd_DequeueHeader copies the 7 header bytes
#   into 0x4369..0x436F; the payload is read into the scratch buffer at 0x4370 by
#   DSP_RingBuf_ReadAndCompare. The type byte is saved at 0x4368, so 0x4368..0x436F+payload is
#   a contiguous verbatim copy of the message -- which is exactly what the reply path sends
#   back to the main CPU.
#     0x4368 type: 0x2B voice/effect parameter, 0x2C channel+global config, 0x2D effect
#                  preset / slot configuration. Anything else -> DSP_Cmd_DefaultSkip.
#     0x4369 target selector: 0x00 = global, 0x30..0x3F = DSP voice channel (low nibble =
#                  channel 0..15), 0x40 = "consume and drop".
#     0x436A sub-length / 0x7F marker (0x08, 0x09, 0x0A..0x0E, 0x7F are all tested)
#     0x436B sub-command / parameter id
#     0x436C,0x436D 14-bit value field (7 bits per byte)
#     0x436E payload byte count
#     0x436F reply/status byte; 0xFF means "no reply unless the payload actually changed"
#   0x4366 holds the ring byte count sampled at the top of each Audio_Process_DSP pass
#   (DSP_StoreBufferCount).
#
# BULK-STREAM STATE (0x60..0x7F class), the only three words that gate the consumer:
#     0x4488 total expected byte count of the stream in flight
#     0x448A bytes accumulated so far
#     0x448C stream-active flag / chunk counter  ** see [UNCERTAIN] and the wedge note **
#   A stream opens with a 32-byte chunk whose bytes +5,+6 are a two-byte length:
#   total = (b5 << 7) + b6 + 8, stored in 0x4488. (The `and WA,0x07FF` in the source is a
#   no-op on an already zero-extended byte, so this is NOT a 7-bit-per-byte MIDI packing --
#   b5 contributes its full 8 bits shifted left by 7.) Chunks accumulate into 0x448A until it
#   reaches 0x4488, at which point both are cleared and 0x448C returns to 0.
#
# EFFECT CONFIGURATION BUFFER at 0x448E, exactly 0x122 = 290 bytes, ending at 0x45AF.
#   Three independent confirmations of the size: DSP_Reset copies 0x91 words (=290 bytes) from
#   0xF01E in internal RAM to 0x448E; DSP_StateTable_Reset copies 0x91 words from it to the
#   shadow at 0x45CA; and DSP_Cmd_LoadEffectPreset refuses any 0x2D preset whose declared
#   payload size is not exactly 0x122.
#     0x448E .. 0x4495   8-byte header. +0 = "config not loaded / unchanged" flag written by
#                        DSP_ApplyConfig; +6 = a 0/1 mode word clamped by DSP_Config_ClampLimits.
#     0x4496 + n*0x38    effect slot n record, n = 0..4, 56 bytes each (EFF_GetSlotBuffer).
#   Slot record fields actually touched in this region (offsets from the slot base):
#     +0x00  algorithm number, clamped to 0..0x63 (0..99) by DSP_Config_ClampApply. Values
#            0x33/0x34/0x45/0x46 get special treatment in EFF_SlotActive_UpdateFlags.
#     +0x02  one word, diffed by DSP_EFFParam_DiffMid
#     +0x04..+0x24  seventeen words, diffed by DSP_EFFParam_DiffInnerBody
#     +0x1E  word read by EFF_SlotActive_LoopNext as an index (doubled) into the dirty array
#     +0x28  one word, diffed by DSP_EFFParam_DiffLevel4Body
#     +0x30  word compared against 0x63 by EFF_SlotActive
#     +0x36  word, diffed by DSP_EFFParam_DiffAlgoSection
#   SHADOW COPY of the whole 290 bytes at 0x45CA (DSP_StateTable_Reset writes it at the end of
#   every DSP_State_ApplyAll, so "shadow" == "state as of the last apply").
#
# GLOBAL MIXER / ALGORITHM WORDS just above the config buffer:
#     0x45B0 voice-type/algorithm selector (copied to 0x44B4 = slot 0 record +0x1E by
#            DSP_ApplyAlgoForVoiceType)
#     0x45B2, 0x45B4, 0x45B6  the three arguments of DSP_MixerCoeff_Compute (0x03C067)
#     0x45B8, 0x45BA  a value/enable pair; 0x45B8 is copied to 0x454A (= slot 3 record +0x0C)
#            only when 0x45BA != 0
#     0x45BC + n*2   five words of per-slot pending state, read-and-cleared by
#                    DSP_SlotMuteState_ReadAndClear
#     0x45C8 result word of DSP_State_ApplyAll
#
# DIRTY-FLAG ARRAYS (one word per flag, all set to 0 or 1, consumed outside this region):
#     0x4930 + n*2         five per-slot "slot is live" flags
#     0x493A + i*2         two DSP-link flags (i = 0,1)
#     0x493E               global "algorithm changed" flag
#     0x4940 + n*0x32      per-slot dirty block, 50 bytes per slot, n = 0..4:
#         +0x00 slot changed        +0x02 + i*2  one word
#         +0x04 + i*2  seventeen coefficient-changed words
#         +0x10 relative to 0x4958/0x495A/0x495C/0x495E/0x4960 -- five separate "changed"
#               words, of which the 0x4960 one is the "anything in this slot changed" summary
#         +0x26 (base 0x4966) one further word
#
# TONE-GENERATOR AUXILIARY POOL (Voice_Poly_NoteOn and its two setup routines):
#     0x3B13 round-robin slot index, masked to 0..7
#     0x3B14..0x3B1B eight owner bytes, one per slot; bit 7 = "slot in use"
#     0x3B1C..0x3B5F 68-byte TG staging block, refilled from the ROM template at 0x012115
#                    (0x22 words) on every note-on
#     Latch encoding is region 6's: value written to 0x100000 is (register << 6) | voice.
#     0x800 + slot = register 0x20, voice `slot`;  0x840 + slot = register 0x21, voice `slot`.
#     Note-on writes 0xFF00 to reg 0x21 then 0xFF80 to reg 0x20; release writes 0xA200 then
#     0xA280. Every pair is bracketed by res/set 7,(P6) exactly as region 6 documented.
#
# ============================================================================================

[ROUTINE] 0x035656 TONEGEN_SETUPPERCUSSIONVOICE  replaces=LABEL_035656  confidence=high

[ROUTINE] 0x0356C9 VOICE_POLY_NOTEON  confidence=high
; ALREADY NAMED in the reference file -- doc header only, no rename.
; Handler for internal pseudo-MIDI packets whose status byte is >= 0xF0. Reached from
; MIDI_Dispatch (0x0323F0 area) with XWA pointing at the 4-byte packet in the MIDI scratch
; at 0x2AF4: +1 = status (0xF0 | channel), +2 = note, +3 = velocity.
; The KN5000's own firmware injects such packets: DSP_WriteAlgoInitPreset and
; DSP_SlotState_DisplayRestore push one of the canned 4-byte messages at ROM 0x0121EB /
; 0x0121EF / 0x0121F3 (`F0 50 B0 01`, `F0 50 B0 05`, `F0 50 B0 06`) into the MIDI ring via
; Audio_CmdHandler_00_1F and then call MIDI_Dispatch immediately. So this is the path the
; DSP subsystem uses to make the tone generator produce its own reference tone.
; Behaviour:
;   channel = status & 0xF; if status < 0xF0 return; if channel > 5 force channel = 0
;   slot = (0x3B13) = ((0x3B13) + 1) & 7        -- pure round robin, the tone generator's
;                                                  active-voice bitmap is NEVER consulted
;   velocity = packet[+3] & 0x7F ; note = packet[+2] & 0x7F
;   if velocity == 0 -> Voice_Poly_NoteOn_ReleasePath (note-off)
;   else: TG reg 0x21 voice slot <= 0xFF00, TG reg 0x20 voice slot <= 0xFF80, then call
;         through the 6-entry table at ROM 0x012159 indexed by channel, then mark
;         (0x3B14 + slot) = note | 0x80.
; Hardware: writes 0x100000 (address latch) and 0x100002 (data) directly, with the
; res 7,(P6) / set 7,(P6) address-vs-data strobe and the mandatory settling nops.
