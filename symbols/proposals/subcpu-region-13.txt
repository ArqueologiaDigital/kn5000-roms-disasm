# region 13: 0x0370BF..0x038CF8
# The effects (EFF) state-application engine and the whole low-level DSP programming
# layer: the per-slot dirty-flag bookkeeping, the mute/reset/link/volume/parameter
# application loops driven by DSP_State_Dispatcher, the debug-traced wrappers that push
# bytecode programs at the two DSP chips, the GPIO bit primitives, and the byte-level
# packers that turn a 24-bit coefficient into the 5-byte word IC311 expects.
#
# METHOD (read before integrating). Every address in this region except five already
# carries a real, hand-maintained symbol in the AUTHORITATIVE LLVM build
# (rebuilt_ROMs/kn5000_subprogram_v142.llvm.elf; 178 symbols in range, dumped with
# `llvm-nm -n`). symbols/subcpu_symbols_reference.txt still shows LABEL_xxxxxx at 133 of
# them. Those 133 entries below adopt the build's name VERBATIM, so integration is a pure
# text substitution with zero semantic risk; the documentation is the new work. Twenty
# further addresses (0x038365..0x0383F7) carry non-LABEL_ names in the reference that
# differ from the build ONLY in letter case (DEBUG_PRINT_STRING vs Debug_Print_String);
# per the rules those are LEFT ALONE and argued in [UNCERTAIN]. Five addresses have no
# symbol in the reference at all and are genuinely new names (no `replaces=`).
# Verified before proposing: `python3 scripts/build/compare_roms.py` => 100.00% on all 8
# LLVM ROMs and all 6 ASL ROMs (15 "Similarity: 100.00%" lines, zero others).
# Disassembly cross-checks done with
# `/home/fsanches/compartilhado/mame/unidasm <slice> -arch tlcs900 -basepc 0xADDR` on the
# 0x30000-byte payload at file offset (addr - 0x00EF00); the base check is that 0x0370BF
# decodes to `ld BC,DE / mul BC,0x0032 / add BC,0x0010 / lda XHL,0x4958`, exactly the
# prologue the LLVM source shows for EFF_DspChannel_Init_MultiTableDirty.
# Naming style: the whole region is CamelCase-with-subsystem-prefix (EFF_*, DSP_*) in
# both sources, so the five new names follow that and not UPPER_SNAKE.
#
# THE FOUR DATA STRUCTURES THAT EXPLAIN THE WHOLE REGION (all measured from the code,
# every address confirmed by unidasm, none assumed):
#
# (A) THE CONFIG BLOCK -- 290 bytes (0x91 words; that is the LDIRW count used by
#     DSP_StateTable_Reset and by the two snapshot routines at 0x037E3E/0x037E50).
#     Layout, established here:
#       +0x00 u16 flagA  -- "rewrite the common header" (tested at 0x037A9E, 0x037D8C)
#       +0x02 u16 flagB  -- "algorithm changed"        (tested at 0x037A78, 0x037D93)
#       +0x04 u16 flagC  -- "cold / full reload"       (tested at 0x037D72, 0x037A82,
#                           0x0379C6, 0x037A19, 0x038032)
#       +0x06 u16 mode   -- 0 or 1; DSP_Config_ClampLimits (outside the region) forces
#                           anything >1 to 0. Passed to EFF_Disconnect / EFF_Link.
#       +0x08 + 56*slot  -- five 56-byte PER-SLOT RECORDS (slot = 0..4).
#     PER-SLOT RECORD (56 = 0x38 bytes; the stride is computed everywhere in this region
#     by the idiom `xbc=slot; sll 3 (=*8); sub xwa (=*7); sll 3 (=*56); inc 8`):
#       +0x00 u16  EFFECT NUMBER, 0..127. Index into the class table at 0x012226 and into
#                  the algorithm/parameter pointer tables at 0x01ED7C / 0x01EF0C.
#       +0x04 .. +0x24  seventeen u16 PARAMETER VALUES, param[0..16]. Proof: they are read
#                  as block+12+56*slot+2*param (0x038246, 0x0382AB), i.e. record+4+2*param,
#                  and the parameter loop is clamped to 0x11 = 17 entries at 0x0378A0.
#       +0x26 u16  index (into that array) of the VOLUME parameter. Skipped by the normal
#                  parameter iterator (0x0378D6) precisely because EFF_VolumeLoop owns it.
#       +0x2C u16  PARAMETER COUNT, clamped to 17.
#       +0x2E u16  parameter base index (only slot 0's copy is used, see 0x037127).
#       +0x1E u16  variant flag; bit 0 selects one of the two parameter-edit ORDER lists
#                  at 0x0122A6 / 0x0122B1 (0x037920).
#       +0x36 u16  LINK flag: 1 = this slot is linked into the chain, 0 = it is not.
#     Three instances of this block exist in DRAM: the working copy the caller fills in at
#     0x045324, the SHADOW ("last applied") copy at 0x0045CA, and a pair at 0x0046EC /
#     0x00480E that only the two dead snapshot routines touch (see [UNCERTAIN]).
#
# (B) THE PER-SLOT DIRTY-FLAG BLOCK -- 5 blocks of 50 bytes (25 u16) based at 0x004940,
#     block n at 0x004940 + 50*n. Every `mul <r>,0x32` in this region is this stride, and
#     the highest word any code touches, 0x004960+0x10 = 0x004970, is exactly the 25th and
#     last word of block n -- that is the proof of the 50-byte size.
#       +0x00 (0x004940) slot needs (re)programming        (0x037781, 0x0379B2, 0x037A96,
#                                                           0x037DD2)
#       +0x02 (0x004942) coefficient block A dirty
#       +0x04..+0x24 (0x004944..0x004964) seventeen PER-PARAMETER dirty flags,
#                    param i at 0x004944 + 50*n + 2*i  (0x0378BC, 0x03794E, 0x037C4C)
#       +0x26 (0x004966) coefficient block B dirty
#       +0x28..+0x2C (0x004968/0x00496A/0x00496C) three auxiliary dirty flags
#       +0x2E (0x00496E) LINK dirty          (0x037AFE, 0x037B5F, 0x037BBC)
#       +0x30 (0x004970) VOLUME dirty        (0x037997, 0x0376F8)
#
# (C) THE SMALL GLOBALS just below the shadow block, all 16-bit-direct addressable:
#       0x004930 + 2*n  EFF_SlotActive[5]   u16, 1 = slot n currently carries an effect
#       0x00493A + 2*c  DSP_ChipActive[2]   u16, 1 = chip c takes part (c: 0 = IC311
#                       "DSP1", 1 = IC310 "DSP2"); gates DSP_MuteLoop / DSP_UnmuteLoop
#       0x00493E        global "algorithm change pending" u16 (DSP_AlgorithmChangeCheck)
#       0x0045BC + 2*n  per-slot DSP-class cache, written as classtable[eff]+1 or 0
#       0x0045C8        apply-result word, cleared then returned by DSP_State_ApplyAll
#       0x001040        32-bit tick counter that DSP_WaitForDelay spins on
#
# (D) THE SLOT->HARDWARE TABLES at 0x01ED6D and 0x01ED72 (5 bytes each; see [DATA]).
#     0x01ED6D = { 0, 0, 1, 1, 1 } maps effect slot -> DSP chip number, and it is that
#     byte -- not the slot -- that EFF_Disconnect / EFF_Link / EFF_WriteHeader pass to
#     DSP_WriteGlobalConfig. 0x01ED72 = { 28, 24, 46, 20, 20 } is the per-slot settle time
#     in milliseconds that the loops max-reduce and hand to DSP_ScheduleDelay.

[UNCERTAIN] 0x037E3E DSP_State_Dispatcher_Data is a WRONG NAME in both sources and I have
left it alone as the rules require. It is not data: it disassembles cleanly to
`ld XIY,0x46EC / ld XIX,0x480E / ld BC,0x91 / ldirw / ld HL,0 / ret`, an 18-byte routine
that copies one 290-byte config block from 0x0046EC to 0x00480E, and the next 18 bytes are
its inverse (which I have proposed as EFF_ConfigSnapshot_Restore at 0x037E50). I recommend
renaming it to EFF_ConfigSnapshot_Save. Both are dead code -- no caller exists in the
payload -- but calling live code "data" hides the fact that 0x0046EC and 0x00480E are two
more config-block-sized RAM regions.

[UNCERTAIN] EFF_Disconnect (0x037F4F) and EFF_Link (0x037FAE) compute their pointer-table
index as `base + 12*mode + 4*slot` (verified byte by byte: `xde=mode; xde+=xde; xde+=xwa;
sll 2,xde` = mode*12). But the two tables are five 32-bit pointers each and lie back to
back at 0x01F3F0 and 0x01F404, so the natural mode stride is 20, not 12. With mode == 1 --
a value DSP_Config_ClampLimits explicitly permits, it only rejects >1 -- slot 2 and slot 3
of a disconnect would fetch the LINK table's first two pointers. Either (a) block[+0x06] is
never actually 1 on the paths that reach these two routines, or (b) this is a genuine
firmware indexing defect. I could not settle it from the disassembly alone; it needs a
trace of block[+0x06] on real hardware or in MAME. Recorded, not acted on.

[UNCERTAIN] The class table at 0x012226 yields 1 or 2 for effects that need a DSP program.
