# region 6: 0x027A91..0x02AD02
# MIDI channel-voice application layer: the 26 "part" records, the CC / channel-pressure /
# pitch-bend / system-message handlers that write them, the per-audio-tick voice state
# machine that retires and re-triggers notes, and the low-level tone-generator per-voice
# register-write primitives (0x100000/0x100002) that every one of those paths funnels into.
#
# INTEGRATION NOTE (read first, it saves a wasted pass):
#   The AUTHORITATIVE LLVM build already carries a real name for EVERY address in this range
#   -- 243 symbols, ZERO LABEL_ placeholders (verified with
#   `llvm-nm -n rebuilt_ROMs/kn5000_subprogram_v142.llvm.elf`).
#   symbols/subcpu_symbols_reference.txt is the one that lags: 198 of its 223 entries in this
#   range are still LABEL_xxxxxx.  Those 198 need no thought -- copy the ELF name verbatim.
#   This file therefore does NOT re-propose them.  What it contributes is (a) doc headers for
#   the existing names, (b) genuinely NEW names for the ~30 subroutine entry points that live
#   INSIDE the three blocks the converter emitted as `.byte` data and that consequently have
#   no symbol at all, and (c) three ELF symbols missing from the reference file.
#
# ★ THE THREE "DataTable" BLOCKS IN THIS REGION ARE NOT DATA, THEY ARE CODE.
#   VoiceCC_DataTable_0280FE (0x0280FE-0x028838, 1851 bytes),
#   VoiceCC_DataTable_028F75 (0x028F75-0x029E30, 3772 bytes) and
#   VoiceModWheel_DataTable_02A061 (0x02A061-0x02A0E8, 136 bytes)
#   -- 5623 bytes total -- disassemble cleanly as TLCS-900H from their first byte and are
#   reached by ordinary `calr`/`jrl` from named code.  Names carrying "DataTable" are
#   actively misleading; see [UNCERTAIN] at the end.
#
# STRUCTURES USED THROUGHOUT (all verified from the code in this region):
#   PART table   0x041368, 26 entries x 0x11F bytes.  Index = MIDI part 0..0x19.
#                +0x02 flags word (b0 delay-enable, b5 LFO-active)
#                +0x06 long pointer to the patch/tone descriptor
#                +0x0A flags word 2 (b0 sustain, b2 chorus, b6 sostenuto)
#                +0x0F sostenuto  +0x10 expression  +0x12 soft  +0x13 porta rate
#                +0x14 porta depth (w)  +0x16 porta time  +0x17 reverb depth
#                +0x18 chorus depth  +0x1B..+0x20 scaled modulation results
#                +0x25 delay depth  +0x26 delay feedback
#                +0x63 LFO/ramp state byte  +0x6E.. 4 x 0x25-byte output-slot records
#                +0x102.. portamento target words  +0x10E/+0x110/+0x112 mix weights
#   VOICE table  0x04308E, 64 entries x 0x47 bytes.  Index = hardware voice 0..0x3F.
#                +0x00 voice number  +0x01 flags word (b8 hold, b10 legato, b15)
#                +0x01 &0x3C = voice "section" selector, values 4/8/0x10/0x20
#                +0x04 owning part  +0x13 long ptr  +0x23 long ptr to the tone record
#                +0x2D word  +0x2F note-off/portamento request word (mask 0x8080)
#                +0x31 portamento-active word (bit 15)  +0x40 byte
#   TG STAGING   0x0451CC, the scratch record every ToneGen writer reads its payload from.
#   GLOBALS      0x041342 audio-tick phase byte, 0x041343 global flags word,
#                0x041347 master tune, 0x041349 pitch-bend range, 0x04134B/4C/4D,
#                0x04134E..0x041359 twelve per-pitch-class bytes, 0x04135C,
#                0x04135E..0x041365 rhythm-mode block.
#
# ★ TONE-GENERATOR ADDRESS-LATCH ENCODING (measured here, 30+ independent instances):
#   latch value written to 0x100000 = (register_number << 6) | voice_number,
#   i.e. 64 voices per register.  Every write is bracketed by
#       res 7,(0x18)   ; P6 bit 7 low  -- address phase
#       ld (0x100000),WA
#       nop
#       set 7,(0x18)   ; P6 bit 7 high -- data phase
#       ld (0x100002),WA
#       jr $+2 / nop / nop / nop        ; fixed settling delay, NOT dead code
#   This independently confirms the MAME memory-map comment that latch 0x0000-0x0003 is the
#   active-voice bitmap (register 0, voices 0-63 = 4 words) and that latch 0x0180+ch is the
#   per-voice envelope level (register 6).  P6.7 is the tone generator's address/data strobe.
#   Registers seen written from this region: 0x02 amplitude, 0x04/0x05 pan pair,
#   0x06 envelope level, 0x07, 0x10 pitch, 0x11, 0x13, 0x15, 0x16, 0x18,
#   0x20/0x21/0x22/0x24/0x25/0x27/0x28 (the three volume/EG pairs).

; Reached when the word at [voice+0x23]+0x0A has bit 15 CLEAR, i.e. the voice's tone record

four should logically be TONEGEN_WRITEVOICE_*, matching their siblings ToneGen_WriteNote2ch
and ToneGen_WriteNote6ch_*. I have NOT renamed them -- they are existing real names.

[UNCERTAIN] Voice_AllVoices_WritePan (0x028D4C) writes no pan register. It calls

[UNCERTAIN] Voice_WriteChannelAssign (0x028C14) / Voice_ReadChannelAssign (0x028C28) do not

0x0280FE VoiceCC_DataTable_0280FE, 0x028F75 VoiceCC_DataTable_028F75 and
0x02A061 VoiceModWheel_DataTable_02A061.  None of the three is a data table -- each is the
