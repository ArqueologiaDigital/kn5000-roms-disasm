# region 7: 0x02AD03..0x02C8E3
# The note-on / note-off front end: articulation-parameter setters, the per-slot pitch and
# articulation math, and the four "typed" note-on bodies that build voice-slot records,
# ask NoteOn_Dispatch for physical tone-generator slots, and commit the records.
#
# METHOD (read before integrating). Every address in this region already carries a real,
# hand-maintained symbol in the AUTHORITATIVE LLVM build
# (rebuilt_ROMs/kn5000_subprogram_v142.llvm.elf; 124 symbols in range, dumped with
# `llvm-nm -n`). symbols/subcpu_symbols_reference.txt still shows LABEL_xxxxxx at 103 of
# them. The [ROUTINE]/[LABEL] entries below therefore adopt the build's names VERBATIM so
# the two stop disagreeing -- integration is a pure text substitution, zero semantic risk.
# The documentation is the new work. Six addresses in the 0x02AE58..0x02AFBD run have NO
# symbol in EITHER source; those are genuinely new names and are marked as such (no
# `replaces=`). Six further addresses carry conflicting non-LABEL_ names in the reference
# file; per the rules those are left alone and argued in [UNCERTAIN].
# Verified before proposing: `python3 scripts/build/compare_roms.py` => 100.00% on all 8
# LLVM ROMs and all 6 ASL ROMs; disassembly done with
# `unidasm <slice> -arch tlcs900 -basepc 0x02AD03` on the 0x30000-byte payload at file
# offset 0x1BE03 (address 0x02AD03 - 0x00EF00), and 0x02AD03 decodes to the exact
# `dec 8,xsp / ld (xsp+6),a` prologue that the LLVM source shows for
# Voice_Selector_ComputeMixWeights, which is the base check.
#
# THE THREE DATA STRUCTURES THAT EXPLAIN THE WHOLE REGION (all measured, not assumed):
#
# (A) PART RECORD -- 0x041368 + part*0x11F (287 bytes). Every one of the ~70 distinct
#     absolute constants the firmware uses with `muls wa,0x11F` lies in
#     0x041342..0x041486; taking 0x041368 as the base (it is the most-used constant, 90
#     occurrences) puts the highest one, 0x041486, at +0x11E -- exactly the last byte of a
#     287-byte record. No other base fits. Confirmed independently: routines that receive a
#     slot record load its +0x23 pointer and then address it at +0x0102/+0x010A/+0x010B/
#     +0x010E/+0x0110/+0x0112/+0x0114/+0x0118, all < 0x11F (0x02B30D, 0x02B411, 0x02B31C).
#     Layout established in this region:
#       +0x02  (0x04136A) u16 LAYER-ENABLE MASK. Bits 0..3 = the four layers; bits 13/14/15
#              select which note-on variant runs. Tested at 0x02B72A, 0x02BA5D, 0x02BABF,
#              0x02BD95, 0x02BF31, 0x02C704, 0x02C80E. If this word is zero the whole
#              note-on becomes a silent no-op -- see [UNCERTAIN]/findings.
#       +0x06  (0x04136E) u32 pointer to the tone/patch record for the part.
#       +0x16, +0x6D  i8 transpose contributions (0x02B41B, 0x02B425).
#       +0x6E .. +0x101  four 0x25-byte (37) LAYER SUB-BLOCKS, indexed layer*0x25 + 0x6E
#              (0x02B73E, 0x02BDA9, 0x02C23A, 0x02C471). 4*0x25 = 0x94 and 0x6E+0x94 =
#              0x102, i.e. the array ends exactly where (B) begins -- that is the proof of
#              the entry size. Sub-block fields used: +0x00/+0x04/+0x08 u32 pointers,
#              +0x08 (=part+0x76 for layer 0) u32 pointer.
#       +0x102 .. +0x109  four u16 ARTICULATION WORDS. Written nibble-wise by the
#              0x02AE22 setter family, consumed by Voice_Slot_CalcArticParams,
#              Voice_Slot_CalcAmpNibble, Voice_Slot_FindOctaveOffset and
#              Voice_Selector_FindBestSlot.
#       +0x10A..+0x10D (0x041472..0x041475) four i8 articulation DEPTH bytes.
#       +0x10E (0x041476), +0x110 (0x041478), +0x112 (0x04147A) three u16 mix-weight /
#              pitch-offset words, produced by Voice_Selector_ComputeMixWeights.
#       +0x114 (0x04147C) u32 tick timestamp;  +0x118 (0x041480) flags, bit 7 = "restart
#              the portamento timestamp", bit 7 also set/cleared by Voice_NoteOn_Type2.
#
# (B) VOICE-SLOT RECORD -- 0x47 bytes (71). TWO arrays share this layout:
#       0x002942 + i*0x47   STAGING array, i = 0..3, one entry per layer of the note that
#                           is currently being built.
#       0x04308E + s*0x47   LIVE array, s = PHYSICAL TG SLOT 0..0x3F.
#     The note-on bodies fill the staging array, call NoteOn_Dispatch, and then copy
#     0x47 bytes (`ld bc,0x23 / ldirw / ldi` = 35 words + 1 byte) staging[i] -> live[slot].
#     That copy is at 0x02BBCB, 0x02BBFB, 0x02C08A, 0x02C3A0, 0x02C6AE. Fields:
#       +0x00 u8 = own slot number (written back after the copy);  +0x01 u16 flags/priority
#       (velocity<<6 | small code: |0x12, |0x08, set bit 2, set bit 4);  +0x03 u8 layer
#       index;  +0x04 u8 part index;  +0x05 u8 key | 0x80;  +0x06 u16 final pitch;
#       +0x08 u16 base pitch;  +0x0C u8 velocity;  +0x0D u16 pitch accumulator (portamento);
#       +0x13/+0x17/+0x1B/+0x1F u32 parameter-block pointers;  +0x23 u32 -> the PART RECORD;
#       +0x27 u32 -> the layer sub-block;  +0x2D/+0x2F/+0x31/+0x35/+0x36/+0x38/+0x3A
#       algorithm/effect words.
#
# (C) THE NOTE REQUEST RECORD -- the caller-supplied struct that every note-on body
#     receives in XWA. +0x00 u16 = key | part<<8 | 0x80; +0x02+i u8 = "layer i requested"
#     (0x80 | priority, or 0x00 = not requested); +0x06+i u8 = a second per-layer flag
#     (0x00 or 0x80); +0x0A+i u8 = THE SLOT NoteOn_Dispatch ASSIGNED, or >= 0x40 for
#     "none available". Every commit site tests `cp (rec+0x0A+i),0x40 / jr nc` and skips
#     silently on failure. That 0x40 is where the 64-voice polyphony limit lives.
#
# TONE-GENERATOR BUS PROTOCOL, as used by the two direct-access routines in this region
# (0x02B4A1, and the identical inline sequences at 0x02C762/0x02C866): clear bit 7 of SFR
# 0x18 (= PORT 6 on the TMP94C241), write the register number to 0x100000, `nop`, set bit 7
# of SFR 0x18, write the data word to 0x100002, then a 3-cycle `nop` pad reached via a
# `jr T` to the next instruction. Reads (DAC_Write_Sample, 0x022384) clear P6.7 and leave it
# low. So P6 bit 7 is the address/data phase line of the IC303 bus. MAME's
# src/mame/matsushita/kn5000.cpp does not model port 6 at all.

[ROUTINE] 0x02AD03 Voice_Selector_ComputeMixWeights  replaces=LABEL_02AD03  confidence=high
; Recomputes the three mix-weight / pitch-offset words of one part from that part's four
; articulation words.
; IN : A = part index (0..0x19).  OUT: none in registers.
; Writes part+0x10E, part+0x110, part+0x112 (0x041476/0x041478/0x04147A + part*0x11F).
; Body: forms XHL = part+0x102 (the articulation word array) and calls
; Voice_Selector_FindBestSlot with three output pointers into its own frame --
; XBC -> COUNT, XDE -> INDEX, pushed arg -> VALUE. FindBestSlot scatters the 3x3 nibbles of
; artic[0..2] into a 9-byte scratch buffer through the permutation table at
; 0x00F77D..0x00F785 (3 bytes per group), then returns INDEX = the first scratch entry >= 4
; (else the first non-zero entry), VALUE = that entry, COUNT = how many entries are >= 4.
; The three results are then table-mapped:
;   part+0x10E = u16 [0x00F786 + COUNT*2]            (10-entry table)
;   part+0x112 = u16 [0x00F79A + INDEX*2]            (9-entry table)
;   part+0x110 = u16[0x00F7D2 + COUNT*2]
;              + u16[0x00F7AC + INDEX*2]
;              + u16[0x00F7BE + VALUE*2]
; The four tables are exactly 10/9/9/10 entries and butt up against each other
; (0x00F786+0x14 = 0x00F79A, 0x00F79A+0x12 = 0x00F7AC, 0x00F7AC+0x12 = 0x00F7BE,
; 0x00F7BE+0x14 = 0x00F7D2), which is what pins COUNT to 0..9 and INDEX to 0..8.
; Touches no hardware. Only caller: Voice_InitFromSlot (0x02ADC1), i.e. it runs whenever an
; articulation parameter changes, never per note.

[ROUTINE] 0x02ADC1 Voice_InitFromSlot  replaces=LABEL_02ADC1  confidence=high

; Builds the final and base pitch words for one STAGING voice-slot record.

[ROUTINE] 0x02C5D8 Voice_NoteOn_Rhythm  replaces=LABEL_02C5D8  confidence=high
; Allocates and commits ONE physical voice for a single-layer part. Despite the name it is
; used for both the note-on and the note-off half of a key event -- see [UNCERTAIN].
; IN : XWA = a caller-owned note request record (both callers put it on their own stack),
; C = part index, E = key, one stacked byte = velocity. `retd 0x02`.

;   velocity != 0 : layer index 0, Voice_Allocate_1of4(mask 1, selector 3, velocity),
;                   requestrec+0x06 = 0x40, +0x03 = 0, +0x07 = 0.
;   velocity == 0 : layer index 1, velocity forced to 0x50,
;                   requestrec+0x02 = 0, +0x06 = 0,

; Both paths then zero requestrec+0x04/+0x05/+0x08/+0x09, call NoteOn_Dispatch, and commit

[LABEL] 0x02C653 Voice_NoteOn_Rhythm_BranchB  replaces=LABEL_02C653  confidence=high

[LABEL] 0x02C6C7 Voice_NoteOn_Rhythm_Exit  replaces=LABEL_02C6C7  confidence=high

[ROUTINE] 0x02C6CD VOICE_SETPITCH  confidence=high
; NAME LEFT AS-IS (the reference file's existing non-LABEL_ name). The LLVM build calls this

; The SECOND half of a real note-on, for parts whose tone record selects this path.

; Three guards, all of which return silently:

[UNCERTAIN] 0x02AE22 VoiceSlot_DataTable_02AE22 is a misnomer: the bytes at 0x02AE22 are CODE (`dec 2,xsp / ld (xsp),a / ... / ret`), not a table, and the address is reached by a real `call 0x02AE22` at 0x02EDE7. I adopted the build name so the reference file stops disagreeing with the ROM that is actually built, but the honest name is something like Voice_Artic_SetWord0_LowByte. Renaming it must be done in BOTH v142/subcpu/kn5000_subprogram_v142.s and archive/asl/subcpu/kn5000_subprogram_v142.asm; I did not touch either.

[UNCERTAIN] 0x02B4A1: the build calls this ToneGen_WriteNoteKey, the reference file calls it ToneGen_SilenceChannel. I believe the REFERENCE name is the better one and the build name is wrong: the routine's payload is `(0x100002) <- 0x7E00` with the latch set to the slot number, which the sub-CPU memory map documents as "FREE a voice", and its only caller frees slots whose active-voice bit just fell to 0. It does not write a key. Left alone per the rules; flagged because a wrong name here actively misleads anyone chasing the voice-allocation bug.

[UNCERTAIN] Five further build-vs-reference name collisions, all left alone: 0x02B4E3 (build Voice_Init_Type4 / ref Voice_Build_Register_Set), 0x02B717 (Voice_Setup_Typed / Voice_Build_Partial_Descriptor), 0x02BA2C (Voice_NoteOn_Type4 / Voice_Build_Four_Partials), 0x02C6CD (Voice_SetPitch / VOICE_SETPITCH), 0x02C7D7 (Voice_NoteOff / VOICE_NOTEOFF). For 0x02B717 and 0x02BA2C the reference names describe the code better than the build names do. For 0x02C6CD/0x02C7D7 the two agree in meaning and I confirmed both from the caller: Voice_NoteOn calls Voice_SetVelocity then Voice_SetPitch for a real note-on, and Voice_NoteOn_ZeroVelocity calls Voice_NoteOff.

[UNCERTAIN] 0x02C5D8 Voice_NoteOn_Rhythm: I could not justify "Rhythm". The routine is the shared allocate-and-commit helper for BOTH Voice_SetPitch (velocity != 0) and Voice_NoteOff (velocity == 0), and its two arms differ only in which layer index and capability mask they use. Nothing in it references the rhythm/style subsystem. A name like Voice_Request_CommitOneSlot would be defensible; I left the build name alone.

[UNCERTAIN] The "_Type1/_Type2/_Type3/_Type4" suffixes across this region are the build's invention and are NOT a tone-generator concept -- they distinguish how many layers the note-on stages (2, 4-via-Type3, 1, and 4-with-algorithms respectively). They are self-consistent, so I kept them, but a reader should not expect a "type" field in the data.

[UNCERTAIN] Part-record base. Region 4's notes state the per-voice software record is at 0x041300 + channel*0x11F. My measurement says 0x041368. Under a 0x041300 base the highest constant the firmware actually uses with `muls wa,0x11F`, 0x041486, sits at field offset +0x186, which is larger than the 0x11F stride and therefore impossible; under 0x041368 it sits at +0x11E, the last byte of the record. Three independent confirmations: the +0x6E layer array is exactly 4*0x25 bytes and ends at +0x102 where the articulation words begin; routines that receive a slot record dereference its +0x23 pointer at +0x0102..+0x0118, all inside 287 bytes; and 0x041368 is by far the most-used constant (90 sites) as one would expect of field 0. I did not edit region 4's file.

[UNCERTAIN] Voice_Slot_CalcArticParams walks a 0x51-stride array reached through the u32 at part+0x6E, i.e. it reinterprets the first four bytes of layer sub-block 0 as a pointer. That is consistent with the sub-block's +0x00 being a pointer everywhere else, but I could not prove what the 81-byte entries ARE. The 0x51 = 9*9 coincidence with Voice_KeyIndex_Pack3Nibbles is suggestive of a 9x9x9 lookup, not proven.

[UNCERTAIN] SFR 0x18 is P6 on the TMP94C241 (MAME src/devices/cpu/tlcs900/tmp94c241.cpp line 1633). I am confident bit 7 is a tone-generator bus phase/strobe line because every single IC303 access in the firmware brackets itself with it, but I have no schematic confirmation of what the pin drives.

[UNCERTAIN] Voice_Selector_FindBestSlot (0x02AC54, just outside this region) can return INDEX = 0xFF when all nine unpacked nibbles are zero -- it initialises both candidate registers to 0xFF and only overwrites them on a hit. Voice_Selector_ComputeMixWeights then uses that 0xFF as a word-table subscript. I could not determine whether the all-zero case is actually reachable at run time, so I have not called it a defect, but see the findings.
