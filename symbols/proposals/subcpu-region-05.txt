[ROUTINE] 0x025CCB VOICE_UPDATEPAN_FULL_OSCTABLEPATH  replaces=LABEL_025CCB  confidence=high
; Not a routine entry -- this is the main body of Voice_UpdatePan_Full, whose entry
; (0x025C87) sits just below this region's lower boundary. Documented here because the
; region starts inside it.
;
; Voice_UpdatePan_Full(XWA = voice-slot record) computes the THREE (level,rate) register
; pairs that the sub-CPU keeps for a voice in the tone-generator shadow block, for the
; "full" voice type -- the one whose tone record carries a per-oscillator trim table.
; Called from Voice_Release_Type4.
;
; This branch is taken when bit 11 of slot+1 is CLEAR. It reads a signed per-oscillator
; trim byte from tonerec[0x010C] (tonerec = the pointer at slot+35), adds it to
; paramA+39 (paramA = the pointer at slot+23), clamps the sum to 0..0x64 with
; ClampS16_WA_To_DEBC, and converts it through the 101-entry curve at 0x011899 into an
; 8-bit register level. The bit-11-set branch instead takes a fixed level from the byte
; at 0x0118B3 and jumps straight to _CheckMax.
;
; Level modulation then follows: if paramA+51 is non-zero the LFO/velocity scaler
; Pan_ScaleWithVelocity(paramA+48,+49,+50, depth paramA+51, velocity slot+8) is added,
; and if paramA+46 is non-zero PitchBend_Scale(depth paramA+46, note slot+12) is added
; too; each sum is re-clamped to 0..0xFF.
;
; Register value format written into the shadow block is (level << 8) | rate, where rate
; comes from the 0..0x7F curve at 0x011963. Bit 7 of the low byte is a separate "apply
; immediately" flag that only the per-tick writers (Voice_ComputeAndWriteVolume*) set.
;
; Hardware: nothing directly. The results land in RAM at 0x0451E4/E6/E8; they reach the
; tone generator later, when ToneGen_WriteVoiceParams pushes shadow offsets +24/+26/+28
; to TG register banks 0x800/0x840/0x880 via the 0x100000/0x100002 latch pair.

; Voice_ComputePitch(XWA = voice-slot record). Computes the voice's pitch word and
; stores it at slot+13; also clears the portamento offset at slot+51.
; Callers: Voice_Init_Type4, Voice_Release_Type4, Voice_Release_Type4_BranchA.
;
; Inputs: slot+12 = MIDI note (bit 7 is a flag, not part of the note -- if set, bit 11

;

; Touches no hardware; the result reaches the TG later via Voice_ApplyPortamento ->

[UNCERTAIN] On the evidence I read, the curated "LevelPair" family of names is the more accurate of the two. Voice_UpdatePan_Full/_Mono and Voice_ComputeAndWriteVolume1/2/3 all produce the SAME thing and target the SAME chip registers: a 16-bit word (attenuation<<8) | (bit7 = apply-now flag) | (bits 0..6 = rate), for three register pairs at TG banks 0x800/0x840, 0x900/0x940 and 0x9C0/0xA00. The paramA fields feed them in (level,rate) couples -- (39,40), (41,42), (43,44) -- which is an envelope-segment layout, and the portamento ramp treats 0xFF00 in those registers as the terminal "silent" value. Nothing in the code computes a left/right balance. I therefore believe "Pan" in Voice_UpdatePan_* / Voice_WritePan_Passthrough / Voice_InterpolatePanCurve is wrong, and that the routines are level/rate (envelope) writers. I have NOT renamed anything; if the project agrees, the rename should be made in the authoritative LLVM source first and this proposal file regenerated.

[UNCERTAIN] Voice_InterpolatePanCurve (0x026283) has no pan behaviour at all: its only caller adds its return value into the PITCH accumulator in Voice_ComputePitch_ApplyLFO. A name in the VOICE_PITCH_* or VOICE_VELCROSSFADE_* family would describe it better. Same for Voice_InterpolateNoteCurve, which is the key-position twin.

[UNCERTAIN] The tail labels of Voice_UpdatePan_Mono (0x0261BC, 0x0261E0, 0x026226, 0x026244) are named "Voice_UpdatePan_Full2_*" in the current build, but they are unambiguously part of Voice_UpdatePan_Mono (0x025F7F) -- Voice_UpdatePan_Full ends at 0x025F7E with its own ret. [UNCERTAIN] Voice_ComputePitch_InlineData (0x026522) is a misnomer: those 17 bytes are executable code (a clamp of WA into [DE..BC], returning HL) that nothing references. It is emitted as .byte only to preserve the byte-exact rebuild. A name such as VOICE_CLAMP_DEBC_UNREFERENCED would be honest, but again I have not renamed it.

[UNCERTAIN] Voice_LoadPitchTable_*, Voice_LoadFilterTable_* and Voice_LoadToneTable_* do not load tables. They scale a DSP algorithm parameter by a ramp position and broadcast the result to every voice of a part. Their behaviour is closer to VOICE_PARAMBCAST_*.

[UNCERTAIN] Voice_ToneTableRamp_Down indexes the 26-entry table at 0x010DB4 with (+100 >> 1), whose maximum is 0x4F/2 = 39, and with (+101 / 5), whose maximum is 0x96/5 = 30. Both exceed the table and read into the adjacent table at 0x010DCE. Voice_ToneTableRamp_Up uses /6 on the same +101 field, giving a maximum of exactly 25 -- in range. I could not determine whether the /5 is a deliberate second scale domain (Voice_ToneTableApply_Pitch and _Filter do convert +101 between a *5 and a *6 representation) or a firmware defect. It is a wrong-value read, not a crash.

[UNCERTAIN] I could not determine the physical meaning of the tone-generator register banks themselves (0x800/0x840/0x880/0x8C0/0x900/0x940/0x980/0x9C0/0xA00/0xA40) -- the mapping above is what the sub-CPU writes, not what IC303 does with it. [UNCERTAIN] Voice_AllocateForAny / Voice_AllocateForFull (both outside this region, both called from inside it) do not allocate.
