# region 14: 0x038CF9..0x03A932
# The operand-decoder library of the DSP parameter BYTE-CODE INTERPRETER: 27 leaf routines
# that each pull one field out of a packed parameter stream, run it through a fixed curve /
# interpolation / floating-point formula, and hand the resulting DSP coefficient back to the
# interpreter arm that called them.  Plus the four DSP_State_* routines that own the 0x91-word
# DSP configuration image and hand it to a background task.  No hardware is touched here except
# by DSP_TuneOffset_WriteSequence and DSP_BiquadWarp_FP, which emit through DSP_DispatchCommand
# / DSP_DispatchData / DSP_WriteOscParam.
#
# INTEGRATION NOTE -- READ FIRST, IT SAVES A WASTED PASS
#   The AUTHORITATIVE LLVM build already carries a real name for EVERY address in this range:
#   115 symbols, ZERO LABEL_ placeholders (verified with
#     llvm-nm -n rebuilt_ROMs/kn5000_subprogram_v142.llvm.elf
#   after `make llvm-all` + `python3 scripts/build/compare_roms.py` = 100.00% on all 14 ROMs).
#   symbols/subcpu_symbols_reference.txt is the file that LAGS: all 115 of its entries in this
#   range are still LABEL_xxxxxx.  Those need no thought -- copy the ELF name verbatim; the
#   `replaces=` field below gives the exact placeholder for each.
#   What this file CONTRIBUTES is (a) doc headers for the existing names, (b) exactly ONE
#   genuinely new label (0x038E10, the top of a task's forever-loop, which is a branch target
#   with no symbol in either source), and (c) the decoded opcode->decoder map and the decoded
#   curve formulas.  NOTHING in this file renames an existing non-LABEL_ symbol; the names I
#   believe are actively WRONG are listed, with evidence, under [UNCERTAIN].
#

# THE PARAMETER STREAM FORMAT (proved from DSP_StreamDecode_3ByteWord, 0x03CF07)
#   A "value" in the stream is THREE bytes b0,b1,b2 assembled as
#       v = (b0<<24) | (b1<<16) | (b2<<8)          (24-bit signed, left-justified in 32 bits)
#   and the routine returns the advanced cursor in XHL.  That is why every decoder here does
#   `sra 8,XWA` to get the 24-bit value back, and `sra 8 / and 0xFF` to get just b0.
#   Every decoder in this region takes XWA = address of the caller's stream CURSOR (a long in
#   the interpreter's frame), reads *cursor, consumes fields, and writes the advanced cursor
#   back through that same pointer before returning.  The scalar result is returned in XHL.
#
# SHIFT-COUNT-0 WARNING (this bit everything below)
#   On TLCS-900H a shift count field of 0 means SIXTEEN.  `sla 0x07,XBC` + `sla 0x00,XBC` is
#   therefore XBC<<23, not XBC<<7.  Confirmed three independent ways: (a) the alternate arms of
#   the same routine spell the same thing as `sla 0x0f` + a later `sla 0x08`; (b)
#   DSP_StreamDecode_3ByteWord uses `sla 8` + `sla 0` to build a <<24 field mask 0xFF000000;
#   (c) it is the only reading under which the piecewise curves below join up continuously.
#   The <<23 is a Q23 fixed-point scaling: 2^23 == 1.0 in the DSP's coefficient format.
#
# EXTERNAL TABLES THIS REGION READS (all in the program image, outside the region)
#   0x012397  27 x float32  ISO 1/3-octave centre frequencies, 40 Hz .. 16 kHz  (EQ freq LUT)
#   0x012403  32 x float32  0.1,0.2..1.0,1.5,2.0..4.0,5.0..20.0                 (EQ Q/BW LUT)
#   0x012483  100 x uint32  algorithm-type-0 coefficient table
#   0x012613  100 x uint32  algorithm-type-1 coefficient table
#   0x0127A3  128 x uint32  algorithm-type-2 coefficient table (also used by AlgoParam_Decode)
#   0x0129A3  100 x uint32  coefficient table for opcode 0x61
#   0x012B33  100 x uint32  coefficient table for opcode 0x62
#   0x012CC3..0x012F57      the float32 / float64 constant pool for every FP curve below.
#                           Recurring values: 44100 (the sample rate), 441000, 220500, 1000,
#                           99, 2, 8388608 (=2^23), 32768, 65536, 0.5, -12.
#   The 100-entry stride and the recurring /99 and /198 divisors say the user-facing parameter
#   range on this instrument is 0..99.
#
# NO HARDWARE IS TOUCHED except:
#   DSP_TuneOffset_WriteSequence -> DSP_DispatchCommand/DSP_DispatchData (0x036A2E/0x036A4F),
#   DSP_BiquadWarp_FP            -> DSP_WriteOscParam (0x0387E6) and
#                                   DSP_WriteCoeffData_5B_Direct (0x0388B3).
#   Both funnel into DSP_Send_Command / DSP_Send_Data, which select DSP1 (uPD6383 / IC311) when
#   the chip selector is 0 and DSP2 (MN19413 / IC310) when it is 1.  See [UNCERTAIN] for the
#   bug-relevant note about who can block.

; Decodes ONE parametric-EQ band descriptor.  NOT a byte-code arm -- it is reached only by the
; `calr` at 0x03A962 inside DSP_BiquadCoeff_Compute (0x03A933, opcode 0x70), which is the first
; routine of region 15.
; In:  WA (-> IZ) = word index into the caller's array
;      XBC = float* out: centre frequency
;      XDE = float* out: Q / bandwidth
;      stack args (retd 0x0010, four longs):
;        (XSP+0x38) = the parameter-stream cursor -- read, advanced by one byte, RETURNED in XHL
;        (XSP+0x3C) = base of a word array (the band's three fields live in it consecutively)
;        (XSP+0x40) = uint16* out: the filter TYPE (low nibble of the stream byte)
;        (XSP+0x44) = float* out: the gain-derived scalar
; The stream byte splits into two nibbles:
;   LOW nibble = filter type
;     0 : full band -- freq from the 27-entry Hz LUT at 0x012397, Q from the 32-entry LUT at
;         0x012403, gain from the third word
;     1 : Q is FORCED to the literal 0.1 (0x3DCCCCCD); only the frequency word is read
;     2 : Q is FORCED to the literal 2.0 (0x40000000); frequency and gain are read
;     other : nothing is computed, the three output pointers get whatever was on the stack
;   HIGH nibble = which field of the three-word group the index currently points at
;     0x00 : freq = arr[i],   Q = arr[i+1], gain = arr[i+2]
;     0x10 : freq = arr[i-1], Q = arr[i],   gain = arr[i+1]
;     0x20 : freq = arr[i-2], Q = arr[i-1], gain = arr[i]
;     (for type 2 the high nibble only distinguishes "gain at i+1" from "gain at i")
; The gain word is sign-extended, promoted to double, combined with 0.5 (0x012F07 etc.) and
; -12.0 (0x012F0F etc.) -- the same pair repeated for all five arms -- and normalised to a
; float.  The 27-entry LUT is the ISO 1/3-octave series 40 Hz..16 kHz and the 32-entry LUT runs
; 0.1..20.0, which is what makes "parametric EQ band" certain rather than inferred.

[LABEL] 0x03A6F5 DSP_FilterLUT_Mode0x10  replaces=LABEL_03A6F5  confidence=high
; Type 0, high nibble 0x10: freq = arr[i-1], Q = arr[i], gain = arr[i+1].

[UNCERTAIN] The floating-point helper names this region calls are, I believe, systematically
wrong, and that is why several routine headers above stop short of giving a formula.  The
evidence, all from call sites in this region: FP_SP_CallWithBuf8 (0x03DDCA) is called as
(XWA = dst buffer, XBC = pointer to an INT) and every consumer then treats the destination as a
float -- it is an int-to-float conversion, not a "call with buffer".  FP_DP_NegMantissaLS
(0x03DCF2) is called as (XBC = a 4-byte float, XWA = an 8-byte destination) and the destination
is subsequently pushed as a double -- it is a float-to-double promotion; its body does a
3-bit right shift of a 64-bit pair through the carry, which is mantissa alignment, not
negation.  FP_DP_NormalizeMantissa (0x03DD6C) is the inverse (double -> float).
VoiceFloat_CompareAndConvert (0x03D533) is invoked with a five-push sequence -- two doubles and
a result pointer, 20 bytes cleaned up by `lda XSP,XSP+0x14` -- and one of the two doubles is
always a literal base (2.0 in the volume/detune/reverb curves, 10.0 in DSP_BiquadWarp_FP).
That is pow(base, exponent).  It has nothing to do with voices.  Likewise
ToneGen_Compare_Voice (0x03D2AC) is used by DSP_ParamEQ_Curve_FP and by
VoiceFloat_CompareAndConvert itself as a floating-point comparison primitive.  All of these are
outside my range; I am recording the evidence rather than touching them.
