The Technics SX-KN5000 effects processor

A strategic review of an autonomous reverse-engineering effort

Independent multi-agent review · 31 July 2026 · Prepared for Felipe Correa da Silva Sanches

What this document is. An independent assessment of a long-running attempt to reverse-engineer and emulate an undocumented digital signal processor. It answers four questions: how fast the work is actually progressing, whether the effort is stagnating or approaching a breakthrough, whether complete decoding of the chip is realistically achievable, and what other approaches could unlock progress.

It assumes no prior knowledge of the project, the hardware, or the techniques involved. Sections 1 and 2 provide the necessary background; readers already familiar with the work can begin at section 3.

1. Background: what is being reverse-engineered, and why

1.1 The instrument

The Technics SX-KN5000 is a professional arranger keyboard manufactured by Matsushita (Panasonic) in the mid-1990s. Like most instruments of its class it is a small computer: a main processor running firmware from ROM, a tone generator that synthesises the notes, and a dedicated effects processor that adds reverb, chorus, delay, equalisation and similar treatments to the sound before it reaches the outputs.

The goal of the wider project is to preserve these instruments in MAME, an open source emulator whose purpose is to document computing hardware by reimplementing it precisely enough that original software runs unmodified. Preservation here means something stricter than "sounds about right": the emulated machine should behave as the original does, for reasons that can be demonstrated rather than asserted.

1.2 The chip at the centre of this review

The effects processor is IC311, an NEC uPD6383GF. It is undocumented. No datasheet for it is publicly available, no programming manual survives, and its instruction set has never been published. Everything known about it has been inferred from three sources:

  • the firmware ROM of the KN5000, which contains roughly one hundred effect programs that the main processor uploads into the chip at runtime;
  • the service manual and a pin-compatible appearance of the same part in an unrelated product, which together establish the pinout;
  • the behaviour of the emulator itself when a candidate interpretation is implemented and measured.

The chip executes a small program every audio frame. Each instruction is a 36-bit word divided into fields:

  hi12[35:24]  .  class4[23:20]  .  addr8[19:12]  .  lo12[11:0]

  within lo12:   SRC = bits[10:6]      (where the operand comes from)
                 ACT = bits[4:0]       (what the instruction does)
  within hi12:   bit 4  = store        bit 10 = end-of-program
                 bit 11 = format escape
                 f98 = bits[9:8]       f31 = bits[3:1]     (meaning unknown)

"Decoding the DSP" means establishing what each field value means — which operand source each SRC code selects, what arithmetic each ACT code performs, how memory is addressed, and how the results reach the audio outputs. The instruction stream is known exactly; its semantics are not.

1.3 What "correct" would look like

The chip's programs implement named studio effects — CONCERT REVERB 1, CHORUS, MULTI TAP DELAY and so on. A correct decoding would cause the emulated chip, fed the same audio and the same parameters, to produce the same output as the physical instrument. At present it produces silence: the two registers that present audio to the outputs read exactly zero on every frame measured.

2. How the work is organised

2.1 The autonomous loop

The work is carried out by an autonomous agent system on a recurring schedule — a "tick" every fifteen minutes. Each tick, the system reads its own handover notes, decides what to do next, dispatches work, records results, and updates its documentation. A single emulator run takes about ten minutes, which shapes the cadence.

Work is divided into two kinds of lane:

The build lane (one at a time)
The only agent permitted to modify the emulator source, recompile, or run the emulator. Serialised deliberately: two agents editing the same device would corrupt each other's measurements.
Read-only passes (several in parallel)
Agents that may read anything — the instruction corpus, archived emulator logs, the notes, the source — but change nothing. These have repeatedly found errors the main line missed, including defects in the project's own measuring instruments.

2.2 The evidence discipline

Every claim carries a grade, and these grades appear throughout this report:

MEASURED observed directly in a run or in the instruction corpus   FORCED follows necessarily from something already established   INFERRED a reasonable reading, not compelled   SPECULATIVE a pattern noted for later testing

Alongside the grades, the project operates a set of numbered standing rules, each adopted after a specific mistake. Several are referenced later in this report; the most consequential are:

  • Pre-register predictions and falsifiers before running an experiment, and compute the expected null result first. A criterion that cannot fail is not a test.
  • Run a control whose answer is already known. If the control fails, the instrument is wrong and the experiment decides nothing.
  • Compare minimum against maximum before reporting any output. A constant appears as "output" in every summary statistic. Two claims that the chip had begun producing audio were published and retracted on this basis; one was a direct-current offset.
  • A census printing a clean zero is indistinguishable from a correct negative. Any new detector must first be validated against a case whose answer is known.

2.3 The public record

The work is documented continuously in three places: a numbered technical register of roughly 225 sections (in which later sections retract earlier ones in place), a set of handover and index documents designed so that work can resume after any interruption, and a public blog series which has reached part 117.
