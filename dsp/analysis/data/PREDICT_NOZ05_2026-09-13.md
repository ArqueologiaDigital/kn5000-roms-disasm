# PRE-REGISTERED: does breaking the cell-0x05 write loop un-rail the pickup?  (§71)

Written and committed **BEFORE the run**, per the project's own rule.

## The mechanism this tests
§70 localised the rail to `iw45`'s clamped bit-4 store. ★ That was the PERPETUATION, not the
origin: at `iw8` — the *first* word of the frame that touches cell `0x05` — NO OPERATION already
reads `0x800000` and the FLANGER reads `0x2C7018 = 2 912 280`, a real sample. So the rail is
**present before the frame starts**, left by the previous one.

⇒ **IT IS A LATCH-UP, not a steady-state scale error:**

```
   cell 0x05 holds the rail
        -> iw8 reads it as -8 388 608
        -> the kernel's arithmetic runs to full scale with the wrong sign
        -> iw45's bit-4 store clamps it back into cell 0x05
        -> next frame, iw8 reads the rail again           (self-sustaining)
```

The FLANGER never enters the loop because its `0x05` carries a real sample; `PSHIFT=2` keeps
NO OPERATION out of it because halving the datum keeps the loop below the sign boundary.

## The arm
`UPD6383_NOZ05=1` — the device's OWN default-off diagnostic: *"EVERY kernel-A site-2 store to
cell 0x05 is suppressed -- which is EIGHT words, not three, iw9 among them"*. If cell `0x05` is the
INPUT DEPOSIT and the kernel-A stores to it are a decode error, suppressing them **breaks the loop**
and the deposited sample survives to `iw8`.
