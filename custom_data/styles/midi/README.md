# The 240 factory accompaniment styles, as Standard MIDI Files

One `.mid` per style-directory record, generated by
`scripts/build/style_to_midi.py` from `original_ROMs/kn5000_custom_data.ic19`
and the Composer factory memory image inside `kn5000_table_data.rom`.

```
make style-midi          # regenerate all 240
make verify-style-midi   # round-trip every event through the file it wrote
```

## ⚠ These are a VIEW, not the source

`custom_data/styles/*.styles` is what the ROM is built from and it round-trips
byte-exactly. MIDI cannot hold the cell allocation and link topology, the PAD
bytes after the `0x83` terminator, or which statuses were explicit rather than
running, so **the MIDI is not a build input** and no ROM target depends on it.
Deleting this directory cannot change a ROM byte.

## Naming

    <bank>_d<dir>_r<record>_<style name>.mid

`<dir>` is the directory's ordinal within the blob: `section_1_2`, `section_3_4`
and `section_5_6` each carry **two** 30-record directories, both numbering their
records 0..29, so bank+record alone is not unique.

Which chains belong to which record is established in
`scripts/analysis/style_directory_chains.py`: the five u16 fields at record
+0x00/+0x04/+0x06/+0x08/+0x0A are consecutive cell pointers, and across all 240
records they name **all 1,200 linked chains and none of the 818 unlinked template
blocks** -- a bijection.

## What the files contain

Format 1, **96 ticks per quarter note** -- the format's own resolution, from the
firmware's timing routine, not a choice made here. Track 0 is a conductor track;
tracks 1-5 are the record's five chains, one per MIDI channel 0-4.

| stream | MIDI |
|---|---|
| `0x90 NOTE`, `0x91 NOTE2` | note on/off; tick = beat*96 + pos, duration = dur_beats*96 + dur_ticks |
| `0xD1 CTL1` | control change 1 (modulation) |
| `0xD2 CTL2` | **pitch bend**, 14-bit = `(v << 7) \| (2v - 128 if v >= 64 else 0)` |
| `0xD3 CTL3` | control change 64 (damper pedal) |

The controller identities come from `SeqPerformance_EventDispatch` at ROM
0xFE89A8, whose selector bodies each end in `SndPart_SetParam` with a parameter
id; see `docs/accompaniment-style-format.md`.

**Nothing is discarded.** Every non-`BEAT` event is *also* written verbatim as a
sequencer-specific meta event `FF 7F <len> <status> <args>` at its tick, so the
file carries the whole event stream even where the meaning is unknown.
`make verify-style-midi` reads them back: **41,537 of 41,537** non-`BEAT` events
recovered, 0 files mismatched.

## What is deliberately NOT in them

* **Tempo.** A style has none -- the player supplies it. The files carry a
  nominal 120 BPM (`--bpm`).
* **Instruments.** The part is not in the stream; at runtime it comes from RAM
  0x7E52. No program change is emitted and no General MIDI instrument is claimed.
  The five channels exist only so the parts are separable by ear.
* **`NOTE2`'s two extra bytes.** The KN5000's own emitter can produce three
  distinct pairs and this corpus contains 57, so the styles were authored on
  equipment whose table is not in these ROMs. They ride in the verbatim meta
  event and are never rendered.
* **The slots' musical roles.** Five chains per style is consistent with a
  KN-series style's parts, but nothing here establishes the order, so the tracks
  are named `slot 0`..`slot 4`.

## A sanity check on the result

The corpus's pitch-class histogram over all 39,216 notes is
C 29.1%, D 11.9%, E 14.1%, G 16.1%, every other class below 7% -- strongly tonal
in C, which is what accompaniment patterns recorded in a reference key look like.
Three files (`section_5_6_d0_r19/21/23_clear.mid`) carry no notes: they are empty
factory slots, kept so the set is complete.

The per-status event census this produces agrees exactly with the independently
published one in `docs/accompaniment-style-format.md` once the Composer bank is
separated out (IC19: 26,633 NOTE, 7,538 NOTE2, 13,965 BEAT, 112 CTL1, 1,227 CTL2,
770 CTL3, 1,050 END).
