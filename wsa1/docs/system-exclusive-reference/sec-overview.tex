\chapter{Overview}

The Technics SX-WSA1R exchanges data over MIDI System Exclusive. This reference describes
the messages it sends and accepts: their byte layout, the bulk-dump transfer protocol, the
universal messages it honours, and what it reports when a transfer fails.

\section{Applicability}
This reference describes operating system version \textbf{2.0}. An earlier version~1
exists; its behaviour may differ and is not covered.

\section{Ports}
The instrument has two sets of MIDI sockets, MIDI~1 and MIDI~2. Ordinary performance data
is handled on both. \textbf{Bulk dump transfers use MIDI~1 only} --- a dump offered on
MIDI~2 is not received, and the instrument sends dumps only from MIDI~1.

\section{Relationship to the published manual}
Technics' own guide documents \textsc{sysex bulk dump} as a feature: which menu rows exist,
that the \textsc{send} button starts a transfer, that the MIDI~1 sockets must be used, and
three error numbers. It states no byte layouts, and the instrument shipped without a MIDI
implementation chart. This reference supplies what the guide leaves out, and follows it
wherever both describe the same thing --- with one exception, the meaning of
\textsc{error 42}, set out in chapter~\ref{ch:errors}.

\section{Verification}
The message layouts, the payload encoding and the checksum rule in this reference have been
checked against a bulk dump captured from a real instrument: 2\,883 messages carrying a
\textsc{sound} and \textsc{combination} transfer. Of these, 2\,876 carry a checksum, and
all 2\,876 verify under the rule given in chapter~3. Every transfer in the capture
delivered exactly the byte count its header declared.

The parameter placement in chapter~\ref{ch:params} has been checked against the same
capture. The \textsc{system, part \& midi} category was reassembled from it and each
parameter's own field read out of the result, for all 32 parts: 1\,833 fields, of which
1\,832 hold a value inside the range the instrument accepts for that parameter. Run
against a plausible but wrong placement --- one uniform stride for all 32 parts, instead of
the two runs chapter~\ref{ch:params} describes --- the same check puts 69 fields out of
range, so it is capable of rejecting a wrong map.

Two fields in that capture label themselves. Every part's MIDI channel holds its own part
number, so the 32 parts spell out an unbroken ramp from 0 to 31 --- which the wrong
placement interrupts at part~8, the first part past the gap. Every part's pan holds 64,
the value the instrument's own scale displays as \textsc{ctr}. Those two names in
chapter~\ref{ch:params} therefore rest on a real dump as well as on the instrument's
screen.

\section{Conventions}
Byte values are hexadecimal. A field written \bytes{\textit{nn}} takes one of the values
listed for it. Ellipses inside a message stand for a body whose length depends on the
message.

Every message begins with \bytes{F0} and ends with \bytes{F7}, as required by MIDI.

\begin{note}{Real-time messages are safe inside a transfer}
System Real Time bytes (\bytes{F8}--\bytes{FF}) may be interleaved anywhere inside a
System Exclusive message without disturbing it. Conversely, while the instrument is
receiving a System Exclusive message it ignores \bytes{F8} \textsc{timing clock},
\bytes{FA} \textsc{start}, \bytes{FB} \textsc{continue} and \bytes{FC} \textsc{stop} for
transport purposes.
\end{note}
