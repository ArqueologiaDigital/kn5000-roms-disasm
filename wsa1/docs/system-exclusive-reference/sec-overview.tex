\chapter{Overview}\label{ch:overview}

\begin{caution}{This is unofficial documentation}
Nothing here comes from Technics or Panasonic, and nothing here has been checked by them.
This document was written by inspecting a disassembly of the program ROMs, operating
system version~2, and by confronting what that showed with a bulk dump captured from a
real instrument. The same ROMs ship in both machines, so it describes the SX-WSA1 keyboard
as fully as the SX-WSA1R rack; chapter~\ref{ch:models} gives the two behavioural
differences between them.

Technics did publish a specification of its own, and where that specification covers the
same ground this document follows it and uses its terms --- section~\ref{sec:published} says what it is and
where it differs. Everything beyond it is inference from a disassembly, and inference can
be wrong. Treat a statement here as a report of what one machine was observed to do, not
as a guarantee about yours.
\end{caution}

The Technics SX-WSA1R exchanges data over MIDI System Exclusive. This reference describes
the messages it sends and accepts: their byte layout, the bulk-dump transfer protocol, the
universal messages it honours, and what it reports when a transfer fails.

\section{Applicability}
This reference describes operating system version \textbf{2.0}. An earlier version~1
exists; its behaviour may differ and is not covered.

\section{Ports}
The instrument has two sets of MIDI sockets, MIDI~1 and MIDI~2. Ordinary performance data
is handled on both. \textbf{Bulk dump transfers use MIDI~1 only} --- a dump offered on
MIDI~2 is not received, and the instrument sends dumps only from MIDI~1.

\section{Relationship to the published documentation}\label{sec:published}
Technics documented this instrument's System Exclusive implementation, in the
\emph{Reference Guide} that shipped alongside the two user manuals. Its pages~34--35 carry
a MIDI implementation chart headed \emph{Synthesizer} \textsc{[sx-wsa1]}
\emph{Synthesizer module} \textsc{[sx-wsa1r]}, and pages~41--56 give the message format,
the address map and the parameter tables. Where that guide and this reference describe the
same thing, the guide's terms are used here and its statements are followed.

This reference exists because the published specification describes the \emph{format} and
not the \emph{behaviour}. It does not say what raises each error number, that a dump can be
requested only while one screen is displayed, that the \textsc{exclusive} filter governs a
single message, that the rack refuses two functions silently, or that the instrument stops
announcing its own General MIDI changes once a controller has sent one. Those are the
subject of the chapters that follow, and they were established by decoding the program and
by checking a dump from a real machine.

\begin{note}{An earlier edition of this reference said no chart was published}
It said the instrument shipped without a MIDI implementation chart. That was wrong: the
chart and the full message format are in the \emph{Reference Guide}, which is a separate
volume from the user manual the claim had been checked against. The document now takes the
published specification as its starting point.
\end{note}

One statement of the published documentation is contradicted here: the meaning of
\textsc{error 42}, set out in chapter~\ref{ch:errors}.

\section{Verification}
The message layouts, the payload encoding and the checksum rule in this reference have been
checked against a bulk dump captured from a real instrument: 2\,883 messages. Despite its
name the capture is a three-category session --- \textsc{system, part \& midi},
\textsc{sound} and \textsc{combination} --- which matters, because the first of those is
the category chapter~\ref{ch:params} maps, so the parameter tables can be read against it
directly. Of these, 2\,876 carry a checksum, and
all 2\,876 verify under the rule given in chapter~\ref{ch:bulk}. Every transfer in the capture
delivered exactly the byte count its header declared.

The parameter placement in chapter~\ref{ch:params} has been checked against the same
capture. The \textsc{system, part \& midi} category was reassembled from it and each
parameter's own field read out of the result, for all 32 parts: 1\,833 fields, of which
1\,832 hold a value inside the range the instrument accepts for that parameter. Run
against a plausible but wrong placement --- one uniform stride for all 32 parts, instead of
the two runs chapter~\ref{ch:params} describes --- the same check puts 69 fields out of
range, so it is capable of rejecting a wrong map.

\begin{note}{What the capture covers, and what covers the rest}
Three of the four bulk-dump categories appear in it. \textsc{sequencer} does not, and
cannot: the capture came from a rack, which refuses that category
(chapter~\ref{ch:models}).

That category is confirmed a different way. The eight address-and-length pairs the
instrument accepts were decoded from the program, and Technics printed the same lengths
in its \emph{Reference Guide}. The two sets are identical, area by area, including all
three \textsc{sequencer} blocks and the guide's own word \emph{Variable} for the last of
them. The guide also prints \textsc{sequencer : wsa1 only} beside its request table ---
the same restriction the program gives the rack.

What a capture would still add for that one category is frame-level behaviour --- its
checksums, continuation and acknowledgements have been watched on the other three, and the
program runs all four through one path --- and the part of a song record that
section~\ref{sec:seqmemory} does not reach, which is now the 672 bytes outside its record
stream and the \textsc{performance} block.
\end{note}

Two fields in that capture label themselves. Every part's MIDI channel holds its own part
number, so the 32 parts spell out an unbroken ramp from 0 to 31 --- which the wrong
placement interrupts at part~8, the first part past the gap. Every part's pan holds 64,
the value the instrument's own scale displays as \textsc{ctr}. Those two names in
chapter~\ref{ch:params} therefore rest on a real dump as well as on the instrument's
screen.

\section{Conventions}
Byte values are hexadecimal. A field written \bytes{\textit{nn}} takes one of the values
listed for it. Ellipses inside a message stand for a body whose length depends on the
message.

Every message begins with \bytes{F0} and ends with \bytes{F7}, as required by MIDI.

\begin{note}{Real-time messages are safe inside a transfer}
System Real Time bytes (\bytes{F8}--\bytes{FF}) may be interleaved anywhere inside a
System Exclusive message without disturbing it. Conversely, while the instrument is
receiving a System Exclusive message it ignores \bytes{F8} \textsc{timing clock},
\bytes{FA} \textsc{start}, \bytes{FB} \textsc{continue} and \bytes{FC} \textsc{stop} for
transport purposes.
\end{note}
