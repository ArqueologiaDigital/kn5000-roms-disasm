; ==============================================================================
; 0xFC0000-0xFC2FFF -- the 0x0716 MESSAGE MODULE: an index-dispatched page of
; handlers, each of which stages a short message at RAM 0x0716 and posts it to
; CPU 2 over the 0x7C0000 link

;
; CHOSEN by notes/prom_a_call_graph.py --modules: T_F40FC8-T_F41060 (39 slots,

; T_F41070-T_F411A0 (77 slots) and T_F42470-T_F42524 (46 slots) -- so the span
; carries 165 of the directory's prom_a slots and 164 distinct targets, more
; than any other 12 KiB of the image.
;
; ITS BOUNDS ARE THE ROM'S, not a choice: 0xFBFFD4-0xFBFFFF is 44 bytes of 0x0E
; and 0xFC25EE-0xFC2FFF is 2578 more, while the longest run of 0x0E strictly

; notes/gen_prom_a_block.py emits `.fill`.  0xFC25ED is the last routine's own

; That is an ADDRESS-DERIVED name of the kind this tree already uses

; below is established byte by byte, but WHAT is being edited is not.  The four
; strings suggest a sound/combi name editor and that is exactly the sort of
; plausible guess this tree prefers a `sub_XXXXXX` over.  Every routine whose
; role is not established keeps its address label.
;
; WHAT IT DOES.  Three things interlock, and each is readable in the bytes:
;
;   1. AN INDEX DISPATCHER, twice.  0xFC0990 and 0xFC09AF are two byte-identical
;      31-byte routines (byte 32 differs, so 31 is maximal):
;
;          ld L,(0x20b8)      ; L := the index
;          cp L,A             ; A := the page's highest legal index
;          jr UGT, ret        ; out of range -> do nothing
;          and (0x070f),0xfd  ; clear bit 1 of the module's flag byte
;          ld XIX,0x00000716  ; XIX := the message staging buffer
;          xor H,H
;          sla 0x02,HL        ; HL := 4 * index
;          ld XWA,(XIY+HL)    ; XWA := handler[index]
;          call T,XWA
;
;      XIY is the page's handler table and A is its last legal index, both
;      loaded by the caller.  72 callers have that exact three-instruction
;      shape, which is exactly the 64 + 8 `calr` sites the two dispatchers have.
;

;      own `ld A,n` gives its table's length; the ten lengths are 14, 27, 7, 14,

;      0xFC09CE + 524 = 0xFC0BDA, which is the value of entry 0 -- the table
;      ends exactly where the first routine it points at begins.  No gap, no
;      overlap, no count taken by eye.  All 131 entries are instruction
;      boundaries of this module; 50 of them are distinct.
;
;   3. EVERY HANDLER POSTS TO CPU 2.  The handlers build a short byte message at
;      RAM 0x0716 and call one of two senders:
;
;        0xFC1A1E  ld XIX,0x716; push XIX, BC, 0x0000; T_F40ED4
;        0xFC1B09  push XIX (the CALLER's), BC, 0x0001; T_F40ED4
;

;      T_F40ED4 is prom_a 0xF8E02C, in the converted 0x7C0000 link
;      block-transfer layer.  That routine takes (stream, length, pointer),
;      chops the buffer into 0x20-byte packets and writes one header byte
;      `(stream << 5) | (n - 1)` to the link port -- `sll c,0x05` at 0xF8E0A7,
;      `ld XBC,0x007c0000` at 0xF8E0AF, `ld (XBC),A` at 0xF8E0B7.  So the two
;      senders differ only in which of the eight link streams they use.
;      0xFC1A1A is a `calr`-and-return trampoline onto the first; it is what the
;      module actually calls, 30 times, against 1 direct call on the callee.
;

;
;   0x0716..     the staged message.  Byte 0 is an opcode.  Nine distinct values
;                are written as `ld (XIX),imm` -- 0x00, 0x80, 0x88, 0x90, 0xB0,
;                0xC0, 0xD0, 0xE0, 0xF0, every one a multiple of 8 -- and five

;                Msg0716_DefaultMessages.  The length passed to a sender is 1 to
;                5 bytes.
;   0x070E,0x070F  two flag bytes.  0x070E's bits 0-3 are set by four
;                nine-byte published entry points at 0xFC065A, 0xFC0663,
;                0xFC066C and 0xFC0675, each of which also sets bit 0 of 0x070F.
;   0x20B8       the index the dispatcher reads; 15 sites name it.
;   0x20B9       the value being edited; 17 sites name it.
;   0x207A       a mode byte, named at 3 sites, all three inside
;                Msg0716_BiasOpcodeByMode.
;   0x76A2 + 0x40*k   32 records of 0x40 bytes, named by the table at 0xFC1162.
;
; WHAT IS **NOT** ESTABLISHED, and is left as `sub_XXXXXX` on purpose:
;   * what any individual handler does.  The four strings in the module --
;     "Sound Name *****", "Combi Name *****", "Combi Group Name", "EXT Silent
;     Group" -- are the only words it contains, and every one of them is used as
;     a FALLBACK, loaded only when a pointer compares equal to an all-ones
;     sentinel or a bit is clear.  They name the object, not the routine.
;   * what CPU 2 does with the messages.  Nothing on this side says.
;   * 0x00C00000, which the loader at 0xFC0076 passes to the link layer and adds
;     to two 16-bit offsets held at RAM 0x0874 and 0x087C.  prom_a and prom_b
;     contain ZERO instructions that dereference 0x00C00000 in any of the twelve

;     board (notes/FINDINGS-memory-map.md row F5 and the CPU-2 table).  That the

;
; ⚠ FIVE PUBLISHED DIRECTORY SLOTS IN THIS SPAN CANNOT BE ENTRY POINTS.
; T_F41184, T_F4118C, T_F41190, T_F41194 and T_F41198 are well-formed

; bound of ZERO, and each is published by exactly one slot.

; Converted 2026-08-25 by notes/gen_prom_a_screens.py.  11,044 substantive bytes
; and a 5,526-byte 0x0E pad; it closes the LAST large `.incbin` in the upper half
; of prom_a.
;
; ★ WHY THIS SPAN COULD BE FRAMED AT ALL.  Almost every routine here is the same
;   four instructions:
;
;       ld (0x2540),<layer>          ; which display layer
;       ld XIY,<list start>
;       ld XIX,<list end>
;       call 0xF417F0                ; DisplayList_Run  (or 0xF417F4, the
;       ret                          ;                   second interpreter)
;       <the display list itself, inline, immediately after the `ret`>
;
;   so code and data alternate every few bytes and a linear decode is worthless.
;   But the call site names BOTH ENDS of every list in immediates, and a display
;   list is self-checking: each record is `+0 opcode, +1 LENGTH OF THE WHOLE
;   RECORD` and the interpreter advances by that byte
;   (notes/FINDINGS-ui-display-list.md).  So the split is read off the ROM:
;
;     TEST 1  walking the length bytes from <start> must land EXACTLY on <end>.
;             It does for 56 of 56 spans.  (prom_b's 244 spans came in at 243.)
;     TEST 2  with those 56 spans and the 13 tables below removed, a linear
;             disassembly of everything that is left produces ZERO undecodable
;             bytes.  Guess one table boundary wrong and the decode
;             desynchronises and prints `db`, so this test can fail.
;
;   Both are re-run by `python3 notes/gen_prom_a_screens.py --check`, which
;   REFUSES to emit the region if either fails.
;
; ★ WHAT THE SCREENS ARE.  The text is in the lists, so this module is where a
;   large part of the machine's UI vocabulary lives: SEQUENCER / REALTIME /
;   EDIT, MASTER / REC0RD (sic, with a zero) / TRACK / ASSIGN, STEP, MEDLEY,
;   S0NG (also with a zero) / SELECT, AFTER T0UCH, NOTE EDIT, DRUM EDIT,
;   KIT:, and two help panels that read "Press up/down button under screen
;   corresponding track that want edit."  The five biggest lists --
;   0xFF0E2B, 0xFF0F11, 0xFF10E0, 0xFF1332 and 0xFF158A, 230 to 600 bytes each
;   -- are whole screens; the 51 small ones are single boxes and rules.
;
; ★ TWENTY-TWO `bit 0,(0x601F70)` tests sit in this module -- the byte pattern
;   F2 70 1F 60 C8, counted over the span -- and most of them pick a different
;   display list either way; ScreenDrawPtrs_FEF9FA / ScreenDrawPtrs_FEFA2A are
;   two whole pointer tables selected by the same bit.  Whatever that bit is, it
;   switches the machine between two screen layouts.  It is NOT established
;   here what it means.
;
; ⚠ WHAT IS NOT ESTABLISHED.  Which screen each list belongs to; what
;   (0x601F00), (0x601F3A), (0x601F53), (0x601F70) and (0x601F75) are; and what
;   Data_FF17E2 is.  Every routine is `sub_XXXXXX` except the three that the
;   kit-category legend pins.
;
; ⚠ 5 bytes of the 3,956 code bytes are emitted as `.byte` with unidasm's text
;   in a trailing comment: 0xFF0162, 0xFF016E, 0xFF017B, 0xFF0181 and 0xFF01F5.
;   They decode but this toolchain cannot spell them back
;   (notes/llvm-mc-tlcs900-spellings.md).  They are instructions, not data.

@@NAME 0xFF03E9 KitCategoryLegend_SelectBase
; ---------------------------------------------------------------------
; KitCategoryLegend_SelectBase -- XIY := the legend table for the selected part
; Called from: 0xFF03DE (`calr`), inside the routine that then issues SWI7
;          service 0x17 with BC = 6.
; Inputs:  (0x601F00), the selected part; the byte table at RAM 0x00603422;
;          RecordPtrs_RAM76A2 (0xFEB330) and the 64-byte records it points at.
; Outputs: XIY = one of five bases -- 0xFF0485 (type 0x20, the GM drum-kit
;          legends), 0xFF079D (0x28, "user1 "), 0xFF07AB (0x29, "user2 "),
;          0xFF07B9 (0x30, "ext   "), or 0xFF047F (six spaces) for anything
;          else.  A, WA, XIX, XIY clobbered.
; Evidence: `ld XIX,0x00603422 / ld A,(0x601F00) / ld A,(XIX+A) /
;          ld XIY,0x00FEB330 / sll 2,WA / ld XIX,(XIY+A) / ld A,(XIX+0x01)`
;          then the five-way compare.  ★ That is the SAME five-way switch on
;          the SAME +0x01 type byte that 0xFEB2E3 uses to pick a drum-NAME
;          block, so the legend table and the name table are indexed by one
;          object.
; Unknown:  what types 0x28/0x29/0x30 mean beyond their own legends.
; ---------------------------------------------------------------------

@@NAME 0xFF043C KitCategoryLegend_Index
; ---------------------------------------------------------------------
; KitCategoryLegend_Index -- HL := the index into that legend table
; Called from: 0xFF03CE (`calr`), immediately before the coordinates are set.
; Inputs:  the same chain as KitCategoryLegend_SelectBase.
; Outputs: HL = the record's +0x00 byte when the type is 0x20, and 0 for types
;          0x28, 0x29, 0x30 and for anything else -- which is why those three
;          bases each need only their own single 6-character entry.
; Evidence: `ld A,(XIX+0x00) / xor HL,HL / ld L,A / ret` on the 0x20 arm,
;          `xor HL,HL / ret` on the others.
; Unknown:  nothing here.
; ---------------------------------------------------------------------

@@NAME 0xFF03C2 Screen_DrawKitCategoryLegend
; ---------------------------------------------------------------------
; Screen_DrawKitCategoryLegend -- draw the 6-character kit legend at x=0xD5
; Called from: 0xFF03BE (`calr`), the tail of the routine at 0xFF03B3.
; Inputs:  bit 0 of (0x601F70) -- if it is CLEAR the routine draws nothing.
; Outputs: six characters on the display, and SWI7 service 0x17 called with
;          (0x2530) = 0x00D5, (0x2532) = 0x0006, XIY = the base, HL = the
;          index, BC = 6.
; Evidence: the literal coordinate stores at 0xFF03D1 and 0xFF03D7, the two
;          `calr`s to KitCategoryLegend_Index and _SelectBase, and
;          `ld BC,0x0006 / ld A,0x17 / swi 7` at 0xFF03E2-0xFF03E7.
;          ★ BC is the entry WIDTH: it is the same register the whole module
;          uses for it, 1 for Digits_FEF999 and 6 here.
; Unknown:  which screen this is drawn on.
; ---------------------------------------------------------------------
