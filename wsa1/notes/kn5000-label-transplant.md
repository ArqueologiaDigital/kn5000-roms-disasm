# KN5000 sub-CPU labels that transplant onto WSA1 addresses

> **See also** `notes/FINDINGS-kn5000-transplant-offset.md` — an independent
> re-derivation of the same 0xEB00 error from prom_a's side (it was hit while
> converting `0xFE692E`), plus the corrected **105-proposal** table and
> `prom_a/kn5000_run_offsets.py`, which re-proves the mapping and exits non-zero
> if it ever stops holding.

> ## ⚠ RETRACTION — every row of the original table was wrong
>
> This file previously listed 8 label proposals generated by
> `scripts/analysis/transplant_kn5000_labels.py`. **All 8 named the wrong object**, because
> the script converts a payload FILE OFFSET to a KN5000 link address with
>
> ```
> addr = 0x400 + offset          # WRONG
> ```
>
> The sibling's ROM file is not a contiguous image of its link map. Its Makefile
> (`../kn5000-roms-disasm/Makefile:635-641`) builds the ROM as `full[0:256] + full[60416:]`,
> where `full[]` starts at address `0x0400` — so the file has a **60,160-byte hole** in it and
> the mapping is
>
> ```
> offset  < 0x100 :  addr = 0x0400 + offset
> offset >= 0x100 :  addr = 0xEF00 + offset      # everything of interest
> ```
>
> Everything after the first 256 bytes was therefore off by **0xEB00**.
>
> **Proof, from the bytes** (`python3 notes/prom_c_kn5000_xref.py --selftest`): payload offset
> `0x1A64` holds `00 00 01 00 02 00 04 00 08 00`, which is verbatim the start of
> `EGEnv_ValueCurve_Simple` (`../kn5000-roms-disasm/v142/subcpu/subcpu_data_tables.s:1360`), and
> the sibling's symbol table puts that label at `0x010964 = 0x1A64 + 0xEF00`. Under the old
> formula the same label would have to sit at payload offset `0x10564`, where the bytes are
> `B8 B7 B6 B5 …` — a different table entirely.
>
> `scripts/analysis/transplant_kn5000_labels.py` has **not** been edited (it belongs to another
> agent's lane); use `notes/prom_c_kn5000_xref.py` instead, which carries the corrected mapping
> and re-proves it on `--selftest`.

Two things to notice.

* The old names were not merely misplaced, they were **thematically plausible and wrong**, which
  is the dangerous kind. `EGEnv_ValueCurve_Simple` on an envelope curve in a synthesiser sounds
  right; the object at that address is actually the keybed **touch** input curve.
  The two prom_c rows land 0x26 bytes into tables that this project has now converted and
  named independently, from prom_c's own reference sites, as
  `ToneGen_Velocity_Input_Curve` (0xFCC61A) and `ToneGen_Velocity_Output_Curve` (0xFCC71A) —
  see `prom_c/wsa1_prom_c.s`.
* The corrected prom_a rows land in the compiler's **arithmetic runtime**
  (`Int_SignedDiv_NegResult`, `FP_UnsignedDiv_Overflow`). Shared library code is exactly what
  two firmwares from the same vendor and toolchain should have byte-identical, and it carries
  no instrument-specific meaning. Anyone working prom_a should re-derive these from the fixed
  mapping before using them.

## Prefer the verified route

`notes/gen_prom_c_tables.py --verify` establishes 36 byte-identical, correctly-addressed table
transplants in prom_c — not by trusting a formula, but by requiring three independent things to
agree: byte identity at the sibling's stated size, a table chain that closes with no gap or
overlap over 9,525 bytes, and 39 of 43 start addresses appearing as literal address operands in
prom_c's own code.
