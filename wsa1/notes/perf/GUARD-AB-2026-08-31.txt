    truncated decode.  With the guard it is not reachable at all.  This is the
    tool's own "paints data as code" failure, and it was in its output.

WHAT THIS MEANS
  The published figure ANY 1,670 is not the reachability of these images; it is
  the reachability of these images plus phantom edges from truncated window
  tails, minus real bytes those same tails mis-framed.  The corrected figure is
  1,702.

  ⚠ NOT LANDED, because the brief for this lane is that an optimisation must not
  change an answer, and this changes four modes.  It is a CORRECTNESS change and
  needs Felipe's decision and a re-recorded baseline, not a performance lane's.

  ⚠⚠ AND IT BLOCKS THE PERFORMANCE WORK.  While the tail is in, what _BOUND
  holds at an address depends on which window reached it first, so the tool's
  answers depend on WALK ORDER -- and persisting the decode index, pre-decoding
  an image, or changing WINDOW cannot be shown answer-identical.  The 83% of the
  run that is unidasm cannot be attacked until this is settled.
