EVERY BYTE THE WINDOW-TAIL GUARD MOVED, AND WHAT MOVED IT.

WHAT LANDED
  notes/reachability.py, _decode_window(): rows whose instruction could extend
  past the end of the 2 KiB buffer are dropped, because unidasm decoded them
  from TRUNCATED bytes.  MAXLEN = 7 is the longest TLCS-900 instruction measured
  in these images (one linear decode of prom_a: 274,588 instructions).

      if o + WINDOW < len(d):
          end = start + WINDOW
          rows = [r for r in rows if r[0] + MAXLEN <= end]

HOW THIS WAS MEASURED
  Two full cold walks, from the SAME FILE: the pre-guard tool is
  reachability.py with MAXLEN = 0, which keeps every row because every row of a
  window starts before that window's end.  One module attribute apart, so there
  is no second copy of the walk to drift.

  ★ AND THE EQUIVALENCE IS CHECKED, NOT ASSUMED.  The MAXLEN=0 side reproduces
  the committed pre-guard answers EXACTLY -- 361,931 / 242,549 / 216,419 reached,
  1,590 / 80 / 0 reachable-and-unconverted, and 53,872 / 17,111 / 13,207 windows
  decoded, which are the spawn counts the profiling lane measured.  Those answers
  are frozen in notes/perf/baseline-preguard-2026-08-31/ and --explain refuses to
  report if its pre side does not match them.

      python3 notes/perf/guard_accounting.py --side pre  --out DIR   # ~17 min
      python3 notes/perf/guard_accounting.py --side post --out DIR   # ~17 min
      python3 notes/perf/guard_accounting.py --explain DIR
      python3 notes/perf/guard_accounting.py --focus prom_a:0xFC3D54 --out DIR
      python3 notes/perf/guard_accounting.py --selftest

THE RESULT: 231 BYTES MOVED, IN 68 RUNS, AND EVERY ONE IS ATTRIBUTED
      63 runs  STREAM  a truncated row's LENGTH was wrong, so the walk resumed
                       inside a real instruction and framed a shifted stream
       3 runs  EDGE+   a truncated row hid a REAL branch target
       2 runs  EDGE-   a truncated row invented one
       0 runs  UNEXPLAINED
  The STRONG sets move too, image-wide (prom_a +1, prom_b +5, prom_c +3/-24) and
  all 33 of those bytes are STREAM.  None of them is inside an .incbin span, which
  is why the STRONG column of the work list does not move.

  ⚠ THE INSTRUMENT HAD TO BE REBUILT TWICE TO GET THIS.  A first pass matched
  moved runs to nearby truncated rows by PROXIMITY and left 17 runs unexplained;
  a second read the final boundary index and left 16, because `_BOUND[addr]` is
  LAST WRITE WINS -- a later window that decoded the same address from whole
  bytes had overwritten the very row the walk consumed.  The tail table, which
  records every row a window contributed from its last 6 bytes WITH the window it
  came from, is the only record of what the walk was handed; and the model has to
  stop where walk() stops, at FLOW_END, or it claims bytes the walk never marked.

------------------------------------------------------------------------------
1. THE 9,216-BYTE SPAN, AND THE FALSE EDGE THAT PUT IT ON THE WORK LIST
------------------------------------------------------------------------------
  prom_a 0xFC3000-0xFC5400 was on the work list because ONE byte in it,
  0xFC3D54, was reachable.  The whole chain, and every step is in the data:

    the real code at 0xFBCF4E is   9e 08 3f 1e 00   `cp (XIZ+0x08),0x001e`, 5 B
    the 2 KiB window at 0xFBC74F ENDS AT 0xFBCF4F -- one byte into it
    unidasm, given those truncated bytes, emitted   3 B `db`
    the walk stored that and resumed at 0xFBCF4E + 3 = 0xFBCF51,
        which is the FOURTH BYTE of the real instruction
    decoding from 0xFBCF51 gives   1e 00 6e   `calr 0xfc3d54`
    the walk queued 0xFC3D54, walked it, and marked one byte:
        the ROM there is 0e 0e 0e 0e ... and 0e decodes as `ret`

  So a 9,216-byte span sat on the coverage work list because a truncated decode
  invented a call to it, and the byte it "reached" is one of a run of 0x0E
  filler.  With the guard, the row at 0xFBCF4E is dropped from that window, the
  next window decodes the instruction from whole bytes, the walk resumes at
  0xFBCF53, and 0xFBCF51 is never a decode start:

    guarded: consumed rows naming 0xFC3D54 -- NONE.  Named by a seed -- NO.
             0xFC3D54 is not in the guarded reached set.

------------------------------------------------------------------------------
2. THE ONE BYTE THAT ENTERS THE WORK LIST
------------------------------------------------------------------------------
  prom_a 0xF96259-0xF96418, 447 B, 1 reachable.  The row at 0xF969AD is a
  RELATIVE call whose displacement was read past the end of the window at
  0xF961AE (which ends at 0xF969AE):

      truncated   3 B `calr 0xf969b0`      <- a target 3 bytes ahead
      whole bytes 3 B `calr 0xf96315`      <- the target the machine calls

  The truncation did not invent an edge here, it HID one, and 0xF96315 was
  unreachable in the published figure for that reason.  The same shape gains
  16 bytes at 0xFA1AC7 (`jr F,0xfa1a68` truncated from `jr F,0xfa1ac7`) and 23
  bytes at prom_b 0xF5945E.

3. THE +32 IN 0xFA15CC-0xFA5400

  Two runs of 16 bytes, and nothing else in that span moves:
      +0xFA1A11-0xFA1A21  STREAM  window 0xFA120E ends at 0xFA1A0E; the row at

4. EVERYTHING ELSE
------------------------------------------------------------------------------
  The other 64 runs (197 bytes) are in ALREADY CONVERTED code, so they move the
  `reached` totals and no work-list row.  They are the same defect: a truncated
  row's length is wrong, the walk resumes off-boundary, and it either stops early
  at a spurious `swi`/`ret` (losing real bytes) or frames bytes the machine never
  executes (gaining phantom ones).  Both directions occur -- 205 bytes gained and
  26 lost -- which is why the corrected figure is not simply larger.
