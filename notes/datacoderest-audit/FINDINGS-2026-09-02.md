# DATA-AS-CODE audit results, the 7 unmeasured images (lane DATACODEREST, 2026-09-02)

Tool: `scripts/analysis/kn5000_rest_data_as_code_audit.py`. Reproduce with:

    python3 scripts/analysis/kn5000_rest_data_as_code_audit.py --build       # once
    python3 scripts/analysis/kn5000_rest_data_as_code_audit.py --verify      # byte-identity, all 7
    python3 scripts/analysis/kn5000_rest_data_as_code_audit.py --report
    python3 scripts/analysis/kn5000_rest_data_as_code_audit.py --null
    python3 scripts/analysis/kn5000_rest_data_as_code_audit.py --selftest

## The number that matters: the seed-coverage gap, per image

`reached_bytes / code_bytes` from `--null`'s own accounting. This is the
SAME caveat the v10 census reported (17.3% gap there) -- the fraction of
CODE-territory bytes this static method can prove reached by a real branch,
call, fallthrough, C-table reference or pointer-table entry. What is NOT
reached is not automatically debt: it also contains real code invoked
through indirect dispatch (`jp (reg)`-style jump tables) this method cannot
resolve, exactly the trap notes/DEBT-INVENTORY-2026-09-02.md warns against
for v10's raw "375,743 B unreached" figure.

| image | code bytes | reached bytes | reached % | gap |
|---|---:|---:|---:|---:|
| v9 | 1,024,122 | 264,580 | 25.8% | 74.2% |
| v7 | 644,740 | 278,231 | 43.2% | 56.8% |
| v142 (subcpu payload) | 125,290 | 60,370 | 48.2% | 51.8% |
| subcpu boot (IC30) | 3,618 | 3,517 | 97.2% | 2.8% |
| table_data | 18,711 | 15,770 | 84.3% | 15.7% |
| custom_data (IC19) | 0 | 0 | n/a -- no code at all | n/a |
| HD-AE5000 | 120,617 | 26,001 | 21.6% | 78.4% |

**v9, v7, v142 and HD-AE5000 all have a WORSE seed-coverage gap than v10's
17.3%.** ⚠ **Their LOW-confidence buckets and their raw "unreached_bytes"
totals must NOT be quoted as debt** -- v9's 751,005 B and v7's 364,734 B LOW
figures in particular are almost certainly dominated by real code reached
through computed/indirect dispatch, the same phenomenon that made v10's raw
number worthless. Two confirmed real instances of exactly this shape were
found and fixed as false positives during this audit (see below) before the
figures below were trusted; the residual LOW bucket should be assumed to
hold more of the same, unquantified.

**subcpu boot and table_data are the clean images here** (2.8% and 15.7%
gap, no HIGH or MEDIUM findings at all, LOW residue of 101 B and 2,941 B
respectively) -- same verdict shape as all four WSA1R images. **custom_data
has zero code entirely** (100% data, matching its role as flash
configuration storage) -- data-as-code is not a meaningful category for it.

## The signal false-positive rate (`--null`)

Byte-content signal (ASCII ratio / periodicity, gated on dominant-byte
ratio) measured over every REACHED (proven genuine) region -- how often it
fires on code known to be real:

    TOTAL  reached_regions=2710  false_positive_regions=28 (1.03%)
           reached_bytes=648,469  false_positive_bytes=1,939 (0.30%)

Matches v10's own calibration (0.3-2.3%). This licenses trusting a HIGH
finding's ascii/periodicity shape; it does NOT license trusting the
LOW/total-unreached figures, which is a seed-coverage problem, not a signal
problem -- the two are independent and both are reported here, unlike the
one-line "false-positive rate" a less careful report might quote.

## Two real false positives found and fixed before trusting any number

Both were HD-AE5000 findings that on inspection are genuine code reached
through indirect dispatch -- exactly the trap this audit exists to avoid
repeating:

1. **`.Lppe_jump_table`, 17,264 B** (`0x295642-0x2999B2`, entry point named
   `HDAE5000_Code_2_PartB` -- a name that says CODE). Reached only via
   `hdae5000_ui_display.s:15884`: `lda_24 xix, (0x2953ce)` / `add xix, xwa`
   / `ld xiy, (xix)` / `jp (xiy)` -- a genuine 5-entry indirect jump table.
   Fix: promote `.word`/`.long` POINTER-TABLE entries to full reachability
   seeds (not just an address-only signal), which is safe because the
   RECORD_TABLE calibration case (below) is a bare immediate load, not a
   pointer-table entry, and cannot be exonerated by this change (confirmed
   by `--selftest`).
2. **v9/v7's ~735,000-line clang-compiled ui_widgets C tables** (the same
   widget-descriptor/paramblock architecture v10 has). A function-pointer
   entry inside one of these compiles to a raw blob that `llvm-mc
   -show-encoding` renders as one giant `.ascii` literal -- invisible to a
   ROM-byte scan. Fix: ported `v10_data_as_code_census.py`'s own fix,
   scanning the raw `.c`/`.h` source text for identifier tokens matching
   known labels (1,871 matches found in v9 alone), scoped to v9/v7 (the
   only two of these seven images with C source at all).

Both fixes only moved the specific corroborated false positives; neither
could exonerate the RECORD_TABLE calibration case (re-checked by
`--selftest` after each fix).

## Confirmed findings (the two documented HD-AE5000 calibration cases)

Both still present, unconverted, as of 2026-09-02:

* **HDAE5000_RECORD_TABLE, 6,356 B** (`0x29C0AA-0x29D97E`), reported MEDIUM
  (referenced only as an address, `ld` immediate at `0x280045`, zero
  call/jump sites). This is the audit's own regression test
  (`--selftest` #3b): confirmed the exact documented size, confirmed
  unreached, confirmed not silently dropped.
* The 309 B version string calibration case is **already converted** to
  `.ascii` by a sibling lane (not a live finding any more); its exact bytes
  are used as this tool's `--selftest` planted-case text instead (#3).
* A handful of small HD-AE5000 MEDIUM findings (14 B, 6 B, 2x 2 B) are the
  same shape as RECORD_TABLE at a smaller scale, plus 3 tiny HIGH findings
  (35 B, 19 B, 18 B) -- one of which corresponds to the "smaller instance"
  in `HDAE5000_Lang_Codes` the debt inventory names but doesn't size
  (`hdae5000_data_tables.s:32860-32866`: `ei 16 / reti / .byte 0xa2, 0x05 /
  pushw bc / push sr / .byte ...` sitting inside an otherwise-`.asciz`
  table).

## v9 and v7: HIGH-confidence candidates, hand-corroborated

v9: 141 regions / 7,796 B HIGH. v7: 44 regions / 1,702 B HIGH. Both null
rates ~0.3% by bytes (see above). Spot-checked the four largest v9 HIGH
regions by finding the nearest preceding label (none of these regions have
their own label -- they sit inside a larger, mostly-real routine):

| region | preceded by (nearest label) | delta |
|---|---|---:|
| `0xFEFA6D-0xFEFC07` (410 B) | `SendPartDataBlock_Data` | +196 |
| `0xFD17AB-0xFD191E` (371 B, period=0.97/4) | `PanelEvt_Handler_4_DualValueCheck` | +196 |
| `0xF6B108-0xF6B1F5` (237 B) | `AccScreen_UIDataBlock` | +1841 |
| `0xF75B2B-0xF75BE9` (190 B) | `Data_InOutGridDispatch` | +77 |

Three of four sit inside or just after a label whose OWN name says `Data` --
consistent with these being genuine data spans mis-disassembled into
instruction mnemonics, the same shape as the calibration cases, not a
coincidence. Not converted by this lane (analysis-only); named here for a
conversion lane to pick up. Full per-region list is in `--report`'s output;
this file only reproduces the largest.

## What this lane does NOT claim

* The LOW-confidence bucket (752K v9 / 365K v7 / 88K hdae5000 / 64K v142) is
  explicitly NOT reported as debt -- the seed-coverage gap table above is
  the reason, not a hedge.
* v142 and hdae5000's MEDIUM findings (437 B and the RECORD_TABLE family,
  7,633 B total across both images after the two fixes) are named
  candidates needing the same per-region human corroboration the
  calibration cases themselves required (checking for a call/jump site,
  not just an address load) -- this audit does not convert anything.
* No claim is made about v10 or any WSA1R image; those already have their
  own dedicated, previously-run instruments.

## Does this lift the "every figure is a lower bound" caveat?

**Partially, and the honest answer is stated per image, not as one
headline:**

* **subcpu boot and table_data: YES.** Both now measured, both clean (no
  HIGH/MEDIUM, tiny LOW residue, high seed coverage). Their prior debt
  figures are no longer lower bounds for this category.
* **custom_data: YES, trivially** -- zero code, so no data-as-code category
  applies.
* **HD-AE5000: PARTIALLY.** Measured and largely converted to two
  corroborated calibration findings (6,356 B + small change) plus 72 B of
  small HIGH candidates -- but the 78.4% seed-coverage gap means its own
  debt total is still not a tight upper bound; more of the LOW bucket could
  be real debt, unquantified.
* **v9, v7, v142: NO, not yet.** All three are now MEASURED (a HIGH/MEDIUM
  candidate list exists, with a corroborated ~0.3% signal false-positive
  rate) but their seed-coverage gaps (74.2%, 56.8%, 51.8%) are wide enough
  that the caveat cannot be lifted for them -- it can only be narrowed from
  "nothing counts this" to "here is the specific, bounded, evidenced
  residue (HIGH+MEDIUM), and here is the size and likely cause (indirect
  dispatch) of what remains unmeasured." That narrowing is itself the
  measurement this lane was asked to make: the caveat is no longer "we have
  not looked," it is "we have looked, here is what we found, and here is
  the documented reason the rest resists this method."
