# SPEC — encoding selectors `:i3` / `:opc` / `:io` for the TLCS-900 backend

*Produced 2026-09-04 by a judged design panel: 4 independent designs × 4 adversarial lenses,
then one synthesis. This file is the decision of record; implement from it.*

**recommend_proceed:** True

## Chosen approach

BUILD design 2 ("encoding-selector-table") — but only its CORE MECHANISM: the encoding selector is a LITERAL TOKEN spliced into the short def's AsmString (`"cp", "$rs1, ${imm}:i3"`), so the short form's matchable carries one MORE asm operand than the long form's and a selector-free source line is structurally unable to reach it. Everything else is grafted or replaced.

Three substantive changes to design 2 as submitted:

(1) SELECTOR NAMES. `:s` is REJECTED (three of four reader lenses across the panel independently condemned it, and it is falsified in-tool: `ldb d,4`=24 04 and `lds8 d,4`=cc ac are BOTH two bytes, so "short" does not name anything). The vocabulary is three identifiers, each naming a mechanism visible in the bytes and each bound to exactly one encoder path:
      :i3   the operand value is packed into the opcode byte's low 3 bits (prefix+r, then 0xA8|n for LD / 0xD8|n for CP) — encoder PrefixSmallImm
      :opc  the operation has its own dedicated primary-map opcode with the register folded into it (0x20+r) — encoder SingleByteRegImm
      :io   the dedicated I/O-space store opcode (0x08 / 0x0A) — encoders LdIoImm / LdIoImm16
    Splitting design 2's single `:s` across `:opc` and `:io` is not cosmetic: SingleByteRegImm EMITS A FIXUP for a symbolic immediate, while LdIoImm SILENTLY PUSHES 0. One tag cannot carry both contracts. This directly answers the "a shared tag's guarantee set only weakens" finding raised against designs 2 and 3.

(2) THE GUARD IS MOVED INTO llvm-project AND REPLACED WITH LLVM'S OWN. Design 2's `assert_encoding_families_complete.py` is dropped from `gate-all`: it lives in the wrong repository (a backend author never runs the disassembly Makefile), it keys on spelling, and its predicate provably misses the likely case. I VERIFIED the miss myself: appending `def CP8_tiny : PrefixSmallImmInst<0xD8, (outs), (ins GR8:$rs1, i8imm:$imm), "cp", "$rs1, $imm", []>` leaves the shape key already-declared, so the checker passes. The replacement is LLVM's own ambiguity analysis, which I ran and which DOES catch it: `llvm-tblgen -gen-asm-matcher -debug-only=ambiguous_instrs` reports `warning: ambiguous matchables: CP8_tiny ... is incomparable with: CP8ri`. Baseline on the unmodified tree is 2 pairs (LINK / LINK32r, a pre-existing defect). The gate becomes "the ambiguity report must not grow past the recorded baseline", enforced by a lit test in llvm/test/.

(3) RANGE/CONSTANCY PREDICATES ARE ADDED ON TOP OF THE ARITY SEPARATION. Arity alone makes the ENCODING CHOICE safe; it does nothing about the three live silent miscompiles in the very defs being retargeted. Grafted from design 3.

I overrule no judge's verdict (no lens flagged a fatal flaw on any design), but I overrule three of their MEASUREMENTS, having re-run them: the site counts of ~47,305 quoted by judges on designs 3 and 4 are wrong — the brief's 71,667 reproduces EXACTLY (cps 19,261 / lds 18,564 / lds32 14,239 / ldb 16,138 / ldio 2,354 / ldwio 1,111; lds8 = 0); and design 4's "stib_d8 0 sites, stiw_d8 2 sites" is wrong (14 and 18).

## Why it won

It won on evidence I generated myself rather than on its own prose, and it is the only mechanism whose central claim I could execute rather than reason about.

THE MECHANISM IS VERIFIED, NOT ARGUED. I patched a scratch copy of the target, ran this tree's `llvm-tblgen -gen-asm-matcher`, and got:
    { 1153 /* cp */, TLCS900::CP8ri,     Convert__Reg1_0__Imm1_1, AMFBS_None, { MCK_GR8, MCK_Imm } },
    { 1153 /* cp */, TLCS900::CP8_small, Convert__Reg1_0__Imm1_1, AMFBS_None, { MCK_GR8, MCK_Imm, MCK__COLON_i3 } },
Two operands versus three. `cp xwa, 5` produces two actual operands and cannot reach a three-operand matchable — not "is deprioritised", cannot reach. Constraint 1 is therefore satisfied by ARITY, with no priority field, no `PreferSmallerInstructions` (default false, unset here), and no arbitration of any kind to mis-tune. Every competing design satisfies constraint 1 by NARROWING `isImm()`, which is a one-line global lever over all 1,182 defs whose inertness can only be argued.

THE PRINTER IS FREE, WHICH IS THE HALF EARLIER CONVERSIONS OMITTED. `-gen-asm-writer` on the same patched tree emits `O << ":i3";` and `O << ":opc";` with no PrintMethod, no C++, no decoder change. For 68,202 of the 71,667 sites (everything except ldio/ldwio) the round trip closes for zero lines of printer code, so re-disassembling a region stops reintroducing the names this work retires.

IT DOES NOT DEPEND ON THE BRIEF'S FALSE PREMISE. Three designs independently measured, and I reproduced, that `ld d, 4` has THREE legal encodings today — cc 03 04, cc ac (`lds8`), 24 04 (`ldb`) — and TWO OF THEM ARE THE SAME LENGTH. "Shortest that fits" is not fragile-in-future; it has no defined answer for this family TODAY. Constraint 2 is therefore not a precaution, and a design whose selector count per family is irrelevant to it is the correct shape.

INTRODUCTION IS PROVABLY INERT. `cp a, 4:i3` is a hard parse error at the pinned assembler ("unknown token in expression"), and the gated `.s`/`.inc`/`.asm` sources contain ZERO operand colons outside parentheses — the only 17 hits in the whole repo are in `archive/asl/`, an AS-macroassembler archive that is not in the LLVM build. No line that assembles today can change meaning.

CHEAPEST ON THE COST LENS. No new operand KIND, no `isImm()` change, no MCCodeEmitter change for the selector itself, no ISel exposure (all nine target defs carry `[]` patterns), and `daddr8` reuses `parseMemriOperand` verbatim the way `daddr16` already does.

## Final syntax

```
FEATURE A — :i3, the value packed into the opcode byte's low 3 bits. Every byte string below re-verified this session against toolchain-snapshot/llvm-mc.snap.
cp a, 4          -> c9 cf 04                UNCHANGED default (long form)
cp a, 4:i3       -> c9 dc                   (today: cps a, 4)
cp hl, 4:i3      -> db dc                   (today: cps hl, 4)
cp xwa, 5        -> e8 cf 05 00 00 00       UNCHANGED — v10/maincpu/file_io/single_load.s:361, still 6 bytes
cp xwa, 5:i3     -> e8 dd                   the short form must be ASKED FOR
ld hl, 0         -> db 03 00 00             UNCHANGED
ld hl, 0:i3      -> db a8                   (today: lds hl, 0)
ld xiz, 0        -> 46 00 00 00 00          UNCHANGED
ld xiz, 0:i3     -> ee a8                   (today: lds32 xiz, 0)
ld d, 4:i3       -> cc ac                   (today: lds8 d, 4 — 0 sites in tree, def exists)

FEATURE B — :opc, the operation's own dedicated primary-map opcode with the register folded in (0x20+r).
ld d, 4          -> cc 03 04                UNCHANGED default
ld d, 4:opc      -> 24 04                   (today: ldb d, 4)

FEATURE B — :io, the dedicated I/O-space store opcodes (0x08 / 0x0A). Address parenthesised with its width stated, per UPDATE 7; selector on the last operand, per the stated convention.
ld (0x07:8), 0xff        -> f0 07 00 ff        UNCHANGED default
ld (0x07:8), 0xff:io     -> 08 07 ff           (today: ldio 0x07, 0xff)
ldw (237:8), 0x8e00      -> f0 ed 02 00 8e     UNCHANGED default
ldw (237:8), 0x8e00:io   -> 0a ed 00 8e        (today: ldwio 237, 0x8e00)

THE THREE-ENCODING FAMILY, which exists TODAY and settles constraint 2 on evidence rather than principle: ld d, 4 / ld d, 4:i3 / ld d, 4:opc are cc 03 04 (3 bytes), cc ac (2 bytes), 24 04 (2 bytes). Three encodings, three spellings, and the two short ones TIE — so 'the shortest that fits' is not merely unsafe, it is not a function.

REJECTED BY CONSTRUCTION — each is a named error, never a byte, and never a silent fall-back to the long form:
cp a, 4:3        -> error: an encoding selector is an identifier such as ':i3'; a numeric ':N' is an ADDRESS WIDTH and is written inside the parentheses of a direct address, e.g. (0x2075:16)
cp a, 4:s        -> error: unknown encoding selector ':s'; expected :i3, :opc or :io
cp a, 4:zz       -> error: unknown encoding selector
cp a, 9:i3       -> error: 9 does not fit the 3-bit opcode field (must be 0..7) — NOT silently promoted to the long form, and NOT silently masked to 1 as `cps a, 9` does today
ld hl, SYM:i3    -> error: the 3-bit opcode field cannot hold a relocatable expression (today `cps a, SYMX` silently drops the symbol and emits c9 d8)
ld (0x07), 0xff:io  -> error: the I/O short form takes an 8-bit direct address, written (n:8) — an unsuffixed (n) keeps meaning the 24-bit default everywhere
ld (0x1ff:8), 0xff:io -> error: 0x1ff does not fit an 8-bit direct address (today `ldio 0x1ff, 0xff` silently emits 08 ff ff)
ld d, 4:opc:i3   -> error (one selector per operand)

NOT ADOPTED: an explicit long-form selector (`cp a, 4:l`). Two accepted spellings for one byte string breaks printer injectivity, and re-disassembly would drop the tag anyway. Consequence, stated: the ABSENCE of a selector is itself an encoding decision and no grep finds it; the untagged default rows are pinned in lit instead.
```

(during development, LLVM_MC points at the freshly built binary; the snapshot path is the pinned reference). WHAT A GREEN GATE PROVES HERE: that the assembler still turns the committed text into the same 13 ROM images. After step 9 it also proves that 71,667 rewritten source lines select the same encodings they selected before, which is a genuinely strong statement — those sites are dense and any mis-selection desynchronises an image immediately.

WHAT IT DOES NOT PROVE, and four of these are specific to this change:

1. AT STEP 4 IT CANNOT SEE THE FEATURE AT ALL. No source writes a selector yet, so green certifies non-regression and nothing else. A criterion that cannot fail is not a pass — which is why step 8's four foils must be run and must go red before any green is believed.

2. THE PRINTER AND DECODER ARE ENTIRELY OUTSIDE IT. gate-all is a statement about the assembler. The step-7 change to disassembler TEXT — `cps a, 4` becoming `cp a, 4:i3`, `stib_d8 7, 255` becoming `ld (7:8), 255` — moves no byte and the gate is structurally blind to it. Its instruments are llvm-lit's disasm-roundtrip.s and scripts/analysis/decode_encode_asymmetry_sweep.py, whose ASYM and LENGTH counts must not RISE (and should fall by the io rows). This is the half of the work earlier conversions were criticised for leaving open, and it is the half the project's own gate cannot certify.

3. THE RENAME-BLINDNESS QUESTION, ANSWERED SPECIFICALLY. For a pure mnemonic rename with no symbolic operand the byte gate is blind, and that DOES apply to part of this change — but not to the part people would guess. It does not apply to the nine def renames: each is accompanied by an AsmString change that adds a required literal token, so a converted site that lost its selector selects the long form and the image grows. It DOES apply, absolutely, to the tag-to-def BINDING in any family whose untagged default is exercised by no source line. Measured this session: `ldw (n:8), ...` occurs ZERO times in the tree, so swapping which member of the LDWIO family is the default would pass gate-all 13/13 while silently redefining `ldw (237:8), 0x8e00` from 5 bytes to 4; `ld (n:8), ...` occurs only 10 times, so that family is thin too. The ONLY instrument that sees this is the untagged-default byte-pin in llvm/test/MC/TLCS900/encoding-selector.s, which is why step 5 is not optional and why the pinned rows must include the defaults.

4. IT CANNOT SEE A FUTURE THIRD ENCODING BEING ADDED SILENTLY. That is the constraint-2 question, and the gate only answers it after conversion and only for spellings the ROMs happen to contain. The instrument is the ambiguity lit test from step 5, verified this session to catch exactly the case a spelling-keyed checker misses.

5. IT CANNOT SEE COMMENT LOSS. assert_comments_preserved.py must hold across every conversion commit.

BEYOND THE GATE, in order: llvm-lit over llvm/test/MC/TLCS900 and the new TableGen test (all green, including the negative tests, which only produce diagnostics rather than aborting once step 0 has landed); the per-site both-spellings equivalence probe with its deliberately-wrong-selector null, per family, before each conversion commit; oracle_ab.py re-run corpus-wide requiring this tree's ambiguous-text count to stay at 0, since the printer change adds new renderings and a collision would show up there; and decode_encode_asymmetry_sweep.py before and after, against its recorded baseline of 472 ASYM + 16 LENGTH out of 1,323,980.

## Grafted from the runners-up

* FROM DESIGN 3 (distinct-operand-kind) — RANGE- AND CONSTANCY-CHECKED PREDICATES ON THE SELECTED OPERAND. Arity separation makes the choice of encoding safe; it does nothing about the encoder. I reproduced all three live silent miscompiles: `cps a, 9` -> c9 d9 (9 masked to 1), `lds hl, 8` -> db a8 (8 masked to 0), `cps a, SYMX` -> c9 d8 (symbol silently DROPPED, no fixup). So the `:i3` immediate gets an operand class whose predicate requires an MCConstantExpr in 0..7 — no relocation can reach an opcode field, so a symbol there is never legitimate. Without this graft the feature ships a spelling that asserts a 3-bit field and then lies about it.

* FROM DESIGN 3 — THE PER-TAG ENCODER CONTRACT, which is why `:s` is split into `:opc` and `:io`. `:opc` (SingleByteRegImm) MUST NOT require a constant: its encoder emits a real fixup, and sites like `ld b, KERNEL_READY_LEVELS:opc` must keep working. `:io` (LdIoImm/LdIoImm16) MUST require a constant: its encoder pushes a literal 0 for a non-immediate with no fixup at all. I also reproduced the address-side hole: `ldio 0x1ff, 0xff` -> 08 ff ff, address 511 truncated to 0xff in silence, so `daddr8` needs a range check too.

* FROM DESIGNS 3 AND 4 — THE ldio/ldwio LEGACY InstAlias DOES WORK, and design 2 was wrong to say it could not. CodeGenInstAlias.cpp permits retyping between Operands of the same MVT, and `i32imm` -> `daddr8` is Operand<i32> -> Operand<i32>. So all six families stage identically and design 2's known_weakness #4 (the one place where 'the backend commit alone is gate-neutral' failed) is deleted outright.

* FROM DESIGNS 3 AND 4, AND FROM THE FUTURE-ENCODING LENS ON BOTH — BYTE-PIN THE UNTAGGED DEFAULT ROW OF EVERY FAMILY IN LIT, not just the tagged rows. This is the single highest-value graft in the packet and I confirmed WHY it is load-bearing by measurement: `ldw (n:8), ...` occurs ZERO times in the tree, so the LDWIO family's untagged default is exercised by no source line at all, and swapping which member of that family is the default would pass all three of design 2's declared defence levels AND pass gate-all 13/13 while silently redefining `ldw (237:8), 0x8e00` from 5 bytes to 4. The lit pin is the only instrument that sees it.

* FROM DESIGN 4 (printer-first-roundtrip) — THE DECODER RE-POINT FOR THE I/O FAMILIES' LONG HALVES. `f0 07 00 ff` currently prints `stib_d8 7, 255` and `f0 ed 02 00 8e` prints `stiw_d8 237, 0, 142`, the latter splitting a 16-bit immediate across two decimal operands. Re-pointing decodeD8 SubOp 0x00/0x02 at LD8mi_dst / LD16mi_dst_02 with the existing DirectAddrW8 sentinel closes the io family's round trip, and printMemOperand already renders the sentinel as `:8`. Scoped as its own optional, separately gated step.

* FROM DESIGN 1 (width-suffix-extended) — THE LAST-OPERAND CONVENTION, STATED AS A CONVENTION. `ldw (237:8), 0x8e00:io` carries two colons meaning two different kinds of thing; the rule is that the encoding selector rides the LAST operand, it is arbitrary, and it is written down rather than left to be inferred.

* FROM DESIGN 1 — THE DOWNSTREAM-TOOLING CLAUSE. The printer change is the only part of this work that alters observable behaviour, and it breaks every script that greps fresh disassembly for cps/lds/lds32/ldb/ldio/ldwio — including notes/syntax-convergence-probes/mnemonic_census.py, whose SYNTHETIC bucket is the project's headline metric. Those tools move in the SAME commit or the next census is wrong in a way that looks like progress.

* FROM DESIGN 1'S BYTE-SAFETY LENS — DO NOT TAKE THE (Xrr+256) SENTINEL BAIT. Design 1 offered `(xix+0:8)` as 'genuinely free on the parser side'; the lens disproved it: addMemriOperands DISCARDS Mem.AddrBytes whenever Mem.Base is set, so the d8-with-zero-displacement form has exactly one channel, the Disp==256 value sentinel. An implementer following that recipe gets a silent length-changing shortening across 1,132 committed sites. Explicitly out of scope, and recorded as a trap.

* FROM DESIGN 4'S IMPLEMENTATION-COST LENS — THE llvm_unreachable CRASH PATH, which I confirmed independently and which becomes step 0 of this spec. Setting `DiagnosticType` on a new AsmOperandClass generates `Match_<Name>` (I saw `Match_Imm3T` at line 51 of the generated matcher and `return TLCS900AsmParser::Match_Imm3T;` at line 777), and TLCS900AsmParser::matchAndEmitInstruction switches over exactly four cases with NO `default:` before falling into `llvm_unreachable("Unexpected match result")`. Every good diagnostic this spec wants is a debug-build abort and release UB until that arm exists. The target has ZERO DiagnosticString/DiagnosticType uses today, which is why nobody has hit it.

## Rejected designs and why

* DESIGN 1, width-suffix-extended (28) — REJECTED ON ITS CENTRAL CLAIM. Its whole case is that a NUMERIC descriptor `4:3` is a literal generalisation of the shipped `(0x2075:16)` idiom. It is not: the address idiom reads correctly because of bracketing parens and visual asymmetry (a long hex address, a familiar width), and stripping both leaves `cp a, 4:3` and `cp wa, 3:3` — single digits on both sides, on all 52,064 feature-A sites by construction, which in a hardware context reads as a BIT RANGE (this project itself writes `lo12[10:6]`). It then has to admit the angle 'carries A completely and carries B not one inch' and bolt on a second kind of descriptor anyway. Its own byte-safety lens also found two routes to a silent wrong byte in the specification as written: the (Xrr+256) sentinel recipe offered as 'genuinely free' actually sets a field nothing reads (addMemriOperands discards AddrBytes when Mem.Base is set), and its constraint-1 section claims `cp a, 9:3` errors 'structurally' when isImmW3 tests only the descriptor token and never the value. Its real contributions — per-def binding, the last-operand convention, the downstream-tooling clause, the sentinel warning — are all grafted.

* DESIGN 3, distinct-operand-kind (29, TOP SCORE) — REJECTED DESPITE WINNING THE POLL. Two reasons. First, its constraint-1 guarantee rests on narrowing `isImm()` at AsmParser:70, a one-line lever over all 1,182 defs whose inertness can only be argued from a corpus fact ('no existing line carries a tag') rather than demonstrated; its own byte-safety lens called it 'the largest lever in the patch' and noted 'the gate barely exercises it'. The arity mechanism needs no such lever and its separation is visible in the generated match table, which I read. Second, it pays for a distinct operand kind, three predicates, three add*Operands, a FieldDesc enum, four PrintMethods and a decoder retarget to obtain a printer round trip that the arity approach gets for free from -gen-asm-writer. Its scoring lead came largely from the quality of its measurements, not from its mechanism — and those measurements (the three-encoding refutation, the range/constancy predicates, the per-encoder-path contract, the untagged-default byte-pin) are precisely what has been grafted. Its `:s` spelling is rejected on the same grounds as design 2's.

* DESIGN 4, printer-first-roundtrip (26) — REJECTED, LOWEST SCORE AND THE ONLY 4 IN THE PACKET. It shares design 3's isImm() lever, and its reader-ergonomics lens scored it 4 with findings I regard as correct: `:3` is sold as a hardware fact ('the immediate occupies the opcode byte's low three bits') but the identical hardware fact stays permanently untagged on `inc 1, a` and `bit 1`, so the tag's real meaning is the much weaker 'this family also has a long form and I picked the other one'; and its `:s` is falsified in-tool by the two-byte tie. It also proposed `let DiagnosticType = ...` on new operand classes, which I confirmed generates a Match_<Name> return code that reaches a switch with no default arm and aborts — a crash on its own advertised negative tests. Two of its measurements are wrong (stib_d8 0 sites, stiw_d8 2 sites; actual 14 and 18). Its genuine contribution, the decodeD8 re-point that closes the io families' round trip and retires `stiw_d8`'s three-operand immediate split, is grafted as step 7.

* THE `:s` SPELLING, from designs 2, 3 and 4 — REJECTED OUTRIGHT AND BEFORE ANY CONVERSION COMMIT, because after 19,603 sites are written the wrong reading is unfixable. `s` reads as 'short'; that guess is CONFIRMED by the bytes at every one of its sites, so the reader is never corrected, yet it is false as a rule — `ld d, 4:i3` = cc ac and `ld d, 4:opc` = 24 04 are the same length. Replaced by `:opc` and `:io`, which name mechanisms and carry different operand-class contracts because their encoders have different capabilities.

* THE CROSS-REPO COMPLETENESS CHECKER (design 2's assert_encoding_families_complete.py in gate-all) — REJECTED AND REPLACED. It lives where the person adding a future encoding will never run it; it keys on spelling rather than on the def set, so a third def joining an ALREADY-DECLARED family passes it (I reproduced this: tblgen rc=0, empty stderr, the new def sorted ahead and would capture every site); and its shape key is contingent on an undisclosed operand-collapse choice that quadruples the exemption list if moved. Replaced by LLVM's own ambiguity analysis run as a lit test in llvm-project, which I confirmed catches exactly that case.

* AN 'ASSEMBLER PICKS THE SHORTEST THAT FITS' RULE, in any form — REJECTED ON EVIDENCE RATHER THAN PRINCIPLE. It would silently rewrite 2,953 measured long-form sites (2,627 `cp r,0..7` + 326 `ld r,0..7`), including single_load.s:361 `cp xwa, 5` from 6 bytes to 2. And it is not merely unsafe, it is UNDEFINED: `ld d, 4` has three legal encodings today and two of them are two bytes, so the rule would have to break the tie by def order — silently.

* THE MNEMONIC-SUFFIX ALTERNATIVE FOR FEATURE B (`ld.opc d, 4`) — NOT REJECTED ON CORRECTNESS, and this must be settled before step 9. Design 1 named it as 'the honest alternative', and the reader case is real: it puts the encoding fact in the column where this tree already puts encoding facts (cpw, incw, ldw), needs no last-operand convention, and reaches form selectors with no immediate at all (`push WA` = 28 vs d8 04, `ldir`, `pushw`/`popw`). It was declined for continuity with the shipped `(addr:16)` idiom, for keeping A and B as ONE parser change as the brief asked, and because a new mnemonic string counts SYNTHETIC in mnemonic_census.py. That last reason is metric-driven, not truth-driven, and it is recorded as such. It is also unverified that `ld.opc` lexes as a single identifier in this parser — AArch64's `b.eq` is handled by explicit mnemonic splitting, not by the lexer. Feature A is unaffected either way.

## Open risks — carry these, do not smooth them

* THE SELECTOR NAMES CANNOT BE CHANGED AFTER STEP 9 AND ARE THE ONE DECISION WITH NO TECHNICAL TIEBREAK. `:i3` is defensible (mechanism-naming, checkable against the bytes, not confusable with a width or a bit range). `:opc` and `:io` are names bound in a table; a reader cannot derive them from the text alone, and only 0.15% of the affected sites carry ROM bytes in a trailing comment against which to check a guess. If a reviewer prefers the mnemonic-suffix spelling for feature B, that must be decided BEFORE the first conversion commit, not after 19,603 sites are written.

* THE VOCABULARY IS NOT UNIFORM ACROSS SIZES AND CANNOT BE MADE SO, because constraint 1 pins the untagged default to whatever historically owned it. The dedicated-primary-opcode shape is `:opc` at 8 bits (0x20+r, LD8ri_short) but is the UNTAGGED DEFAULT at 32 bits (0x40+r, LD32ri). A reader who learns ':opc means the dedicated primary opcode' will read the untagged `ld xiz, 0` and conclude it is not one. Wrong. No naming scheme fixes this; the only mitigations are the family table listing untagged defaults as named members and a glossary shipped in the disassembly tree, not only in a .td comment in another repository.

* THE GATE IS STRUCTURALLY BLIND TO A DEFAULT-MEMBER SWAP IN THE LDWIO FAMILY, measured not hypothesised: `ldw (n:8), ...` occurs ZERO times in the tree, so re-designating which member of that family is the default would pass every TableGen assert and pass gate-all 13/13 while silently changing `ldw (237:8), 0x8e00` from 5 bytes to 4. `ld (n:8), ...` has only 10 sites. The lit byte-pin on untagged defaults is the sole guard, and it is a test written by the same hand that wrote the rule.

* THE ENTIRE PRINTER AND DECODER HALF IS UNGATED BY BYTES. The step-7 text change is invisible to gate-all by construction. Its instruments are lit and decode_encode_asymmetry_sweep.py — the latter is the project's own baseline (472 ASYM + 16 LENGTH out of 1,323,980) and is a corpus measurement, not a proof. A synthetic name that re-assembles to the same bytes is SYMMETRIC and therefore invisible to that sweep too, which means a future InstAlias added at the default EmitPriority 1 over any of these defs would silently revert the printer to a synthetic name with no gate, no sweep and no error catching it. Only the lit round-trip test does.

* THE TRANSITION WINDOW LEAVES AN UNTAGGED PATH INTO EVERY SHORT ENCODING. The nine EmitPriority-0 aliases render through the ALIAS's operand records, so they bypass the new range and constancy predicates; `cps a, 9` keeps silently emitting c9 d9 until step 10 deletes them. The obvious temptation is to keep them 'for compatibility' forever — the tree still carries `incm` a lane later — and if that happens, half of what this work is for is gone.

* THE STEP-6 EMITTER DIAGNOSTICS MAY TURN CURRENTLY-GREEN SOURCES RED, AND THAT IS UNMEASURED UNTIL RUN. The exposure probe says every committed small-immediate operand is a literal 0..7 or one of 85 macro `\Param` substitutions, and that macro arguments are substituted textually before the target parser runs — but that safety rests on AsmParser macro-expansion ORDER, an assumption about LLVM rather than about the ISA, and the tree's own `.if \regnum <= 7` guard is one-sided.

* NOTHING AT TABLEGEN LEVEL PREVENTS TWO DEFS WITH THE SAME MNEMONIC, SHAPE AND SELECTOR. The ambiguity analysis I am gating on is a WARNING under DEBUG_WITH_TYPE, so it requires an assertions build and a lit test that could be disabled or drift; a release tblgen prints nothing. It also already reports a baseline of 2 pairs (LINK / LINK32r), and `link xwa, 0x12345` is a real pre-existing defect that this work does not fix and must not be allowed to mask.

* THE ldio/ldwio CONVERSION IS A RESHAPE, NOT A RENAME, and it is where a lane historically loses work: 3,465 sites across ~180 latin-1 files gaining parentheses, a width suffix AND a selector, converted by a parser rather than a regex. It is also a net READABILITY LOSS at those sites — `ldio 0xd2, 0x29` names what the line does (a TMP94C241 internal-I/O write) and `ld (0xd2:8), 0x29:io` replaces that with two encoding annotations, one of which sits on the operand it says nothing about.

* COVERAGE STOPS AT 71,667 OF 147,842. Feature C (stb_erp/ldb_erp, 6,697 sites, needs a PrevGR8 register class), the 1,132 (Xrr+256) sentinel sites, the register-only form selectors (push WA = 28 vs d8 04, pushw/popw, ldir) and the ~2,371 refused class-3 sites get nothing from this. The selector rides an operand, so a form with no immediate has nowhere to hang one — that is a structural limit of the chosen mechanism, and it is the strongest argument the mnemonic-suffix alternative has. Before implementing, sweep the remaining ~66,000 synthetic sites for OTHER families that are form selectors this same slot could absorb: a second pass over the parser costs more than one wider first pass.

* THE MEASUREMENTS IN THIS SPEC EXIST ONLY IN SESSION SCRATCH UNTIL STEP 1 LANDS. Every number quoted here — the 71,667 split, the 2,953 constraint-1 sites, the 85 macro operands, the 0/10 gate-blindness counts, the 2-pair ambiguity baseline, the 14/18 stib_d8/stiw_d8 counts — came from commands run this session against llvm-mc.snap and this tree's llvm-tblgen, and none of it is committed. Until step 1 lands the probe scripts and the baseline file, none of it is checkable by anyone, including a later pass of this work.
