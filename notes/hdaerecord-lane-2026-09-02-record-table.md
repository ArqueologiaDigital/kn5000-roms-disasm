# HD-AE5000 lane HDAERECORD, 2026-09-02: the data-as-code record table

Lane HDAERECORD (`notes/lanes/BRIEF-2026-09-01.md`, third debt category per
`notes/DEBT-INVENTORY-2026-09-02.md`). Target: `HDAE5000_RECORD_TABLE` at
0x29C0AA, 6,356 B previously disassembled as ~6,150 lines of TLCS-900
instruction mnemonics, and the smaller `HDAE5000_Lang_Codes` instance of the
same defect.

## Why this is data, not code

* The only reference to 0x29C0AA anywhere in the tree
  (`hd-ae5000_v2_06i.s:312`, `lda_24 xwa, (0x29c0aa)`) LOADS THE ADDRESS for
  the "DISK MENU / UI" handler registration — see the Handler Registration
  Table above `HDAE5000_Handler_Registration`. There is no call or jump site
  targeting anything inside 0x29C0AA-0x29D97D anywhere in `hdae5000/*.s`.
* `hdae5000_init_data.s:23-28` already documented, from the RAM-image side,
  that this is 13 records x 24 bytes with fields at +0x00 (procedure pointer),
  +0x0C (class name), +0x10 (parameter type-signature string) and +0x14
  (parameter-name list). This lane confirmed that layout against the raw ROM
  bytes and extended it to account for the full 6,356-byte span.

## What the 6,356 B actually decomposes into

| range | size | content |
|---|---:|---|
| 0x29C0AA-0x29C1E1 | 312 B | the 13 x 24-byte record array |
| 0x29C1E2-0x29D8A9 | 5,832 B | reserved gap, every byte verified 0x00 |
| 0x29D8AA-0x29D97D | 212 B | packed pool of the 26 NUL-terminated strings the records point at (13 class names + 13 parameter type-signature strings, several empty) |

Record layout (24 B): `+0x00 .long ProcPtr`, `+0x04/+0x06/+0x08/+0x0A .short`
x4 (undecoded — one, +0x06, is a constant 0x0160 across all 13 records, an
[INFERENCE] match to the high half of PPI port 0x01600004 this table is
registered under, not traced further), `+0x0C .long NamePtr`, `+0x10 .long
SigPtr`, `+0x14 .long ParamListPtr` (RAM).

`HDAE5000_Lang_Codes` (0x2E5B80) held a smaller instance at 0x2E5BD2-0x2E5BDF:
14 bytes disassembled as `ei 16 / reti / pushw bc / push sr`, sandwiched
between two single-character `.asciz` strings above and the `.asciz "rb"` /
`"TESTTEST.TLX"` pair below — both of the latter ARE genuine `lda_24` targets
(`hdae5000_ui_display.s:3799-3800`). Retyped as a 14-byte `.byte` run; its
actual meaning is UNDECODED (left as an open question, not claimed).

## Evidence

* All 13 `ProcPtr` values land exactly on an already-named `*Proc` routine's
  address (e.g. record 7 -> `HDAE5000_TtlScreenR3Proc` at 0x280645,
  byte-identical).
* All 13 `SigPtr` string lengths match `hdae5000_init_data.s`'s own published
  parameter counts (11,2,0,0,1,0,0,0,0,0,0,6,3), no exception.
* The 5,832 B gap is 100% `0x00`; the 212 B pool decomposes into exactly the
  26 strings the record pointers reference, with zero leftover bytes and zero
  orphan pointers.
* No `call`/`jr`/`jrl`/`jp`/`calr` anywhere in `hdae5000/*.s` targets an
  address inside 0x29C0AA-0x29D97D.

All four checks are automated and reproducible:

    python3 hdae5000/tools/verify_record_table.py

which prints `ALL CHECKS PASSED` reading only
`original_ROMs/hd-ae5000_v2_06i.ic4`. The typed-data source itself was
generated by the previously-rescued `hdae5000/tools/gen_record_table.py`.

## What was NOT converted, and why

Nothing else in this span was left as code. Both `HDAE5000_RECORD_TABLE` and
`HDAE5000_Lang_Codes`'s 14-byte blob are now typed data end to end. The u16
`Field_04/06/08/0A` values inside each record, and the 14-byte
`HDAE5000_Lang_Codes` blob's actual meaning, remain UNDECODED — that is a
semantic-labeling gap, explicitly deferred per the brief, not a structural
one.
