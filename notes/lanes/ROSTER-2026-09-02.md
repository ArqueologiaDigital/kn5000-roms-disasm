⚠ `w10/promdfalsify` and `w10/tier2byte` both hunt the INVERSE hazard: **code
typed as data**. prom_d and custom_data each report zero assembly across a whole
ROM. A `.long` table that is really a routine re-assembles to the same bytes, so
the gate cannot object — and there was a 68,934 B near-miss of that shape
earlier in this push.

## Queued — waiting on a free lane slot

**`w10/missinginsns` — five real TLCS-900 instructions the backend has never
been taught.** Worktree created, brief written, not yet launched (the 20-agent
limit was reached).

`scripts/analysis/unmapped_byte_oracle.py` shows `unidasm` decoding five bytes
that tlcs900_backend refuses outright:

    0x01 normal   0x04 max   0x17 ldf   0x1a JP nnnn   0x1c CALL nnnn

⚠ **Its FIRST job is not the assembler work.** A decoder that cannot see
`jp nnnn` or `call nnnn` can silently end a routine early or frame real code as
data — **in any image, not just v7**. So before adding anything, that lane must
census the PRIORITY images (v10, prom_a..prom_d) for:

* these bytes at the start of a `.byte` run, a `.long` table or an `.incbin`;
* converted routines that END immediately before one of them — the signature of
  a decode that stopped because the decoder could not continue, not because the
  routine did.

If that census finds anything, existing conversions across the push need
re-examining, and that matters more than the 16,683 B of v7 slices these five
bytes gate. v7 remains low priority per the owner's standing order.

⚠ When it does add `jp`/`call` at 16 bits: the address WIDTH IS REQUESTED IN THE
SOURCE, never inferred from whether the value fits. See TOOLCHAIN_VERSION
UPDATE 7 — "narrowest form that fits" would silently change bytes at 339
existing sites.
