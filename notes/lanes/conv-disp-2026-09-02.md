## ⚠ The suffix is not the instruction — read the encoder

The brief called this "the register-plus-displacement family". Five of the
six are not that. `ldb_d8`'s `_d8` is the *data* size, not a displacement:
`LD8_da16` is an 8-bit load through a **16-bit direct address**
(`TLCS900InstrInfo.td:2542`). Only `ld_sril` is a real base-register-plus-d16.
The rewrite target came from the encoder and the `.td`, not from the name.

**And the register spelling is part of the rewrite.** `ldw_d16 xwa, (0x28af)`
is a 16-bit operation written with a 32-bit register name; the native form is
`ld wa, (0x28af:16)`. Spelled `ld xwa, (0x28af:16)` it assembles to
`e1 af 28 20`, a 32-bit load, where the ROM has `d1 af 28 20` — right-looking
text, wrong instruction, wrong bytes. Likewise `ldb_d8 xwa` becomes `ld a`,
because XWA's low byte is A and the ROM's sub-opcode `0x21` says so. The
converter offers both spellings per site and lets the assembler choose, so
none of this mapping is asserted by hand.

## The residual: 1,030 `ld_sril` sites, in two classes

### 189 sites — the 256 sentinel collision (unfixable in source alone)

All 189 use displacement `0x0100`, and all are in `hdae5000/` except one in
`v142/subcpu/kn5000_subprogram_v142.s`. On the native `ld`'s memory operand,
**256 is a sentinel** meaning *"emit the 2-byte `(Xrr+d8)` form with a
displacement of zero"* — `TLCS900MCCodeEmitter.cpp:287`, a deliberate device
for reproducing firmware that used the longer prefix with `d8 = 0x00`.
`ld_sril`'s own encoder has no such sentinel. So one operand text denotes two
encodings depending on the mnemonic:

    ld_sril xhl, (xbc + 0x0100)   ->  e3 e5 00 01 23     (the ROM)
    ld      xhl, (xbc + 0x0100)   ->  a9 00 23

These keep the synthetic mnemonic. Retiring them needs a way to say *"a real
displacement of 256"* on the native operand, which the syntax does not have.
(65536 is a second sentinel of the same shape, one width up; no site uses it.)

### 841 sites — converting them would COST information the byte gate cannot see

These have a displacement in **128..255**, where the encoder warns that the
value does not fit the signed `(Xrr+d8)` field, because `+170` and `−86` are
different addresses that a `d8` byte cannot tell apart. `ld_sril` names the
`d16` form and draws no warning; native `ld` draws one.

**The bytes are identical either way.** The byte gate would have waved all 841
through, green, and the source would have been strictly less definite than
before. The converter therefore requires a candidate to produce the same
*diagnostics* as well as the same bytes and fixups.

★ The count is calibrated against something the converter does not control:
converting these 841 raised the whole build's warning count from **518 to
1,359**, a delta of exactly 841. Two independent instruments, same number.

⚠ This hazard already lives in the tree outside this lane. All 518 baseline
warnings are this same shape — e.g.
`v142/subcpu/kn5000_subprogram_v142.s:35128`, `ld xhl, (xwa+140)`, present on
`main` and untouched here. The gate is green, so those spellings are right and
the warning is advisory; but they are the trade this lane declined to make
841 more times. **Not fixed here** — flagged for whoever owns those files.

## ⚠ A gate taken with the shared `llvm-mc` certified nothing

See `notes/TOOLCHAIN-PROVENANCE-2026-09-02.md` for the pinned binary and
the re-link history. What this lane adds is the evidence of what the churn
actually did to a result.

The finished `ld_sril` conversion **failed** a full gate with
`invalid .org offset '1670541'` in `v10/maincpu/storage/fdc_routines.s` — a
file this lane never touched — and **passed 13/13 on the identical sources**
under a pinned assembler minutes later. `~/compartilhado/llvm-project` had
eight uncommitted modified backend files at the time, including
`TLCS900MCCodeEmitter.cpp`, and its `llvm-mc` was re-linked repeatedly while
`git log` never moved off `7e541b8ddb07`.

A bisect run against that moving binary produced a *confident and wrong*
answer: it fingered `v10/maincpu/ui/ui_widget_defs.s`, which assembles
**byte-identically** old and new when checked with a fixed binary. Three
distinct `llvm-mc` sha256s were observed in one session, and one of them was
not even executable when `make` reached for it.

★ The rule this lane would add to the brief's existing toolchain entry: **it
is not enough to name the toolchain commit — the commit does not identify the
binary when the backend tree is dirty.** Name the *binary*, by hash, and use
the same one for the per-site proof and for the gate.
