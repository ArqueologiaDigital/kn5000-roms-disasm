# Lane brief — full-disassembly push, 2026-09-01

Standing rules for every parallel lane agent working this push. Read this
before touching anything. It exists so the rules are auditable and identical
across lanes rather than paraphrased into each agent's prompt.

## The goal, stated exactly

**Territorial coverage: every byte of every ROM reproduced by real source.**

**Semantic labeling is DEFERRED.** Do not spend budget inventing names. A
region converted to correct, byte-exact, *unnamed* instructions or typed data
is a WIN. A region given beautiful names but still `.incbin` is not.

## What counts as debt — and the trap

Undisassembled means **any byte not reproduced by real source**. That is:

* `.incbin` of a committed blob, **and**
* long `.byte` / `.word` runs that are really un-decoded code or untyped data.

⚠ **`.incbin` count alone is the WRONG instrument.** This project already
shipped a false "territorially complete" claim by counting `.incbin`
directives in a tree whose remaining debt was written as `.byte` — 8,496 bytes
of sound code sat in plain sight passing a test looking for the wrong word.
Measure bytes, not directives.

⚠ C source compiled byte-exact by `clang -target tlcs900` **is real source**,
not debt. Much of the maincpu `.incbin` total is exactly that. Separate the
two before reporting a number.

## The gate is the only certification

`make gate-all` rebuilds every ROM and compares against the dumps: 9 KN5000 +
4 WSA1R = **13 images**. It is green as of `5831d460` and must be green when
you finish.

* Work in **your own worktree** so your build cannot race another lane's.
* Run the gate **in your worktree**, not in the shared tree.
* ⚠ **GATE ONLY WHAT YOU COULD HAVE BROKEN — ADDED 2026-09-02.** `make gate-all`
  now depends on `all`, so it rebuilds all nine KN5000 ROMs. That is correct
  (before, it certified stale objects) but expensive, and with a dozen lanes
  running it is the bottleneck: eight WSA1R-only lanes were each rebuilding the
  whole KN5000 tree they had not touched, at load 21 on 8 cores.
  **If every file you changed is under `wsa1/`**, your gate is:

      git diff --name-only main    # must show ONLY wsa1/ paths
      make gate-wsa1               # 4 images, independent of the KN5000 build

  and that IS sufficient evidence for your change. The full 13-image gate is run
  **centrally on main after each merge** — it is the integrator's job, not
  yours. Conversely if you touched anything outside `wsa1/`, or any shared
  script, tool or Makefile, run the full `make gate-all` yourself.
* Prove the gate can SEE your change: perturb one converted byte, confirm it
  goes red at that address, then restore. A gate that was never shown to fail on
  your edit has not certified it.
* A conversion that changes one byte is a REGRESSION, not progress. Revert it.
* Before quoting the gate as evidence, be sure it would go red on your change:
  an object built from a stale prerequisite certifies nothing. This tree has
  already been burned by exactly that.

## Repo discipline

* **Never `git add -A`.** Name your paths explicitly. A sweeping add once
  swept 55,000 lines of another lane's work into an unrelated commit.
* **Never `git push`.**
* **Never run `git checkout`, `git stash` or `git reset` in the shared tree** —
  other lanes have uncommitted work and it will be destroyed.
  ⚠ **THIS INCLUDES `~/compartilhado/llvm-project`.** On 2026-09-02 a lane ran
  `git stash` there and stashed a different lane's uncommitted encoder work; it
  was restored, but only because the lane noticed. Backend lanes share that
  checkout the same way disasm lanes share this one. Stage your own hunks
  (`git add -p`) rather than clearing the tree.

* ⚠ **A REFUSAL COUNT IS BLIND TO THE WORST DECODER BUG.** Measuring "how many
  forms does the disassembler refuse" cannot see a form it accepts and reads
  WRONG. Three such bugs were found on 2026-09-02 — `b3 c8` is `bit 0,(xhl)`
  and was decoded as `and (xhl),xwa`; one bit table was mapped a whole group out
  of step, hitting 157 samples; and `92 04`, three bytes, decoded to a one-byte
  instruction. Any decoder census must therefore also:
    * **re-assemble every decode** and require the ROM's own bytes back, and
    * **ask a second decoder** (`unidasm`) to agree on length *and operation* —
      because a round-trip cannot tell an ADD called SUB from an ADD.
* Commit **frequently and granularly**. Work that is committed survives a
  crash; work in a worktree does not.
* Every commit message needs the toolchain line:

      LLVM: tlcs900_backend@<short> (<full>)   <- EXAMPLE SHAPE ONLY, never copy a hash

  Get it yourself with `cd ~/compartilhado/llvm-project && git log -1
  --format="%D @ %h (%H)"`. **Never pad a short hash into a long one.**

## Preservation — a hard rule from the project owner

**Do not destroy existing comments, documentation headers, or semantic
structures.** Modify them only when you are sure the result is semantically
better. **Never flatten the tree into one file**: per-subject source files are
the required shape, and flattening would be cheating.

## Reproducibility

If a number is worth putting in your report, the thing that produced it is
worth committing, in the same session, next to what it measures — with a
README line saying what question it answers and the exact command. `/tmp` is
volatile and does not count.

## Reporting

Report, for your lane: bytes of debt **before** and **after**, how you
measured (naming the script), the gate result, and anything you could NOT
convert with the reason. An honest "this region resisted, here is why" is
worth more than a number that overstates.

## ⚠ Addendum 2026-09-02: a directory-scoped `git add` is not narrow enough

The brief says never `git add -A`, after a sweeping add once pulled 55,000 lines
of another lane's work into an unrelated commit. That rule was followed and the
same failure happened anyway.

While rescuing a script from session scratch, the coordinator ran
`git add -- hdae5000 scripts` — directory-scoped, not `-A`. The lane owning that
directory had an in-progress 6,358-line source conversion uncommitted in it, and
the resulting commit, titled *"rescue this lane's tooling from session scratch"*,
contained both the 181-line tool and the entire conversion. The content was
correct — the lane later re-derived it independently and it matched byte for byte
— but the message describes a fraction of what landed.

**The rule is therefore stronger than "no `-A`": name the FILES.** A directory is
shared state whenever any lane might be working in it, and in this project that is
always. `git add path/to/one/file.py` costs nothing and cannot sweep.

And when rescuing another agent's work, run `git status --porcelain <path>` first
and look at what else is dirty there. If something is, it belongs to whoever is
working in that directory, and committing it under your own message removes their
chance to describe it.


## ⚠ Addendum 2026-09-02: the Edit tool corrupts these latin-1 sources

The disassembly `.s` files are **latin-1, not UTF-8**, and several contain raw
high bytes inside `.ascii` literals.

A lane used the Edit tool to patch one stale line reference in
`accompaniment_engine.s`. The edit applied — and **silently replaced an
unrelated raw byte in a distant `.ascii` literal with U+FFFD**. The narrow gate
caught it only because the diff was 550,133 bytes instead of the expected 1,040.

**Patch these files with an explicit latin-1 read/write**, e.g.

    src = open(path, encoding='latin-1').read()
    ...
    open(path, 'w', encoding='latin-1').write(src)

or operate on bytes. And after any edit to a `.s` file, check the diff SIZE
against what you intended before committing — a plausible-looking edit that
rewrites half a file is the failure this catches.

## ⚠ Addendum 2026-09-02: a directive kind judged from one line is not the run

`v7_slice_v9v10_correspondence.py` reports what a slice is by reading the
label's FIRST line. That is not the same as what the region *contains*:
**152 of 180 DATA-kind v7 slices (68,934 B) are a short data header glued onto a
following routine** — `.zero 8` and then 135 bytes of code, for instance.

Converting on the first-line verdict would have typed real code as `.byte`
across 68,934 bytes. The byte gate cannot object in either direction. Measure
the RUN EXTENT (`scripts/analysis/v7_slice_data_run_extent.py`) before trusting
any kind verdict, in either direction.

## ⚠ UNCONFIRMED: the "plain grep returns 0 on latin-1 sources" claim

A lane reported that plain `grep` "silently returns 0 matches on these latin-1
sources due to a binary-file misdetection", costing it time mid-investigation,
and that `grep -a` is required. That was repeated as fact in a merge commit
message (`300a409c`).

**It does not reproduce.** Tested 2026-09-02:

* `file(1)` reports every v7 maincpu `.s` file sampled as *"assembler source,
  ASCII text"* — none is detected as binary.
* 8 of the first 200 tracked `.s` files do contain bytes >= 0x80, and on one of
  them (`hdae5000_data_tables.s`) plain `grep -c` and `grep -a -c` return the
  **identical** count (13,755).

So the general claim is not supported. Something real may still have happened —
this environment resolves `grep` to **ugrep**, whose behaviour differs from GNU
grep, and a specific file/pattern/flag combination could still misbehave.

**Practical guidance, without overclaiming:** if a tree-wide search returns zero
matches for something you expect to exist, do not conclude it is absent — re-run
with `grep -a`, and cross-check with a Python read using
`encoding='latin-1'`. A zero result from a search is exactly the kind of
answer this project has repeatedly found to be an instrument failure rather than
a fact.

## ⚠ `grep` in an agent shell silently skips files with invalid UTF-8

**Use `grep -a` for every census over these sources.**

In a Claude Code agent shell `grep` is a shell FUNCTION routing to `ugrep -I`
(*ignore binary files*). A source containing a byte sequence that is not valid
UTF-8 is judged binary and **skipped entirely** — no matches, exit status 1,
nothing on stderr:

    grep    -c 'f00c' bad.s   -> (no output)  exit 1     the wrapper
    grep   -ac 'f00c' bad.s   -> 2            exit 0     -a defeats it
    command grep -c 'f00c' bad.s -> 2         exit 0     real GNU grep

⚠ The trigger is **invalid encoding, not non-ASCII**. These sources are full of
proper UTF-8 (`⚠`, `★`) and are fine. Malformed sequences come from writing
UTF-8 text through a latin-1 encoder — the double-encoding mistake — or a tool
emitting a lone lead byte.

⚠ **It is invisible to scripts.** Python's `subprocess` and `bash script.sh`
both invoke `/usr/bin/grep` directly and never see the function, so a probe
written the obvious way reports a false green. The committed probe must be
SOURCED and refuses to conclude anything otherwise:

    source scripts/analysis/grep_encoding_hazard_probe.sh

★ This entry replaces an earlier note (commit `80e16190`) that said the hazard
"does not reproduce". That note was wrong because the test lacked the
precondition — it grepped a *valid* UTF-8 file, where the hazard cannot occur.
A test that cannot fail is not evidence, applied to a shell command instead of a
decoder.

## ⚠ The session scratchpad is SHARED between lanes — namespace your files

A lane dumped an address map to a bare filename in the scratchpad and another
lane overwrote it **mid-analysis** (431,959 → 431,738 entries). It was noticed
only because the entry count moved; nothing errored, and the second lane's map
was perfectly valid — for a different tree.

Write to a lane-private subdirectory: `$scratchpad/<lane>/`. Anything at a bare
path there is racing every other lane, silently, and an address map is exactly
the kind of file whose corruption produces plausible wrong answers rather than
a crash.

★ And the general rule this push has now hit from four directions: **a shared
artefact that is regenerable should be regenerated, not reused.** The map costs
seconds; a wrong one costs a lane's entire analysis.

## ⚠ A STALE ADDRESS MAP is invisible to every check except the rebuilt ROM

A lane wrote 13 island conversions, three of them from an address map **one
revision behind the source**. The map pointed at different bytes than the
source line claimed, and:

* `unidasm` decoded them happily — it was given bytes, not a claim;
* `llvm-mc` round-tripped them happily — the text was self-consistent;
* only the **rebuilt ROM** objected, at `0xF16FCC`.

All 13 were reverted. **Any tool in this tree that reads an address map must
assert that the ROM byte at the mapped address equals the byte the source line
itself states.** Proven, not assumed: with the guard, the stale map produces 501
refusals and the fresh map 0, with an identical accepted set.

⚠ `scripts/analysis/address_line_map.py --dump` has also returned stale content
on a re-run that is not yet root-caused. Treat its output as suspect until the
guard above passes. And ⚠ **the scratchpad is shared** — one lane's dumped map
was overwritten mid-analysis by another lane writing the same bare filename, so
namespace it per lane.

★ The general shape, which this push has now hit from several directions: a
derived artefact that is cheap to regenerate should be regenerated, not reused,
and anything read out of one must be cross-checked against the thing it
describes. An address map is exactly the kind of input whose corruption yields
plausible wrong answers rather than an error.

## ⚠ THE TOOLCHAIN IS SHARED AND MUTABLE — name the build every number was taken with

`llvm-project/build/bin/llvm-mc` is one binary shared by every lane, and a
backend lane rebuilds it in place. Two lanes hit this independently on
2026-09-02:

* one died with a transient `PermissionError` on `llvm-mc` because another lane
  was rewriting the binary mid-run — loud, harmless, and the run was simply
  repeated;
* one reported that "the installed llvm build moved off the pinned
  `6fe210fb0a81` to `6f456a19f05b` during this lane", so its early and late
  measurements were taken with **different decoders**.

The second is the dangerous one, because it is SILENT. A decodability figure is
a property of the decoder as much as of the bytes: the same tree gave a
decodable-byte ceiling of **1,445 B before** and **3,044 B after** two decoder
crash fixes, with not one source byte changed.

**So: state the toolchain commit beside any number that depends on decoding**,
and re-derive a before/after pair with a single build rather than straddling a
rebuild. `cd ~/compartilhado/llvm-project && git log -1 --format="%h"` costs
nothing.

⚠ And if you rebuild the shared toolchain, expect to invalidate other lanes'
in-flight measurements — say so in your report so they can be re-run, and
prefer a private build directory if your change is exploratory.

## ⚠⚠ THE SERVICE MANUALS ARE IMAGE-ONLY PDFs — every text search over them is a FALSE NEGATIVE

**This has now cost the project twice.**

* The SX-WSA1R work spent **nine rounds** searching the ROM for an index→button
  map that was printed on **page 32 of its own service manual** (Technics order
  no. EMID951604, page 32 = II-29/30, the CP1/CP2 switch-matrix P.C. diagram),
  invisible to every search because the PDF has no text layer.
* The same work then spent months on chip-select windows whose decoder outputs
  are **named on pages 19–23** of that manual, in legible P.C. diagrams, for
  exactly the same reason.

⚠ **Both instances are the SX-WSA1R, and this brief previously credited the
first one to the KN5000.** There are two different page 32s and they are easy to
swap: the KN5000's is its IC14 address lines. The source that settles it is the
header of `wave7_panel_button_codes.py`, which names the manual and the page.
The lesson is unchanged — it is the *attribution* that was wrong, not the
pattern — but a standing instruction that misnames which machine burned you is
one a reader will discount when it matters.

`pdftotext` returns nothing. `grep` returns nothing. **Neither is evidence of
absence** — they are evidence that the file is a scan.

    pdftoppm -r 300 -png "<manual>.pdf" out/page     # then LOOK at the pages

Before recording that something "is not documented" or "cannot be established
from available sources", **render the relevant manual pages and look at them.**
The manuals live in `~/compartilhado/KN7000/service_manual/`.

★ What that one habit settled in a single lane: `0x7E0008` is an **ATA task
file** (IC18 Y6 = `HDCS`, and IC1 carries `HDINT`/`HDIORDY` pins); `0x104000`
**is** IC3 L7A1429, promoting a ranked inference to established; IC1 is MAIN and
IC2 is SUB; and the two windows the firmware writes but the schematic leaves
**unnamed** are the two where probably no chip is fitted — an *absence* in the
document doing real work, which only reading it could provide.

## ⚠ `until ! pgrep -f <name>` DEADLOCKS ON ITSELF — never write it

This idiom is everywhere in this push's background jobs and **it can never
exit**:

    until ! pgrep -f data_range_census >/dev/null; do sleep 20; done

`pgrep -f` matches against the whole command line, and the waiting shell's own
command line **contains the string it is searching for**. So `pgrep` always
finds at least itself, `! pgrep` is never true, and the loop polls forever.

Measured 2026-09-02: three such waiters were still alive an hour after the work
they watched had finished, each also keeping the others alive, and each
producing a "stale waiter" task notification every time it was reaped. No real
`data_range_census` or `make gate-all` process existed at all.

**Instead:**

* wait on the **PID**: `while kill -0 $PID 2>/dev/null; do sleep 20; done`
* or wait on an **output file** the job writes when it finishes:
  `until [ -s out.log ]; do sleep 20; done` — and have the job write a final
  `EXIT=$?` line so an empty-but-created file cannot fool you
* or simplest: run the job with `run_in_background` and let the harness notify.

★ The general shape, which this push met four times in other costumes: **a test
whose subject includes the tester.** A `pgrep` that matches itself, a census
that walks its own scratch output, a selftest that asserts a precondition its
own success destroys. Each looks like it is measuring the world and is partly
measuring itself.

## ⚠ A hand-edit to a GENERATED file is invisible until someone regenerates

`wsa1/prom_d/wsa1_prom_d.s` carries a header saying *"GENERATED, never edit this
file"*, and commit `c368fa2b` put 27 lines of a lane's provenance straight into
it. Nothing complained: the bytes were right, the gate was green, and the text
would have vanished the next time anyone ran the generator — losing evidence,
silently, with no diff to look at afterwards. Fixed by moving the text into
`gen_prom_d_asm.py`, where it survives regeneration.

**If a file says it is generated, put your prose in the GENERATOR.**

★ Swept the rest of the tree 2026-09-02 and the hazard is confined. Four `.s`
files have real generators — `gen_msp_factory_defaults_c.py`,
`gen_sndparam_records_c.py`, `generate_ssf_gate_states.py`,
`gui_format_strings_cells.py` — and all four are **dry by default**, writing
only under `--write`/`--apply`, so none can clobber by accident. All verify
clean against the committed sources today. The other ten `.s` files that name a
`.py` in their header name a *verification* script, not a generator.

⚠ Note what the sweep does NOT cover: a generator that is dry today can be given
a write-by-default mode tomorrow, and the check above is a snapshot. The durable
fix is the rule, not the sweep.

## ⚠⚠ A REBUILT TOOLCHAIN CAN MATCH NEITHER SOURCE STATE

The shared `llvm-mc` moved **six times** during one lane on 2026-09-02, and one
link produced a binary whose `jr` handling matched **neither the old source nor
the new one** — it neither truncated nor diagnosed. Re-linking fixed it.

So a decode or encode figure taken across a rebuild window is not merely stale,
it can be **incoherent**: measured against a toolchain that never corresponded
to any commit. Every such figure must name the toolchain commit it was taken
at, and a before/after pair must be re-derived at a single build rather than
straddling one.

⚠ **Your rebuilds invalidate other lanes' in-flight measurements.** Say so in
your report when you rebuild. A private build directory would avoid it, but
`/home` has been sitting near 96% full, so that is not currently available —
which makes announcing the rebuild the only mitigation.

## ⚠ A CONTROL THAT DIES WHEN ITS BUG IS FIXED IS NOT A CONTROL

A sweep's selftest used a **real defective ROM sequence** as its positive
control. A parallel lane fixed that defect, and the selftest went red — not
because the sweep broke, but because its control had been repaired underneath
it.

Pin a verdict rule as a **pure function tested on synthetic input**. Real data
makes a fine *corpus*; it makes a poor *fixture*, because the tree is supposed
to change and a fixture is supposed not to.

★ This is the same family as the earlier `v7_label_parity_evidence.py` lesson —
a measurement whose preconditions its own success destroys — and as the census
that walked its own scratch output. When the thing under test and the thing
doing the testing share state, the test reports on itself.

## ⚠ GATE THE ASSEMBLER, NOT JUST THE BYTES — AND PIN THE BINARY

Two defects of the same family, found together on 2026-09-02.

**The WSA1R Makefile never listed `$(LLVM_MC)` as a prerequisite.** Part 152's
repair reached the KN5000 Makefile only. Touch the assembler, ask `make -n all`
what it plans, and the answer was **0 of 4** WSA1R images — so a WSA1R
`IDENTICAL` could be certifying an object built by an earlier assembler, and a
backend change could alter WSA1R encodings without the gate ever recompiling.
Fixed in `07db0cc2`; `scripts/analysis/assert_toolchain_is_a_prerequisite.py`
now runs inside `gate-all` and its `--selftest` strips the prerequisite back out
and requires the check to go red (0/8 and 0/4).

★ The lesson generalises past make: **ask what your green would look like if the
work had never happened.** Here it looked identical, which is the whole defect.

**The shared `llvm-mc` moves under running lanes.** One lane iterates on the
backend in `~/compartilhado/llvm-project` while others gate against its output.
On the night of 2026-09-02 the binary was re-linked at least five times
(`52563be1` → `8c211d2f`) with git reporting an unchanged `7e541b8ddb07`,
because the tree carried eight uncommitted files. A per-site byte comparison and
the gate that follows it can therefore use **different assemblers**.

Mitigation, since `/home` at 96% rules out per-lane build directories: snapshot
the binary (10.9 MB) and pin every lane to the copy —

```
cp llvm-project/build/bin/llvm-mc toolchain-snapshot/llvm-mc.snap
make LLVM_MC=$PWD/../toolchain-snapshot/llvm-mc.snap gate-all
```

Pass the **same** binary to per-site verification and to the gate, or the two do
not corroborate each other. The backend lane commits in `llvm-project` as each
feature lands: a dirty tree means nobody can rebuild the assembler that produced
the night's numbers, that lane included.
