# llvm-asym lane, 2026-09-02 — the decode/encode asymmetry, measured

**Question.** `scripts/analysis/decode_encode_asymmetry.py` reported five ROM
byte sequences, four of which llvm-objdump printed as a text that re-encodes to
DIFFERENT bytes. Which side is wrong in each — and is four the whole problem or
the tip of it?

Reproducibility: every figure below comes from a file in
`llvm-asym-2026-09-02/`, whose README names the command that produced it.

---

## 1. The four verdicts: ALL FOUR ARE DECODE-SIDE, AND EVERY SPELLING ALREADY EXISTED

⚠ Not one of the four needed a new encoding. Asked directly, `llvm-mc` produced
the ROM's exact bytes for all four in a single command:

    pushw (xiz+4)   -> 9e 04 04        bit 7,(xhl+1)   -> bb 01 cf
    pushw (xix+32)  -> 9c 20 04        ldir85          -> 85 11

That is this project's standing rule firing for the tenth time. The decoder had
the wrong table; the encoder was right in every case.

| ROM bytes | what it really is (unidasm agrees) | what the decoder printed | why |
|---|---|---|---|
| `85 11` | `ldir` with the prefix's base-register field = 5 | `ldir` (= `80 11`) | the field is part of the encoding even though the hardware ignores it; decoding every index to the plain spelling lost it |
| `bb 01 cf` | `bit 7,(xhl+1)` | `and (xhl+1), xsp` (= `ab 01 cf`) | a DESTINATION-table sub-opcode fell through into the SOURCE table's ALU rows |
| `9e 04 04` | `pushw (xiz+4)` | `push xiz` (= `3e`) | decoded to `PUSH16`, the one-byte REGISTER push, throwing the memory prefix away |
| `9c 20 04` | `pushw (xix+32)` | `push xix` (= `3c`) | same |

The fifth case, `7f da 61`, was never asymmetric and still is not.

⚠ **`TOOLCHAIN_VERSION`'s `ldir` refusal was right to refuse, and the correct
fix was the decode-side one it implied.** `tools/spelling-probes/README-ldir.md`
had already established the rule from the raw bytes: `0x80 + (size<<4) + ridx`,
sub-opcode `0x11`; **eight** byte pairs `80 11 … 87 11` all print `ldir`, and
emitting the printed text verbatim gets the wrong bytes at 827 of the 849
`ldir` sites in the ten binaries (97.4 %). Reaching for the native spelling
would indeed have moved bytes. Teaching the DECODER to print `ldir85` for
`85 11` moves none.

**Status: 5 of 5 now round-trip.** ⚠ **Not by this lane.** A parallel backend
lane landed the same three decoder fixes in `1f75e04f774a` and `b3814f8f7b11`
while this lane was measuring; this lane's independent contribution is the
verification, the population below, and §3. Duplicated effort is worth
recording as such rather than claimed.

## 2. THE POPULATION — and it is 122× the sample

`scripts/analysis/decode_encode_asymmetry_sweep.py`, at
`tlcs900_backend@d5ed58d05518`:

    1,323,980 real instructions swept, from all 13 committed images
      OK        1,317,312   99.4964 %
      ASYM            472    0.0357 %   wrong text, right length -- SILENT
      LENGTH           16    0.0012 %   wrong length -- DESYNCHRONISES a sweep
      NODECODE      6,180    0.4668 %   refused outright -- loud

    488 sites in 51 distinct forms.

**Why this is the right population.** An arbitrary offset into a ROM is usually
data, so a linear sweep over raw dump bytes measures mostly noise. This sweep
takes its instruction boundaries from `llvm-mc --show-encoding` over the tree's
own sources: every probe is a real instruction at a real boundary, and its bytes
are the ROM's, because that is what `make gate-all` certifies. Two of the
thirteen images (`custom_data`, `wsa1_prom_d`) contain zero instructions —
verified, not assumed: `--show-encoding` emits not one `; encoding:` for either.

**So: four was the tip.** But the shape of the remainder is not the shape of the
four, and that matters more than the ratio:

* **the SRI / `(Xrr+d16)` printer, ~340 sites.** `e3 e5 00 01 23` is
  `ld xhl,(xbc+256)` in a d16 form; the printer emits a plain `(xbc+256)` and
  the ASSEMBLER then encodes it as the d8 form with the displacement truncated
  to `0x00` — `a9 00 23`. Two defects, printer and parser, and the parser half
  is a silent truncation of exactly the UPDATE 8 class.
* **don't-care bits, ~120 sites.** `06 0c` prints `ei 4` and re-encodes `06 04`;
  the operand's upper bits are architecturally meaningless. `TOOLCHAIN_VERSION`
  UPDATE 11 already recorded ldi/ldd/ei as a refusal for exactly this reason.
  **This part of the count is not a defect** and should not be reported as one.
* **the register-indexed memory-to-memory form, all 16 LENGTH sites.**
  `f3 07 e4 e0 16 8e 25` is a 7-byte `ldmmw_dri`; the decoder consumes 5 and
  calls it `call_rr 14, xbc, wa`. These are the only forms in the tree that
  desynchronise a linear sweep, and they are one family in one image.

### 2b. The forms that COULD break, table by table

`scripts/analysis/decoder_subopcode_cross_check.py` walks 23 prefix tables
sub-opcode by sub-opcode against MAME's unidasm — 5,888 slots — so a wrong entry
is found even where no image contains it:

    AGREE 1790   ASYM 124   MNEMONIC 910   LENGTH 0
    LLVM-NONE 1411   UNI-NONE 30   BOTH-NONE 1623

`MNEMONIC` is mostly cosmetic (this backend spells LDCF `ldcfm`, INC (mem)
`incdi8`); those all re-encode correctly. ⚠ **The first version of this script
tested the NAME before the BYTES and hid 40 real asymmetries behind a cosmetic
label.** ASYM is judged on bytes and is checked first now.

**`UNI-NONE` = 30 forms this backend decodes that MAME leaves undefined**, and
it splits in two:

* 25 are 32-bit register operations in the `E8` table (`cpl xwa`, `neg xwa`,
  `res 0,xwa`, `scc cc,xwa`, …) that are real TLCS-900 instructions MAME's table
  simply does not carry. Here MAME is the incomplete one.
* the two the syntax lane named — **`EXTS8`** (`C8+r`, `0x13`) and **`CALL_DD8`**
  (`F0, addr8, 0x08`) — plus `ld (mem),0` at sub-opcode `0x08`. These are the
  hazardous kind: a decode for a byte MAME calls `db` is exactly what lets a
  linear sweep walk through a data table producing plausible code. Confirmed:
  llvm reads `cb 13` as `exts c` and `f0 63 08` as `call_dd8 99`, unidasm reads
  both as `db`. All **8** sites are twinned v9/v10 pairs in
  `audio/sound_editor_ui.s`, `audio/note_voice_mapping.s` and
  `audio/semenu_routines.s`. **Not changed by this lane** — deleting the decode
  makes those 8 lines stop assembling, which is a data-vs-code reframing call
  for whoever owns those files, and the encodings need the Toshiba manual, not
  a second disassembler, to settle.

## 3. `jr` TRUNCATED ITS DISPLACEMENT SILENTLY — 36 sites, and 2 are worse

Fixed here: `tlcs900_backend@e4326acd28aa`, with
`llvm/test/MC/TLCS900/branch-displacement-field.s` built from real ROM bytes.

⚠ **The reported scope was three mnemonics; it is one.** `jrl` and `calr`
already refused an over-wide operand — they emit through `emitImmediate`, which
has carried the check since `95f7f2d40428`. Only `jr`/`jrcc` (and `djnz`, same
shape) masked with `& 0xFF`. Measured before changing anything, per UPDATE 8's
precedent.

`scripts/analysis/branch_displacement_field_audit.py` over 113,973 `jr`,
36,109 `jrl`, 38,198 `calr` and 278 `djnz` lines:

* **34 sites: SIGN-EXTENDED DISPLACEMENT.** `jr c, 16777183` for -33 — the field
  widened to 24 bits by the disassembly that produced the line. Truncating moves
  no byte. Identical to the 31 `jrl` operands `95f7f2d40428` found.
* **2 sites: A TARGET ADDRESS, and this is the real finding.**
  `wsa1/prom_a` writes `jr T,0xfe434d` at FE42FE and `jr ULE,0xfe525a` at
  FE51FE. Those assembled to the correct `68 4d` / `63 5a` **only because both
  instructions end at a `0x…00` boundary, so the target's low byte IS the
  displacement.** Move either routine by one byte and the source silently
  assembles a branch to the wrong place, with the byte gate green throughout.
* **0 `djnz` sites** pass a bare number at all; it is included for consistency.

Both classes are now rewritten as displacements and the assembler refuses the
mistake. Proof the check can see it: before the source fix, 4 of 8 KN5000 images
stopped assembling with exactly 36 errors at exactly those lines.

## 4. What this lane refused

* **`tsetda` / `tsetda_24` encode sub-opcode `0xA0`; unidasm says TSET is
  `0xA8`** and `0xA0` is STCF. `TSETm`, `TSET_DD8` and `TSET_DD16` all use
  `0xA8`, so the direct-address pair is the odd one out and is probably wrong.
  There are **zero** call sites in the tree, so correcting it would move no
  byte — but it is still changing an existing spelling's encoding, and one
  disassembler is not the Toshiba manual. Recorded, not changed.
* **EXTS8 and CALL_DD8**, per §2b.
* **The 51 broken forms other than the four**, which belong to the printer/parser
  pair for the SRI d16 operand and to the `ldmm_dri` family. Named, counted and
  left for a lane that can take the printer and the parser together; a
  printer-only fix would trade an asymmetry for a different one.

## 5. Method notes worth keeping

* ⚠ **A control that dies when its bug is fixed is not a control.** The sweep's
  first selftest used the real `85 11` as its negative case and went red the
  moment another lane fixed it. The verdict rule is now a pure function
  exercised on synthetic input.
* ⚠ **The shared toolchain moved four times during this lane**
  (`6f456a19f05b` → `1f75e04f774a` → `b3814f8f7b11` → `e4326acd28aa` →
  `e816cddb6e2d` → `d5ed58d05518`), and once produced a binary whose behaviour
  matched NEITHER source state: a link at 22:14 gave a `llvm-mc` in which `jr`
  neither truncated nor diagnosed. Re-linking fixed it. Any decode figure that
  straddles such a window is worthless; every number here names its commit.
* ⚠ **`list.index()` inside a per-probe loop** turned a 15-second sweep into one
  that had not finished in ten minutes at 238,587 probes. O(n²) hides well
  behind a progress-free script.
