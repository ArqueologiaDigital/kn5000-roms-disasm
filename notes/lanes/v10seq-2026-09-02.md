# Lane v10seq — the sequencer's 11,096 `.byte` operands, 2026-09-02

Target: the whole of `v10/maincpu/sequencer/` (15 files) plus
`v10/maincpu/sequencer/accomp_screens/`.

Branch base `a99564a6`. Everything below is produced by a committed script; the
exact command is in each script's header.

## 1. The three-way split (the deliverable that matters most)

`scripts/analysis/seq_byte_operand_triage.py`, on the pre-lane tree:

    python3 scripts/analysis/address_line_map.py --dump /tmp/amap.json
    python3 scripts/analysis/seq_byte_operand_triage.py --amap /tmp/amap.json

| bucket | bytes | share |
|---|---:|---:|
| (a) CODE-AS-BYTE — real instructions spelled as data | 1,392 | 12.5% |
| (b) UNTYPED-DATA — structured data written as a byte soup | 3,939 | 35.5% |
| (c) BYTE-TABLE-OK — a genuine byte table, already correct | 5,765 | 52.0% |
| total | 11,096 | |

**So a majority of the 11,096 is not debt at all.** That was the point of
splitting rather than counting: the raw `.byte` total overstates the debt by
about a factor of two.

The unit is a maximal RUN of consecutive `.byte` lines. Each run is given a ROM
address by `address_line_map.py` (which labels every emitting line, relinks, and
reads the addresses off the ELF — no text matching), then a REGION (enclosing
label to next label, from `llvm-nm` on the real linked ELF), then a reference
kind for that region over the whole `v10/maincpu` tree: BRANCH if a
call/jr/jp/djnz names any label in it, ADDR otherwise.

## 2. How the classifier could be wrong, and the control

Three failure modes, all invisible to the byte gate:

1. code reached only by fallthrough, or through an indirect jump table, has no
   reference of its own and looks address-only → real code lands in (b) or (c);
2. a data-as-code misframe manufactures fake `jr`/`call` operands naming labels
   inside itself, so data can look branch-referenced → data lands in (a);
3. the ASCII test fires on binary data that happens to sit in 0x20–0x7E.

**Control** (`--control`): the same branch-vs-address test scored against the
266 spans lanes V10DAC and V10DAC2 adjudicated **by hand** — 196 judged DATA,
70 judged CODE.

                says CODE   says DATA
    hand CODE          37          33
    hand DATA           0         196

* **0 of 196** hand-judged DATA regions are called CODE. Bucket (a) requires a
  branch reference, so on this control it has a zero false-positive rate — which
  is the direction that matters, because a wrong (a) invites converting data
  into instructions.
  ⚠ Weakness of this control: those 196 spans were already converted to data, so
  their fake branch operands no longer exist in the tree. The measurement is
  right for the tree I classified and does **not** show the test would have
  resisted their pre-conversion form.
* **33 of 70** hand-judged CODE regions are called DATA — failure mode 1, at a
  47% rate. **Therefore 1,392 B is a LOWER BOUND on (a)**, and buckets (b) and
  (c) certainly contain real code. No bulk conversion of (b) is licensed by this
  instrument; every region below was adjudicated individually.

## 3. Bucket (d): blocked on a known decoder gap

Added after the coordinator's `byte_run_start_enrichment.py` finding. Runs
starting with one of `{0x01 normal, 0x04 max, 0x17 ldf, 0x1a JP nnnn,
0x1c CALL nnnn}` — five leading bytes the pinned backend cannot decode at all —
are tagged (d) and reported **crossed with** (a)/(b)/(c), never instead of it.
Pre-lane, over the directory: **414 of 2,873 runs (14.4%) blind vs 6 (0.2%)
control.** None was converted into instructions: the assembler cannot spell them
until lane `w10/missinginsns` lands, and a wrong reading that re-assembles to
the same bytes passes the byte gate.

### ⚠ A confound in that instrument, demonstrated here

`scripts/analysis/seq_blind_start_confound.py`

    python3 scripts/analysis/seq_blind_start_confound.py \
        --file v10/maincpu/sequencer/seq_event_playback.s --before a99564a6

A **misframed data table** manufactures blind-starting runs in bulk: the wrong
instruction stream breaks at every byte the decoder refuses, and a note/channel
table's own values include 0x01 and 0x04 constantly. `seq_event_playback.s` is
the highest-rate file in v10 at 40.9%:

    BEFORE a99564a6   runs=137  blind=56 (40.9%)  control=0
    AFTER  HEAD       runs= 59  blind= 1 ( 1.7%)  control=0

Typing two lookup tables took it to 1.7% and removed 55 of the 56 blind runs —
**without converting anything into an instruction**, so no real undecoded code
can have been removed. This does not refute the image-wide enrichment; the other
three high-rate files in this directory are untouched by it. It does mean a
per-file rate cannot be read as a count of undecoded-code fragments until that
file's data-as-code misframes are cleared.

* **1,135 B of data-as-code retired** — bytes that were instruction mnemonics
  inside a region that is really data.
* **2,311 B of `.byte` operands re-typed** into `.short`, `.long` or an aligned
  record grid with a stated shape.
* **67 B deliberately NOT converted**: two real subroutines living *inside* data
  blocks. `Voice_NoteChannelTable1+0x422` is `call`ed from
  `accompseq_routines.s`; `AccVoice_IndexedTableLookup_BaseOffsets+0x2A2` is the
  routine that reads the +0x2C8 table. Both would have been destroyed by a
  whole-block conversion.

Every conversion is justified by its READER, not by how the bytes look:

* `AccVoice_ParamIndexData` — five references, all `ld xhl, <label>`. The +0x26
  segment is exactly the 48 entries its reader's `cp w,0x30` allows and holds
  nothing but 0/1/2; +0x5B is the ramp 0,5,…,35; +0x63 is 8 LE16 words matching
  its reader's `sla a,1`.
* the three note grids — each reader builds `(note<<3) + ((h&3)<<1)` and ends in
  `ldw_sri`, a WORD load, so each record is four LE16 fields; each block is
  exactly 2 + 128×8 B and ends where the next routine begins.
* `Voice_NoteChannelTable1+0x43F` — 16 rows × 8 LE16, and columns 6 and 7 are
  zero in every row.
* `AccVoice_OffsetTable` — `sll xhl,2` then `ld xhl,(xhl)`, a LONG load, and
  `cp a,0x3f` gives exactly 64 entries; `AccStyle_TempoMultiplierTable` —
  `sla l,1` then `ldw_sri`, and `cp l,0xf` gives exactly 16.
* `AccVoice_IndexedTableLookup_BaseOffsets` — two parallel 84-entry LE32 tables
  the reader loads and adds, plus an 8-entry one bounded by `and hl,7`; +0x152
  is the ramp 0xA0, 0x100, 0x160, … step 0x60.

Seven `naka_header NAKA_TYPE_0x00` macro invocations were removed as a misframe:
the macro emits `00 00 60 01`, and each sat at offset 2 mod 4 from the table
base, i.e. straddling two LE32 entries. The bytes are unchanged.

## 5. Refusals

* **(a) CODE-AS-BYTE, 1,392 B — refused, blocked in the toolchain.** These are
  islands wedged between instructions in branch-referenced routines. The leading
  bytes are overwhelmingly TLCS-900 addressing PREFIXES the backend cannot
  decode: 0xC1 (300 B), 0xF1 (216), 0xC3 (73), 0xD3 (67), 0xF3 (63), 0xF2 (57),
  0xE3 (55), 0x9F (55), 0xD1 (43), 0xF0 (42), 0xC7 (42). Converting them needs
  decoder work in `llvm-project`, not source work here. ⚠ The backend does
  define generic literal emitters (`extpfx2`…`extpfx10`, `mrdb3`, …) that encode
  to exactly their operand bytes; spelling a `.byte` run with one of those would
  change nothing but the directive's name and would frame data as an
  instruction. Not used.
* **The 217 address-only regions holding class-(b) islands (42,175 B of region,
  3,088 B of residue) — refused in bulk.** Several are named `*_Dispatch2`,
  `AppEvent_SubDispatch`, `SeqChan_InitChannelState`: exactly the shape of code
  reached through an indirect jump table, which the control shows this
  instrument misses 47% of the time. Only the six regions above had a reader
  that positively identifies them as an indexed table.
* **`AccPatch_PartNumberTable` (24 B) — checked and refused.** The triage's
  LE16 rule flags it on byte statistics, but its reader is `and a,0x1f` /
  `ld l,a` / `add xhl,<table>` / `ld a,(xhl)`: a 32-entry BYTE table, already
  correct. A realised instance of failure mode 3, found because the reader was
  checked before converting. Every region in section 4 had its reader checked
  the same way.
* **`AccScreen_UIDataBlock` (1,609 B) — left as `.byte`.** Lane B4 already
  re-framed and documented its record shape on 2026-08-30; further typing needs
  the record grammar, not this lane's evidence.

## 6. Gate

Full `make gate-all` in this worktree (13 images), plus the required negative
control: `.short 0x0170 -> 0x0171` in the converted `+0x43F` grid made the v10
build differ at byte 1512595, which is exactly 0xF71492 − 0xE00000 + 1, the
address that grid entry occupies; restoring it returned the ROM to
byte-identical. A gate that was never shown to fail on the edit has certified
nothing.

## 7. The brief's UNCONFIRMED grep claim: confirmed, with the mechanism

`scripts/analysis/grep_skips_latin1_probe.py`

The addendum's report is real and its falsification test was measuring the
wrong property. The discriminator is **UTF-8 decodability**, not "contains
bytes >= 0x80":

* `hdae5000/hdae5000_data_tables.s` -- the brief's control -- has high bytes
  that happen to form valid UTF-8, so it is searched normally and plain and
  `-a` agree. It is the one kind of file the failure cannot affect.
* 4 of this directory's 15 `.s` files do not decode as UTF-8, including
  `accompaniment_engine.s` (11 raw latin-1 bytes, first at offset 23324) which
  holds 6,058 of the 11,096 operands this lane was sent to triage.

It is not a property of the repository or of GNU grep: `/usr/bin/grep` searches
every one of them. It is a property of the shell. In the Claude Code agent
shell `grep` is a function that execs **ugrep with `-I` always on**, and
ugrep's binary test is UTF-8 decodability. Observed there:

    $ grep -c '\.byte' accompaniment_engine.s      ->  (no output at all)
    $ grep -a -c '\.byte' accompaniment_engine.s   ->  1431

A tree-wide `grep -c` over this directory therefore lists 11 of 15 files and
loses the four largest — and prints no diagnostic for the four. Silence, not a
zero, which is why it reads as "the string is absent". This is the first thing
that happened to this lane.
