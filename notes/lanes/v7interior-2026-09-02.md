## The actual answer: none of the three, or rather a fourth thing

The brief's three explanations (wrong start / wrong label / embedded table)
were written for a case where the labels are basically trustworthy and the
puzzle is a local framing disagreement. That is not what this pool turned out
to be.

**14 of the 15 regions' interior labels are simply WRONG for v7** -- not
subtly displaced, not victims of one bad instruction upstream, but assigned
to a v7 byte range that implements different code than the borrowed name
describes. The 15th (`audio_control_engine.s:6762`) is a different, much
smaller thing: a genuine 2-byte orphan gap with no label at all.

### The evidence, built in three independent layers
(`scripts/analysis/v7interior_label_diagnosis.py`)

1. **Boundary anchoring rules out "wrong start."** For every region, decoding
   continuously from EVERY interior label's own address (not just the
   region's census-given start -- TLCS-900 decode is memoryless/forward-only
   per instruction, so restarting at a label is a real independent test) was
   tried. No anchor makes the labels AFTER it land; even independent
   per-block decoding (each label-to-label span decoded on its own, with no
   assumption carried from its neighbours) fails to reproduce the declared
   boundaries. If this were "the census started three bytes early," some
   anchor would fix everything downstream. None does.

2. **`grep -a` finds essentially zero external references** to any of the
   ~100 labels in this pool, tree-wide -- with exactly one exception (below).
   ⚠ **Use `grep -a`.** Plain `grep` silently under-matches these latin-1
   sources: it reports **zero** hits for a string that occurs 33 times in
   `v7/maincpu/ui_widgets/widget_dispatch.s`, because its binary-file
   heuristic misfires on that file. This cost real time mid-lane -- a first
   pass concluded a live label was unreferenced and dropped it, which broke
   the link (`undefined symbol: MidiCC_VoiceParam_8`) until re-checked with
   `-a`.

3. **v9/v10 byte-parity is the decisive layer.** Every one of these labels
   carries the SAME NAME as a fully-disassembled v9/v10 routine -- proof a
   v9/v10-correspondence tool assigned them. Fetching that routine's own
   address in v9 (via its assembled symbol table) and diffing v7's raw ROM
   bytes at the v7 region's address against v9's raw bytes at v9's OWN
   address, over the label's declared size (from
   `v7/maincpu/transplant_manifest.txt`, whose per-label sizes sum with ZERO
   drift across every region -- the byte-count bookkeeping is exact):

   | region (first label) | size | byte diffs |
   |---|---:|---:|
   | `Param_SignExtendRetu_Block` | 222 | 214 (96%) |
   | `StoreAndReturn_Block` | 105 | 103 (98%) |
   | `SeekRecord_Done_Block2` | 75 | 74 (99%) |
   | `SeqFile_SkipTrackPad_Loop` | 149 | 147 (99%) |
   | `MIDI_SendPartVol_StoreAndSend` | 94 | 94 (100%) |
   | `SendChannelPressure_Prologue` | 169 | 168 (99%) |
   | `Voice_EmitMidiNoteAndBankEvents` | 205 | 202 (99%) |
   | `NoteMap_SlotLoop_Continue` | 172 | 170 (99%) |
   | `SndParam_Widget1_CallType4` | 749 | 740 (99%) |
   | `SeqBuf2_InitWithInterrupts` | 111 | 110 (99%) |
   | `MidiSysEx_SendPCRegValue` | 123 | 121 (98%) |
   | `MidiCC_Handler_PairedParamA` | 994 | 984 (99%) |
   | `MIDI_RX_CONTEXT_RESTORE` | 296 | 294 (99%) |
   | `ClkTick_Src2ClickIncrement` | 204 | 196 (96%) |

   96-100% byte divergence, universally. Real shared-then-diverged code
   (same source, different absolute addresses baked into a later compile)
   would show a LOW diff rate -- most opcode bytes identical, only address
   operands differing. This is indistinguishable from unrelated data: a
   correspondence tool matched these regions to v9/v10 routines by NAME and
   SIZE, never by content, and for this whole residual pool it is wrong.

   Concretely, decoding `midi_serial_routines.s:438`'s bytes on their own
   terms (ignoring the borrowed "SC0 serial port init" labels) gives clean,
   sensible MIDI CC dispatch code -- `ld A,(0x95ce); cp A,0x19; ...; ld
   XIX,addr; ld E,(XIX+A); ld (0x95a8),BC; ld (0x95aa),DE; ld (0x95ac),A;
   call 0xfcbd7c` -- the exact same "stage a MIDI event via a register-
   indexed table lookup, call a shared sender" idiom seen correctly-named
   elsewhere in `midi_dispatch_handlers.s`. It is real code; it is just not
   the routine "MIDI_RX_CONTEXT_RESTORE" at all.

### The one exception that proves the rule: `MidiCC_VoiceParam_8`

Of the ~100 labels checked, exactly one has a live, load-bearing reference:
`.long MidiCC_VoiceParam_8 + 38` (33 times) and `+ 59` (once) in real jump
tables in `widget_dispatch.s`. This is corroboration in the opposite
direction from the rest of the pool -- proof that when a label genuinely
matters, it shows up as a real reference, and its absence elsewhere is
informative, not merely unproven.

## What remains blocked, and why: one dominant backend gap

406 B (11.1%) stayed as `.byte` after conversion. This is NOT a residual
mystery -- decoding the undecoded chunks with MAME's `unidasm` (used only for
boundary-walking, not final encoding) names them cleanly, and testing each
form against `llvm-mc` pins down two related, already-partially-documented
LLVM TLCS-900 backend gaps (`DEBT-INVENTORY-2026-09-02.md` item 5):

1. **`BITm`/`SETm`/`RESm` have no 16-bit absolute-address form at all** --
   roughly half the remaining bytes (`bit`/`set`/`res` account for ~210 of
   406 B). The ROM encodes `bit 5,(0x0432)` as 4 bytes with an `0xF1` prefix.
   `llvm-mc --triple=tlcs900 --disassemble` on `f1 32 04 cd` fails outright
   ("invalid instruction encoding"); `TLCS900InstrInfo.td` defines exactly
   one `BITm`/`SETm`/`RESm` (`MemDstBitOpInst<0xC8,...>`), the 24-bit/5-byte
   `0xF2`-prefix form. There is no alternate mnemonic to select the 4-byte
   form -- hand-writing `bit 5,(0x0432)` assembles to `[0xf2,0x32,0x04,0x00,
   0xcd]`, five bytes, the WRONG encoding for what the ROM actually has.
   This is the exact gap the debt inventory already named ("RESm/SETm/BITm
   missing from `decodeMemPrefix()`"); this lane adds the concrete byte
   evidence and the missing-assembler-spelling half of the story.

2. **The mirror direction of `decodeMemPrefix`'s "MemALU register-source"
   table is missing.** `TLCS900Disassembler.cpp`'s `decodeMemPrefix()`
   implements `(mem) OP= reg` (opcode bases `0x88/0xA8/0xC8/0xD8/0xE8/0xF8`,
   its `MemALURegOps` table) but not the mirror `reg = reg OP (mem)` via the
   SAME long/d8-displacement source-memory prefix family (bases ending in
   `0`, not `8`: `0x80` ADD, `0xA0` SUB, `0xC0` AND, `0xD0` XOR, `0xE0` OR,
   `0xF0` CP). Concretely: `af 02 f0` is `cp XWA,(XSP+2)` per `unidasm`, and
   `llvm-mc`'s ASSEMBLER already accepts and round-trips
   `cp xwa, (xsp+2)` -> `[0xaf,0x02,0xf0]` perfectly -- so this is a pure
   DISASSEMBLER gap, not an encoder one. Accounts for the rest of the
   remainder (`cp`/`add` and friends via this prefix family).

**Handoff to `w10/llvmspell`:** both gaps are in
`llvm/lib/Target/TLCS900/Disassembler/TLCS900Disassembler.cpp`. (1) needs a
16-bit-address `BITm16`/`SETm16`/`RESm16` (or equivalent) decode case plus a
matching assembler spelling, mirroring how `LD16mi_dst_02` was split from
`LD16mi_dst` for an analogous 16-bit-vs-other-width collision (see the debt
inventory's LD-immediate entry). (2) needs `decodeMemPrefix()`'s ALU
register-destination-from-memory case extended to the `0x80/0x90/0xA0/0xB0/
0xC0/0xD0/0xE0/0xF0` family the same way `MemALURegOps` already covers
`0x88/.../0xF8`. Neither of these was worked around in this lane -- the
bytes are left as `.byte`, correctly, pending the backend fix.
