# Lane V10AUDIO -- the v10 maincpu audio engine's `.byte` residue

Worktree `~/compartilhado/disasm-lanes/v10audio`, branch `w10/v10audio`.
Scope: every `.s` in `v10/maincpu/audio/` that is not a `sound_data_*` tone
table and not `sound_editor_ui.s` / `semenu_routines.s` (another lane's).

Toolchain: measurements before ~10:20 on 2026-09-02 used `llvm-mc` built from
`tlcs900_backend@58fb7f2afaed`; the final ones and every gate run used
`6f456a19f05b`, which added decode for `ldf` / `jp16` / `call16` / `normal` /
`max`. Where a number is toolchain-sensitive it says so.

## The headline

`scripts/analysis/v10audio_byte_debt.py` (source-text only, no build):

    5,700 B  spelled as `.byte` operands at the start
    5,338 B  at the end

That is a **net** figure and it badly understates the work, because 395 B moved
INTO `.byte` from garbage mnemonics. Gross:

    527 B  `.byte`  ->  `.long` pointer tables / real instructions
    150 B  `.byte`  ->  real instructions (mis-framed instruction re-frames)
    480 B  mnemonics -> typed `.byte` / `.hword` data (data-as-code retired)
    ---
  1,157 B  of territory now says something true that it did not say before

**`make gate-all` is GREEN: 9 KN5000 + 4 SX-WSA1R images, all byte-identical.**

## The split, and how it was decided

`scripts/analysis/v10audio_byte_triage.py` buckets every literal `.byte` run.
It never classifies on whether the bytes disassemble -- data in this ROM
decodes into plausible mnemonics and the byte gate cannot object. It uses what
REFERENCES the run (a whole-image decode of CODE territory only, split into
control-flow targets and address loads), context tiling from established code,
the census's calibrated table-tail guard, and pointer-table shape.

Measured on the tree as it stood BEFORE this lane's conversions (workdir `cw`,
llvm-mc 58fb7f2afaed), 5,700 B in 1,600 runs:

| bucket | runs | bytes | what it is |
|---|---:|---:|---|
| (a) CODE | 197 | 574 | instructions spelled as data |
| (b) TYPE | 3 | 72 | pointer tables to be typed |
| (d) BLOCKED | 140 | 487 | starts on a byte the assembler cannot spell |
| (c) DATA | 1,260 | 4,567 | genuine byte tables |

That table is the *run-level* verdict. The *shape* view is more informative:

* **1,537 runs / 2,873 B are flanked by CODE on BOTH sides** -- islands inside
  functions. 2,339 B of that is in runs of 1-4 bytes.
* **64 runs / 2,525 B are not** -- and 2,471 B of those sit in one place,
  `VoiceMode_ParamConfigTables`' 4-byte parameter records. That is the genuine
  data.

### The controls

* **KNOWN DATA** -- the `.byte` runs of the `sound_data_*.s` tone tables, which
  this lane is forbidden to touch precisely because they are data: **0 of 60
  runs, 0 B, classified CODE.** No false positives.
* **KNOWN CODE** -- 300 whole-instruction windows cut from long contiguous CODE
  runs, size-matched: **198/300 runs, 1,330/1,755 B = 75.8% byte-weighted.**
  So the CODE bucket is a FLOOR, understating by about a quarter.
  An earlier version of this control cut windows at ARBITRARY offsets and
  scored 55%. That was the control's fault, not the classifier's: a real
  `.byte` island was carved out of the source at an instruction boundary, so an
  arbitrary-offset window poses a harder question than the one being asked.

### How the classifier can be wrong

* It only sees references the CODE territory already contains. A run reached
  through a computed jump, or from the SUB-CPU image, has no visible reference
  and defaults to DATA. So "(c)" means *no evidence of code*, not *proven data*.
* Its context walk trusts the assembler's own framing of the bytes before the
  run. Where that framing is wrong -- and this lane found 480 B where it is --
  the walk inherits the error.
* **A measured false negative:** `AudioInit_VoiceRoutingTable`, 248 B, was
  classified DATA (the table-tail guard fired). Reading it end to end shows one
  routine. Found by hand, not by the instrument.

## Bucket (d), and the correction that landed mid-lane

The coordinator first reported a 46x enrichment of `.byte` runs starting on
`{01,04,17,1a,1c}` as evidence of hidden undecoded code, then corrected it to
"mis-framing, direction unknown", then **retracted it entirely** (a shuffle of
the same bytes decodes as cleanly as the bytes themselves; the control rate is
pinned near zero by construction).

This lane never converted anything to instructions on the strength of a blind
first byte. The check is mechanical: of the 11 spans converted TOWARD
instructions or `.long`, not one begins on a blind byte. Exactly one blind-start
span was touched -- 0xFEA514, first byte 0x01 -- and it was converted the OTHER
way, to typed data, where it turned out to be a **table of 16-bit powers of
two**. That is the retraction's own conclusion, reproduced independently here.

For the record, the raw counts in this lane's files (not a ratio -- the control
count is 2, and a ratio over 2 is noise): 100 of 1,563 runs start blind, 38 of
them in `dsp_config_sysex.s`. They are left TAGGED, not converted.

## What was converted

1. **Seven pointer tables, 352 B** (`convert_v10audio_ptr_tables.py`).
   Each is reached by code that computes `index * 4` and then either CALLs
   through the loaded word or copies a record from it. Three begin with a byte
   0xFF and have their unused slots all pointing at their own last byte + 1;
   the two big ones have entry[0] pointing at the byte just past the table and
   20 distinct targets whose sorted spacings are exactly the 0x58/0x44 lengths
   of the config blocks that follow. `VoiceMode3_DispatchTable` had 25 of its
   bytes spelled as `swi`/`jr`/`pushw`/`ldb` -- data-as-code.
   A rescan of all four alignment phases of every `.byte` run this lane owns
   finds no further pointer table.

2. **Four hand-read code runs, 193 B decoded of 318 B addressed**
   (`convert_v10audio_code_runs.py`). Including
   `AudioInit_VoiceRoutingTable`, whose name is a misnomer: 248 unreferenced
   bytes that are one routine. The label is left alone (semantic labeling is
   deferred) with a comment recording the finding.

3. **480 B of data-as-code retired** (`v10audio_retire_data_as_code.py`).
   `VoiceSlot_CheckAndApply_Data*` in `note_voice_mapping.s` was spelled as
   `halt` / `ei 7` / `ldio 9,10` / `pushw 268` / `.fill 8,1,0x04`. Every
   reference to those labels in the tree is `ld xiz, <label>` -- 20 sites, no
   call and no jump -- while the two branch-target labels in the same family
   are genuine code and were left alone. Every byte of 0xFEA356..0xFEA4B7 is
   <= 0x0F, and 0xFEA356..0xFEA3D9 is 0x01..0x0C repeated eleven times.
   Also re-framed one instruction whose leading 0xC2 an `.ascii` had swallowed.

4. **90 mis-framed instructions re-framed, 150 B** (`convert_v10audio_spans.py`).

## The biggest remaining shape, and why it is stuck

`v10audio_spans_reframe_feasibility.py`: **1,088 runs / 1,435 B** in this
lane's files are a `.byte` run holding the FIRST bytes of an instruction that
runs past its end -- the next source line is framed from mid-instruction.

    reframe spellable today   306 runs   379 B   (90 applied; see below)
    reframe blocked           546 runs   734 B   no encoding for the merged form
    refused, table-tail       236 runs   322 B

Of the 306 spellable, only 90 had a source line span matching the merged
instruction exactly; the other 215 would have eaten part of the next line and
were refused rather than guessed at. 1 more had a label inside its span.

## Why the rest of bucket (a) cannot be converted

`v10audio_blocked_forms.py`, on the final tree with llvm-mc `6f456a19f05b`:
**1 of 193 CODE-verdict runs is fully spellable.** The blockers are missing
backend encodings, not missing analysis:

    cp 131 B / set 75 / and 68 / res 68 / bit 44 / or 20 / add 18 ...

concentrated on the 0xF1 (`(nnnn)` direct), 0xB0 and 0x80/0x81 prefixes. These
are a DIFFERENT gap from the five blind leading bytes lane `w10/missinginsns`
is adding; nobody is currently fixing them, and they are worth ~500 B in this
lane alone and far more image-wide.

## Refusals, with reasons

* **0xFC972C (26 B) and 0xFC977B (26 B)**, `audio_control_engine.s`. NOT
  refused on the evidence -- refused because **another lane deliberately put
  them there**. Both carry a comment from lane V10DAC's STRICT rule calling
  them data-as-code. This lane reads them the other way: decoding from
  0xFC9772, which the tree ITSELF still spells as instructions, runs straight
  through both spans; the two spans `calr` the SAME routine 0xFC9DF4 from two
  sites; and every `jr Z` in them lands exactly on an `inc 2,XSP ; ret`
  epilogue. Data does not do that. 22 of each 28 B are spellable if this is
  adjudicated back to code. **This needs a coordinator decision, not a
  unilateral revert.**
* **0xFEA408 (26 B)**, `note_voice_mapping.s`. Decodes as `max ; reti ;
  ld (0x00),0x0704`, and starts on a blind byte, but the neighbourhood is
  `04 04 04 ... 04 07 00 00 04 07 0a 00` -- a small-value table. Left as data.
* **The 2,225 B of non-code-flanked `.byte` in `audio_control_engine.s`** --
  `VoiceMode_ParamConfigTables`' 4-byte parameter records. Genuine data,
  already correctly represented.
* **Every other data-as-code candidate in this lane's files.**
  `v10audio_data_as_code_spans.py` rebuilds lane V10DAC's unreached-CODE spans
  but lets a span bridge a `.byte` island (V10DAC's spans are maximal CODE
  territory, which shatters a misframed region -- it saw 24 B of a 441 B one).
  50 spans / 8,643 B come back "data-like" by the loose byte rule; exactly ONE
  is STRICT, and that one is the region already converted. Hand-reading the
  most periodic of the rest (per 83%, 74%, 63%, 53%) shows all four are **real
  code**: repeated per-voice code templates with an incrementing address
  operand. High periodicity in this ROM is as much a signature of generated
  code as of a table.

## Tooling hazards found

* **`grep` silently skips files here.** See
  `notes/lanes/grep-binary-skip-REPRODUCED-2026-09-02.md`. The brief marks this
  UNCONFIRMED; it reproduces, and the mechanism is ugrep's `-I` plus one lone
  0x81 continuation byte.
* **`convert_code_bytes.convert_block` is not deterministic.** It treats a
  unidasm timeout as "nothing decoded", so under load the same input gives a
  much worse conversion -- measured, 0xFDF61E gave 129 B then 12 B; 0xFDB289
  gave 18 B then 0 B. It degrades safely (more `.byte`, never wrong bytes) but
  it will quietly bank the bad result. `convert_v10audio_code_runs.py` builds
  every replacement twice and aborts if the two disagree.
* **A failed `make` leaves the previous ROM in place**, so `cmp` after a build
  that did not link says IDENTICAL. Check the mnemonic output or the ROM's
  mtime, not just `cmp`.
* **Writing a non-latin-1 character truncates the source file to zero.**
  `open(p,'w',encoding='latin-1')` opens (truncating) and only then raises on
  the bad character. One "warning sign" character in a comment emptied a
  47 KB file. Assert the text is latin-1 encodable BEFORE opening.
